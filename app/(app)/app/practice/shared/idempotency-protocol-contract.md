# Practice-Client Idempotency Protocol Contract

## Purpose

This is the binding law and owner inventory for client-side idempotent-mutation behavior in practice and question-review flows. It records the current implementation so future work does not have to reconstruct the protocol from bug archaeology. The inventory is descriptive of current source, including local variants and explicit non-applicability, and normative for every new client mutation surface. It does not assert that all surfaces share one state machine.

## The six laws

### 1. Key-to-intent binding

A preserved idempotency key may be reused only for the exact semantic request that minted it; any field that changes the write's meaning or persistence context creates a new intent and therefore a new key. This law originated in [BUG-295](<../../../../../docs/_archive/bugs/bug-295-preserved-idempotency-keys-replay-across-changed-intent.md>) and its sibling-surface sweep [BUG-298](<../../../../../docs/_archive/bugs/bug-298-preserved-keys-unbound-on-submit-mark-bookmark-surfaces.md>). New fingerprint-bound surfaces must use [`createRequestFingerprint`, `resolveRequestKey`, and `mintRequestKey`](<../../shared/idempotency-request-key.ts#L61>); start configuration and incomplete-session abandon retain the local owners named below, while end/finalize use dedicated operation refs rather than the shared fingerprint slot.

### 2. Determinacy-gated rotation

Thrown transport, timeout, and other outcome-indeterminate arms preserve the only replay handle; consumed success and returned determinate outcomes retire or rotate it, while a returned outcome that still represents unresolved execution remains preserved. The law originated across [BUG-289](<../../../../../docs/_archive/bugs/bug-289-idempotency-caches-transient-errors-billing-bookmark-feedback.md>), [BUG-290](<../../../../../docs/_archive/bugs/bug-290-state-write-idempotency-caches-transient-internal-error.md>), and [BUG-291](<../../../../../docs/_archive/bugs/bug-291-session-start-key-rotation-on-timeout-conflict-dead-end.md>), and [DEBT-457 Item 1](<../../../../../docs/_archive/debt/debt-457-wave2-determinacy-and-test-hygiene-residues.md#L27>) now applies it to end/finalize. Keyed surfaces reuse [`rotateIdempotencyKeyAfterDeterminateError`](<../../../../../src/adapters/controllers/shared/idempotency-error-policy.ts#L145>) or its generated-key wrapper; draft save and abandon use the documented local variants below.

### 3. Generation-CAS slot ownership

When overlapping invocations can write one persisted request-key slot, each invocation claims a monotonically increasing generation and only the current generation may change the slot; a stale continuation cannot replace a newer preserved key. [BUG-301](<../../../../../docs/_archive/bugs/bug-301-stale-feedback-completion-clobbers-newer-request-key.md>) established this law. Rating and report must reuse [`createRequestKeySlotStore` and `claimRequestKeySlot`](<../../shared/idempotency-request-key.ts#L32>); a ref, request sequence, in-flight boolean, or the start uncertainty tracker is a different fence and must not be described as this generation-CAS primitive.

### 4. Claim/uncertainty-fenced retirement

Every accepted start invocation owns an opaque claim, and retirement is refused while any claim is unsettled or a versioned same-key execution uncertainty may still commit; only a causally later same-key result may consume the uncertainty generation it observed. [BUG-300](<../../../../../docs/_archive/bugs/bug-300-concurrent-start-refresh-retires-pending-key.md>) established the typed concurrent-execution precursor and [BUG-303](<../../../../../docs/_archive/bugs/bug-303-concurrent-start-abandon-retires-still-running-key.md>) established the persistent claim/version retirement law. There is no shared helper: [`claimStartExecutionUncertainty` and `captureIdempotencyKeyRetirement`](<../hooks/use-practice-session-start.ts#L98>) are the single current owner, and abandon participates only when it asks that owner to retire a recovered start key.

### 5. Owner-fenced continuations

An asynchronous success or failure continuation may mutate a request-key slot or UI lifecycle only while it still owns the relevant request, question, session, or presentation generation; mount checks alone are only a limited variant. [BUG-301](<../../../../../docs/_archive/bugs/bug-301-stale-feedback-completion-clobbers-newer-request-key.md>) owns feedback token-slot fencing, [BUG-302](<../../../../../docs/_archive/bugs/bug-302-stale-report-completion-closes-newer-dialog.md>) owns report-dialog presentation fencing, and [BUG-303](<../../../../../docs/_archive/bugs/bug-303-concurrent-start-abandon-retires-still-running-key.md>) owns the start claim/current-key variant. Reuse [`claimRequestKeySlot`](<../../shared/idempotency-request-key.ts#L43>) for a shared token slot; request sequences, current-identity checks, in-flight serialization, and dialog generations remain surface-local owners.

### 6. Reason-discriminated recovery

Targeted conflict recovery is opt-in by an allowlisted machine-readable `details.reason`; absent, unknown, or known non-surface reasons take the generic fail-safe path, except for the explicitly scoped reasonless compatibility arms on session bootstrap and end/finalize. [DEBT-438](<../../../../../docs/_archive/debt/debt-438-conflict-reason-client-coverage-gaps.md>) established targeted recovery and the fail-safe default, and [DEBT-456](<../../../../../docs/_archive/debt/debt-456-client-conflict-reason-discrimination-gaps.md>) completed the bootstrap/end routing and scoped the two legacy exceptions. Practice-session routing must reuse the discriminators beginning at [`getActionResultPracticeSessionConflictReason`](<./question-flow-actions.ts#L224>)—including the ended-session, concurrent-request, and draft-expiry helpers there—while feedback retains its local exact [`feedback_request_token_reused` discriminator](<../../shared/question-feedback-actions.ts#L66>) and no reasonless exception.

## New-surface checklist

1. Name the semantic write intent and every payload/context field that can change its meaning. Decide whether the surface needs a client idempotency key; if it does not, record the accepted durability, admission, and concurrency owner instead of adding a key by reflex.
2. If keyed, define the complete request fingerprint and reuse `createRequestFingerprint`, `resolveRequestKey`, and `mintRequestKey`; do not create a surface-local token algorithm. Prove same-intent replay and changed-intent fresh execution at the real idempotency-wrapper boundary when that boundary is material.
3. Classify every completion arm before choosing key lifecycle: thrown transport/timeout or unresolved execution preserves; consumed success retires or rotates; returned determinate error rotates through the shared idempotency-error policy. Document any deliberate local lifecycle variant.
4. Identify the request-key slot owner. If overlapping invocations can write one slot, reuse `createRequestKeySlotStore` and `claimRequestKeySlot` and prove a superseded generation cannot clobber the current token; do not substitute a ref or UI pending state for generation CAS.
5. Ask whether any same-key execution may still commit after a refresh or recovery action. If yes, name the claim identity, uncertainty generation, causal consumption rule, and retirement owner, and prove retirement is refused while uncertainty or another claim remains.
6. Fence every post-`await` mutation by its real owner: mount, latest request/intent, current question/session, token generation, and any separate presentation lifecycle such as a dialog. Prove stale success, returned failure, and thrown failure cannot mutate the newer owner.
7. Route special recovery only through an exact allowlisted `details.reason`. Reuse `getActionResultPracticeSessionConflictReason` and `isPracticeSessionAlreadyEndedActionConflict`; absent, unknown, and known non-surface reasons must fail safe. A reasonless exception requires an existing API-specific compatibility record and must not spread to a new surface.
8. Ship behavior tests for every applicable law and a named non-applicability/variant for every other law: same versus changed intent, thrown versus returned determinate outcome, consumed success, stale continuation, allowed reason, and reasonless/unknown fallback. Use browser mode for interactive ownership races and do not weaken or duplicate the existing production-shaped suites.

## Explicit non-goals

- This contract implies no runtime abstraction or migration. The
  [DEBT-461 Phase B owner ruling](<../../../../../docs/_archive/debt/debt-461-practice-client-idempotency-machinery-consolidation.md>)
  closed NO-GO on 2026-07-23 because no two live surfaces have identical
  complete transitions. The documented per-surface design is permanent unless
  a new owner direction ruling explicitly reopens that decision.
- Server-side idempotency through `withIdempotency`/`executeIdempotent`, including [DEBT-424's cache-miss-only admission law](<../../../../../docs/_archive/debt/debt-424-rate-limit-idempotent-actions-on-cache-miss-only.md>), is a separate seam; this contract covers client keys, recovery, and continuation ownership.
- Phase A adds no executable characterization. Evidence gaps above are reported rather than filled here.
