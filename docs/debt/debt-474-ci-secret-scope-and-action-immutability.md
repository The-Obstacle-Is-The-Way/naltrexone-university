# DEBT-474: CI Secrets Are Job-Scoped and Required Workflows Reference Mutable Action Tags

**Status:** Open
**Priority:** P2
**Date:** 2026-08-24
**Source:** Split out of [DEBT-473](./debt-473-green-without-evidence.md) by the adversarial review of PR #831. That filing's first draft proposed mirroring the repository's E2E credentials into the Dependabot secrets store so Dependabot PRs could run the E2E lane; the review showed the proposal would widen an exposure that already exists: every provider credential CI holds is available to every step of the required job, and two of that job's actions (plus one in the trial-clock job) are referenced by floating tags that can be moved. All receipts read at `dev` `5a095f12` (identical tree to `main` `33cf36a4`) and from the GitHub API on 2026-08-24.

**Corrections (2026-08-24, PR #831 round 3).** The earlier correction accurately exempted Codecov's immutable `v7.0.0` release, but its Build paragraph omitted both Stripe price variables and `NEXT_PUBLIC_APP_URL`, treated the fork's skip-Clerk build as proof of a Clerk-enabled placeholder build, and quoted GitHub's SHA-only guidance as though the newer immutable-release documentation did not qualify it. The receipts and plan below now name the full build-time schema, keep the real Clerk server key Build-scoped until a focused test proves a placeholder works with Clerk enabled, require that exact proof before reducing the scope further, and present GitHub's two current guidance pages without collapsing their distinction. The final residue pass also removed option (b)'s contradictory instruction to execute an untrusted Dependabot head locally with the shared `.env.local` credentials and distinguished `dev`-targeted version updates' later promotion evidence from default-branch security updates' post-merge-only evidence. The exact-head review then relabeled the two verification greps as human inventories and made the YAML-aware workflow test the proof of scope and pin shape.

**Implementation re-audit (2026-08-26).** Re-derived steps 1 and 2 at `dev` `8b0f9b9a`. The required job still exposes the provider and E2E values at `ci.yml:35-62`, now to 4,213 unit tests as well as checkout/setup/install and every later command; the obsolete skip-policy grep was deleted by DEBT-473 step 2. Current consumers are Build at `:121-122`, the credential validator at `:129-181`, E2E at `:183-187`, and Playwright upload at `:189-198`. The hosted workflow still exposes its full set at job scope (`stripe-hosted-checkout-smoke.yml:38-52`) before Build (`:83-84`) and E2E (`:90-91`). Four textual action tags remain: required-CI setup-node (`ci.yml:77`), immutable Codecov v7.0.0 (`:115`), required-CI upload-artifact (`:191`), and provider-contract setup-node (`stripe-trial-clock-smoke.yml:33`); the hosted workflow is already fully pinned. The implementation will SHA-pin Codecov too so one YAML-aware rule can prove every `uses:` reference without growing release-API special cases. The Build boundary remains exactly `lib/env.ts:38-71,120-178`: real compiled `NEXT_PUBLIC_*` values, non-secret database/app values, and shape-valid server-only placeholders. The real Clerk secret is removed from Build only after the required Clerk-enabled placeholder build succeeds; E2E against that artifact remains the second receipt.

## Description

Two facts about `.github/workflows/ci.yml` combine into one exposure.

### F1 — Every credential is job-scoped, so every step can read it

`ci.yml:35-62` declares the job's `env:` block. It exports `CLERK_SECRET_KEY`, `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY`, `STRIPE_SECRET_KEY`, `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY`, `STRIPE_WEBHOOK_SECRET`, both price IDs, `E2E_CLERK_USER_USERNAME`, and `E2E_CLERK_USER_PASSWORD` from `secrets.*` (with dummy fallbacks for forks) at **job** scope. Those values are therefore present in checkout, pnpm setup, Node setup, install, typecheck, lint, migrate, seed, unit tests (4,213 cases), integration tests, the Chromium install, browser tests, Codecov upload, build, the credential validator, E2E, and the diagnostic upload. Only Build and E2E have any case for real provider values, and only E2E needs the full credential set. `lib/env.ts:38-71,120-178` makes Build nontrivial: it validates `DATABASE_URL`; the Clerk secret and publishable keys when `NEXT_PUBLIC_SKIP_CLERK` is false; the Stripe secret, publishable key, webhook secret, and both price IDs; and `NEXT_PUBLIC_APP_URL`. `lib/db.ts`, `lib/stripe.ts`, and `lib/container.ts` import that schema into the build graph. The fork path (`ci.yml:42-57`) proves only the skip-Clerk variant, not that a placeholder `CLERK_SECRET_KEY` works with Clerk enabled. Because CI's E2E reuses the Build artifact (`playwright.config.ts:51`: `pnpm start` under `CI`), the Clerk and Stripe publishable keys and both price IDs compiled into it must be the real public values; the app URL is already a non-secret job value. Stripe's server-only values need only satisfy import-time shape. Keep the real Clerk secret Build-scoped until the focused Clerk-enabled placeholder build in step 1 proves it can be reduced. Sentry needs no build secret (`lib/env.ts:73-76`; `instrumentation.ts:6-13` treats a missing DSN as disabled), and GitHub CI invokes `pnpm build`, not `vercel.json`'s migration-bearing `buildCommand`.

The repository already knows the correct pattern: `CRON_SECRET` is scoped to the single step that validates it (`ci.yml:124-127`), and the provider-contract workflow scopes `STRIPE_SECRET_KEY` and the price ID to its one execution step (`stripe-trial-clock-smoke.yml:41-46`). The required job does not follow it, and neither does `.github/workflows/stripe-hosted-checkout-smoke.yml:38-52`, which places the same full credential set at job scope ahead of checkout, install, migrate, seed, and build.

What runs inside that environment is not only repository code. The checkout/setup/upload steps execute third-party actions, and most commands after install execute third-party dependency code: typecheck (`tsc`), lint (Biome), migrate and seed (`tsx` plus the database stack), unit/integration/browser tests (Vitest and its plugins), build (Next.js), and E2E (Playwright), plus every transitive package they load. The credential validator is the only remaining pure-bash exception. A dependency bump changes exactly that code. `pnpm-workspace.yaml:83-92` sets `strictDepBuilds: true` and an eight-entry `allowBuilds` map (`@sentry/cli`, `@stripe/cli`, `esbuild`, `sharp` allowed; `@clerk/shared`, `bufferutil`, `core-js`, `utf-8-validate` denied), which makes `pnpm install` exit nonzero on any unreviewed *install* script ([pnpm docs, build settings](https://pnpm.io/settings/build): "When `strictDepBuilds` is enabled, the installation will exit with a non-zero exit code if any dependencies have unreviewed build scripts"). That protects the install step and nothing after it.

### F2 — Two actions in the required job, and one in the provider-contract job, are referenced by floating tags

| Workflow | Line | Reference | Immutable? |
| --- | --- | --- | --- |
| `ci.yml` | `:66` | `actions/checkout@3d3c42e5…` `# v7.0.1` | yes |
| `ci.yml` | `:71` | `pnpm/action-setup@0977fd99…` `# v6.0.10` | yes |
| `ci.yml` | `:77` | `actions/setup-node@v7` | **no** — floating major tag, no release object |
| `ci.yml` | `:115` | `codecov/codecov-action@v7.0.0` | yes — a GitHub immutable release (`gh api repos/codecov/codecov-action/releases/tags/v7.0.0` → `immutable: true`, 2026-08-24) |
| `ci.yml` | `:191` | `actions/upload-artifact@v7` | **no** — floating major tag, no release object |
| `stripe-trial-clock-smoke.yml` | `:33` | `actions/setup-node@v7` | **no** — runs before the step that receives `STRIPE_SECRET_KEY` |
| `stripe-hosted-checkout-smoke.yml` | `:25,:56,:61,:67,:95` | postgres by digest; checkout, pnpm, setup-node, upload-artifact by SHA | yes |

The hosted Checkout workflow is the repository's own standard: it pins by digest and SHA throughout, and `tests/ci-workflow.test.ts:148-156` enforces those pins *for that file only* ("pins dependencies that execute in the secret-bearing hosted workflow"). The required workflow — which bears the same secrets on every same-repo PR — and the provider-contract workflow have no equivalent test.

GitHub's [secure-use reference](https://docs.github.com/en/actions/reference/security/secure-use) still recommends full commit SHAs and warns that ordinary tags can be moved or deleted. Its newer [immutable-releases documentation](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases) supplies the important qualification: a published immutable release locks its associated exact tag against movement and deletion while the release exists. That is why `codecov-action@v7.0.0` is exempt from the finding; a floating major tag such as `@v7` has no release object to lock. The precedent remains exact: in [CVE-2025-30066](https://github.com/advisories/GHSA-mrrh-fwg8-r2c3) (advisory published 2025-03-15), `tj-actions/changed-files`' version tags were "retroactively modified … to reference a malicious commit," and the payload extracted runner-process secrets and printed them in workflow logs. The two floating references here are GitHub-owned, which lowers the likelihood, not the mechanism. SHA pinning remains the repository's uniform policy because the pin test cannot otherwise establish at review time that every exact tag is backed by an immutable release.

### F3 — The Dependabot gap is presented as a constraint, and the obvious fix is the unsafe one

`docs/dev/dependency-update-protocol.md:92` states that GitHub does not provide repository secrets to Dependabot PR workflows, and `tests/ci-workflow.test.ts:53-61` pins the E2E steps' actor guard on that rationale. GitHub's actual rule is that Dependabot-triggered workflows receive **Dependabot secrets** through the same `secrets` context ([GitHub Docs](https://docs.github.com/en/code-security/dependabot/troubleshooting-dependabot/troubleshooting-dependabot-on-github-actions)); `gh secret list --app dependabot` is empty. So the E2E lane *could* run on Dependabot PRs by copying the existing secrets into that store **and** removing the `github.actor != 'dependabot[bot]'` guard at `ci.yml:132,186` — both are required; the secrets alone change nothing — and given F1, that would place the shared Stripe test key, the Clerk dev-instance key, and the E2E user's password in the environment of a workflow whose entire purpose is to execute newly-bumped dependency code. That is the proposal DEBT-473's first draft made and the review rejected.

### F4 — What the credentials are, and what they reach

Names only; no value was read or printed.

- `STRIPE_SECRET_KEY` — TEST mode. Every lane (`local-dev`, `github-ci`, `github-stripe-hosted-smoke`, the `vercel-dev-preview` webhook) shares **one** Stripe test account, partitioned only by the `E2E_STRIPE_OWNER` metadata namespace ([DEBT-386](../_archive/debt/debt-386-e2e-stripe-customer-ownership-drift-webhook-500s.md) lineage; `tests/e2e/helpers/seed-test-user.ts`, `src/adapters/gateways/stripe/stripe-subscription-normalizer.ts:57-67`). The namespace prevents lanes from colliding; it does not limit what a holder of the key can create, read, or delete in that account.
- `CLERK_SECRET_KEY`, `E2E_CLERK_USER_USERNAME`, `E2E_CLERK_USER_PASSWORD` — the Clerk **dev instance** and its shared E2E user. `credential-health-check.ts` verifies the password against Clerk's API at every E2E start (`:490-495`).
- `STRIPE_WEBHOOK_SECRET` — the test-mode signing secret.
- `CRON_SECRET` — step-scoped (`ci.yml:124-127`), but its relationship to the production Vercel value is not recorded. [BUG-244](../_archive/bugs/bug-244-reconciliation-cron-never-scheduled.md) normalized `CRON_SECRET` across all Vercel scopes; whether the GitHub Actions copy equals Production is an owner fact. If it does, the CI copy authorizes production cron routes and should not exist in CI at all — the validation belongs where the value is consumed (`lib/env.ts:79` is `z.string().min(1).optional()` with no header-safety refine).
- `NEXT_PUBLIC_*` values are public by construction and are listed here only because they share the block.

Blast radius if exfiltrated: unbounded writes to the shared Stripe test account (customers, subscriptions, test clocks — the same resources the weekly smoke creates and deletes), Clerk dev-instance user takeover, forged test-mode webhooks, and — only if F4's `CRON_SECRET` question resolves the wrong way — unauthenticated production cron invocation.

**Steps 1 and 2 implementation (2026-08-26; guard correction 2026-08-27).** In required CI the only job-level `secrets.` reference is the value-free `NEXT_PUBLIC_SKIP_CLERK` presence expression (`ci.yml:35-44`). Build receives the four real-or-fallback compiled public values and three shape-valid server-only placeholders (`:106-116`); the full real Clerk/Stripe/E2E set exists only on `E2E smoke` (`:123-140`), while Codecov and the header validator each receive only their own value. The hosted workflow has the same Build/E2E split (`stripe-hosted-checkout-smoke.yml:73-101`). A Clerk-enabled local Build using the real public values and dummy server-only values completed all 23 static routes; `CI=1 pnpm test:e2e` then used that exact artifact through `next start` without rebuilding and passed 43/43 with the real TEST-mode credentials supplied only at runtime. The YAML-aware contract enumerates every permitted secret consumer in all three workflows (`tests/ci-workflow.test.ts:217-279`). A pre-push synthetic fixture then proved the first implementation missed workflow-level and non-`env` job fields; that fixture failed red and the contract now inspects those fields too. Every step-level action and job-level reusable-workflow reference in those files must be a full SHA with a version comment (`tests/ci-workflow.test.ts:298-321`); a second synthetic red fixture proved the original step-only walk missed the job form. Primary GitHub tag receipts match setup-node `v7.0.0`, Codecov `v7.0.0`, and upload-artifact `v7.0.1` (the initial `v7.0.0` comment on the correct upload SHA was caught and corrected before commit). Steps 3-5 remain owner decisions, so this debt stays Open.

## Impact

1. A compromised or tag-moved action, or a malicious transitive dependency executing under typecheck/test/build, can read every provider credential the repository holds, on every same-repo push and PR. TEST-mode scope bounds the damage to the shared test account and the dev Clerk instance, which is why this is P2 and not P1; the `CRON_SECRET` question is the one thing that could raise it.
2. The safe way to give Dependabot PRs E2E evidence (DEBT-473 step 6) cannot be chosen until F1 is fixed, because any credential placed in the Dependabot store inherits the job-scope exposure.
3. The repository's own pinning standard is enforced for the workflow that runs daily and not for the one that runs on every PR.

## Resolution

1. **[x] Step-scope every secret (2026-08-26).** Move the Clerk, Stripe, and E2E entries out of the job-level `env:` (`ci.yml:35-62`) into `env:` blocks on the steps that consume them. `Build` receives the real `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY`, `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY`, and both price IDs (public and compiled into the artifact E2E reuses); the existing non-secret `DATABASE_URL` and `NEXT_PUBLIC_APP_URL`; shape-valid placeholders for `STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET`; and, conservatively, the real `CLERK_SECRET_KEY`. First run a Clerk-enabled Build with a placeholder Clerk secret and the real public key. Only if Build and E2E against that exact artifact pass may the real Clerk secret be removed from Build; the fork's `NEXT_PUBLIC_SKIP_CLERK=true` path is not that proof. `NEXT_PUBLIC_SKIP_CLERK` may remain the single job-level `secrets.` expression, because it tests presence and yields no secret value; the full real set goes to `E2E smoke` only (the bash validator is deleted by DEBT-473 step 3(e)). Apply the same scoping to `stripe-hosted-checkout-smoke.yml`. Migrate, seed, unit, integration, browser, typecheck, lint, and Codecov run with no provider credential in their environment — which is also the honest statement of what they need (DEBT-473 F5 measured the browser lane at 64/398 with all of them unset; the integration provider suites skip without their flags). Red-first: `tests/ci-workflow.test.ts` asserts that the job-level `env:` contains no `secrets.` reference other than the `NEXT_PUBLIC_SKIP_CLERK` presence expression and enumerates which steps may carry each credential, for both secret-bearing workflows. The step that would fail if this is done naively is `Build` at `ci.yml:121`; exercise both the conservative set and the attempted placeholder reduction before merging.
2. **[x] Pin every `uses:` in all three workflows to a full commit SHA with a version comment (2026-08-26)**, and extend `tests/ci-workflow.test.ts:148-156` from the hosted workflow to `ci.yml` and `stripe-trial-clock-smoke.yml` (red-first: the test must fail on the current `@v7`/`@v7.0.0` references). `.github/dependabot.yml:75-83` already covers the `github-actions` ecosystem against `dev`; Dependabot updates SHA pins and their comments together, so pinning does not freeze the actions.
3. **[ ] Resolve `CRON_SECRET`.** Owner confirms whether the GitHub Actions value equals the production Vercel value. If it does: remove it from CI and rotate; move the header-safety check to a zod `.refine` on `lib/env.ts:79` (or the Vercel build), and delete the `Validate header-safe CI secrets` step (`ci.yml:124-127`) and its script's CI role (the function can stay). If it does not: record that fact in `docs/dev/deployment-environments.md` and keep the step or move it per the same reasoning.
4. **[ ] Decide Dependabot E2E, with least privilege.** After steps 1–2, DEBT-473 step 6 can choose between (a) **dedicated, disposable TEST-mode identities** stored as Dependabot secrets, scoped to the E2E steps only and rotated on a schedule. True isolation requires a separate [Stripe Sandbox](https://docs.stripe.com/sandboxes) — fully isolated, so it needs its own products, prices, keys, and webhook endpoint, and `E2E_STRIPE_OWNER` is still required inside it by the seed, cleanup, and contract code — and a separate Clerk development instance. A second user or a restricted key inside the *shared* account only narrows permissions and still reaches every shared object; a restricted `rk_test_` key is additionally not usable without code, because the provider gate (DEBT-473 step 1) and the E2E Stripe client require the `sk_test_` prefix, and would need a credential-gated proof of the full permission set (Checkout, customers, subscriptions, prices, test clocks, CLI fixtures). Choose the isolated form or state the reduced-permissions form for what it is; or (b) no credentials for Dependabot PRs, with the absence made explicit in the evidence summary (DEBT-473 step 3): `dev`-targeted version updates receive later promotion-PR and post-merge `main` E2E, while default-branch security updates receive only post-merge `main` E2E; or (c) a trusted, manually dispatched provider run on the exact PR head after human review, recorded in the PR. Option (a) is the only one that yields automatic PR-time hosted E2E evidence; (b) defers evidence until after the Dependabot change merges, and (c) supplies explicit PR-time evidence. Never execute the untrusted Dependabot head locally with the existing shared credentials, and never copy those credentials into the Dependabot store.
5. **[ ] Record the standard.** Add to `docs/dev/deployment-environments.md` (or a new `docs/dev/ci-secrets.md`): secrets are step-scoped; every `uses:` is SHA-pinned; the pin test covers every workflow; Dependabot secrets, if any, are dedicated identities. Reference it from `AGENTS.md`'s CI section.

## Verification

- `grep -nE "secrets\." .github/workflows/ci.yml .github/workflows/stripe-hosted-checkout-smoke.yml` is the human-readable inventory. The YAML-aware `tests/ci-workflow.test.ts` assertion is authoritative: it proves that both jobs have no job-level `secrets.` reference except the named `NEXT_PUBLIC_SKIP_CLERK` presence expression and enumerates the allowed step-level credential consumers.
- `grep -nE "uses: .*@v[0-9]" .github/workflows/*.yml` is the human-readable floating-tag inventory and returns nothing. The YAML-aware workflow test parses every `uses:` entry in all three files, requires a 40-character SHA plus version comment, and is red on the pre-fix tree.
- A Clerk-enabled `Build` succeeds with the conservative scoped set and E2E succeeds against that exact artifact. If the real Clerk secret is removed from Build, a second receipt proves the same pair with a placeholder Clerk secret and real publishable key; the skip-Clerk fork build cannot satisfy this bullet.
- A same-repo CI run on the fixed head is green with the migrate, seed, browser, integration, and unit steps showing no provider credential in `env` (inspect the step's environment via a diagnostic `env | grep -c STRIPE_SECRET_KEY` step during implementation only; remove before merge).
- The `CRON_SECRET` decision is dated and recorded; if rotated, the Vercel scopes and the cron route are verified with the new value per BUG-244's procedure.
- The Dependabot decision is dated and recorded; if (a), `gh secret list --app dependabot` lists only the dedicated identities and the E2E steps' `env:` reads them.
