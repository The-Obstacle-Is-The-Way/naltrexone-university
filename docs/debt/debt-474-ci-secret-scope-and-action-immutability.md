Two facts about `.github/workflows/ci.yml` combine into one exposure.

### F1 — Every credential is job-scoped, so every step can read it

`ci.yml:35-62` declares the job's `env:` block. It exports `CLERK_SECRET_KEY`, `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY`, `STRIPE_SECRET_KEY`, `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY`, `STRIPE_WEBHOOK_SECRET`, both price IDs, `E2E_CLERK_USER_USERNAME`, and `E2E_CLERK_USER_PASSWORD` from `secrets.*` (with dummy fallbacks for forks) at **job** scope. Those values are therefore present in checkout, pnpm setup, Node setup, install, typecheck, lint, migrate, seed, unit tests (4,213 cases), integration tests, the Chromium install, browser tests, Codecov upload, build, the credential validator, E2E, and the diagnostic upload. Only Build and E2E have any case for real provider values, and only E2E needs the full credential set. `lib/env.ts:38-71,120-178` makes Build nontrivial: it validates `DATABASE_URL`; the Clerk secret and publishable keys when `NEXT_PUBLIC_SKIP_CLERK` is false; the Stripe secret, publishable key, webhook secret, and both price IDs; and `NEXT_PUBLIC_APP_URL`. `lib/db.ts`, `lib/stripe.ts`, and `lib/container.ts` import that schema into the build graph. The fork path (`ci.yml:42-57`) proves only the skip-Clerk variant, not that a placeholder `CLERK_SECRET_KEY` works with Clerk enabled. Because CI's E2E reuses the Build artifact (`playwright.config.ts:51`: `pnpm start` under `CI`), the Clerk and Stripe publishable keys and both price IDs compiled into it must be the real public values; the app URL is already a non-secret job value. Stripe's server-only values need only satisfy import-time shape. Keep the real Clerk secret Build-scoped until the focused Clerk-enabled placeholder build in step 1 proves it can be reduced. Sentry needs no build secret (`lib/env.ts:73-76`; `instrumentation.ts:6-13` treats a missing DSN as disabled), and GitHub CI invokes `pnpm build`, not `vercel.json`'s migration-bearing `buildCommand`.

The repository already knows the correct pattern: `CRON_SECRET` is scoped to the single step that validates it (`ci.yml:124-127`), and the provider-contract workflow scopes `STRIPE_SECRET_KEY` and the price ID to its one execution step (`stripe-trial-clock-smoke.yml:41-46`). The required job does not follow it, and neither does `.github/workflows/stripe-hosted-checkout-smoke.yml:38-52`, which places the same full credential set at job scope ahead of checkout, install, migrate, seed, and build.

What runs inside that environment is not only repository code. The checkout/setup/upload steps execute third-party actions, and most commands after install execute third-party dependency code: typecheck (`tsc`), lint (Biome), migrate and seed (`tsx` plus the database stack), unit/integration/browser tests (Vitest and its plugins), build (Next.js), and E2E (Playwright), plus every transitive package they load. The credential validator is the only remaining pure-bash exception. A dependency bump changes exactly that code. `pnpm-workspace.yaml:83-92` sets `strictDepBuilds: true` and an eight-entry `allowBuilds` map (`@sentry/cli`, `@stripe/cli`, `esbuild`, `sharp` allowed; `@clerk/shared`, `bufferutil`, `core-js`, `utf-8-validate` denied), which makes `pnpm install` exit nonzero on any unreviewed *install* script ([pnpm docs, build settings](https://pnpm.io/settings/build): "When `strictDepBuilds` is enabled, the installation will exit with a non-zero exit code if any dependencies have unreviewed build scripts"). That protects the install step and nothing after it.

### F2 — Two actions in the required job, and one in the provider-contract job, are referenced by floating tags

| Workflow | Line | Reference | Immutable? |

The hosted Checkout workflow is the repository's own standard: it pins by digest and SHA throughout, and `tests/ci-workflow.test.ts:148-156` enforces those pins *for that file only* ("pins dependencies that execute in the secret-bearing hosted workflow"). The required workflow — which bears the same secrets on every same-repo PR — and the provider-contract workflow have no equivalent test.

GitHub's [secure-use reference](https://docs.github.com/en/actions/reference/security/secure-use) still recommends full commit SHAs and warns that ordinary tags can be moved or deleted. Its newer [immutable-releases documentation](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases) supplies the important qualification: a published immutable release locks its associated exact tag against movement and deletion while the release exists. That is why `codecov-action@v7.0.0` is exempt from the finding; a floating major tag such as `@v7` has no release object to lock. The precedent remains exact: in [CVE-2025-30066](https://github.com/advisories/GHSA-mrrh-fwg8-r2c3) (advisory published 2025-03-15), `tj-actions/changed-files`' version tags were "retroactively modified … to reference a malicious commit," and the payload extracted runner-process secrets and printed them in workflow logs. The two floating references here are GitHub-owned, which lowers the likelihood, not the mechanism. SHA pinning remains the repository's uniform policy because the pin test cannot otherwise establish at review time that every exact tag is backed by an immutable release.

### F3 — The Dependabot gap is presented as a constraint, and the obvious fix is the unsafe one

`docs/dev/dependency-update-protocol.md:92` states that GitHub does not provide repository secrets to Dependabot PR workflows, and `tests/ci-workflow.test.ts:53-61` pins the E2E steps' actor guard on that rationale. GitHub's actual rule is that Dependabot-triggered workflows receive **Dependabot secrets** through the same `secrets` context ([GitHub Docs](https://docs.github.com/en/code-security/dependabot/troubleshooting-dependabot/troubleshooting-dependabot-on-github-actions)); `gh secret list --app dependabot` is empty. So the E2E lane *could* run on Dependabot PRs by copying the existing secrets into that store **and** removing the `github.actor != 'dependabot[bot]'` guard at `ci.yml:132,186` — both are required; the secrets alone change nothing — and given F1, that would place the shared Stripe test key, the Clerk dev-instance key, and the E2E user's password in the environment of a workflow whose entire purpose is to execute newly-bumped dependency code. That is the proposal DEBT-473's first draft made and the review rejected.

### F4 — What the credentials are, and what they reach

Names only; no value was read or printed.

- `STRIPE_SECRET_KEY` — TEST mode. Every lane (`local-dev`, `github-ci`, `github-stripe-hosted-smoke`, the `vercel-dev-preview` webhook) shares **one** Stripe test account, partitioned only by the `E2E_STRIPE_OWNER` metadata namespace ([DEBT-386](../_archive/debt/debt-386-e2e-stripe-customer-ownership-drift-webhook-500s.md) lineage; `tests/e2e/helpers/seed-test-user.ts`, `src/adapters/gateways/stripe/stripe-subscription-normalizer.ts:57-67`). The namespace prevents lanes from colliding; it does not limit what a holder of the key can create, read, or delete in that account.
- `CLERK_SECRET_KEY`, `E2E_CLERK_USER_USERNAME`, `E2E_CLERK_USER_PASSWORD` — the Clerk **dev instance** and its shared E2E user. `credential-health-check.ts` verifies the password against Clerk's API at every E2E start (`:490-495`).
- `STRIPE_WEBHOOK_SECRET` — the test-mode signing secret.
- `CRON_SECRET` — step-scoped (`ci.yml:124-127`), but its relationship to the production Vercel value is not recorded. [BUG-244](../_archive/bugs/bug-244-reconciliation-cron-never-scheduled.md) normalized `CRON_SECRET` across all Vercel scopes; whether the GitHub Actions copy equals Production is an owner fact. If it does, the CI copy authorizes production cron routes and should not exist in CI at all — the validation belongs where the value is consumed (`lib/env.ts:79` is `z.string().min(1).optional()` with no header-safety refine).
- `NEXT_PUBLIC_*` values are public by construction and are listed here only because they share the block.

Blast radius if exfiltrated: unbounded writes to the shared Stripe test account (customers, subscriptions, test clocks — the same resources the weekly smoke creates and deletes), Clerk dev-instance user takeover, forged test-mode webhooks, and — only if F4's `CRON_SECRET` question resolves the wrong way — unauthenticated production cron invocation.

## Impact

1. A compromised or tag-moved action, or a malicious transitive dependency executing under typecheck/test/build, can read every provider credential the repository holds, on every same-repo push and PR. TEST-mode scope bounds the damage to the shared test account and the dev Clerk instance, which is why this is P2 and not P1; the `CRON_SECRET` question is the one thing that could raise it.
2. The safe way to give Dependabot PRs E2E evidence (DEBT-473 step 6) cannot be chosen until F1 is fixed, because any credential placed in the Dependabot store inherits the job-scope exposure.
3. The repository's own pinning standard is enforced for the workflow that runs daily and not for the one that runs on every PR.
