# DEBT-453: Duplicated Data Contracts — Difficulty Literals at 6+ Sites, Effective-Selection Rule Triplicated, Write/Read Schema Coupling, Dead `deleteById` Port Method

**Status:** Active
**Priority:** P4
**Date:** 2026-07-09

---

## Description

Four independently verified findings share one root pattern: a data contract that exists in the codebase more than once (or serves two roles at once), with nothing — no shared symbol, no cross-pinning test, no comment — tying the copies together. Each is harmless today; each converts a routine future edit into a silent divergence.

### 1. Write/read schema conflation in `practice-session-params.ts`

[`parsePracticeSessionParamsJson`](../../src/adapters/repositories/practice-session-params.ts#L51) is one schema serving two roles: it validates new sessions at write time ([`create()` at drizzle-practice-session-repository.ts#L372](../../src/adapters/repositories/drizzle-practice-session-repository.ts#L372), controller input via `practice-schemas.ts`) **and** re-parses every stored `practice_sessions.params_json` row on read ([drizzle-practice-session-repository.ts#L182](../../src/adapters/repositories/drizzle-practice-session-repository.ts#L182)). The schema embeds today's mutable product limits — [`MAX_PRACTICE_SESSION_QUESTIONS = 200`](../../src/adapters/shared/validation-limits.ts#L34), 50 tag filters, 3 difficulties, 255-char slugs — plus the closed difficulty enum ([line 15](../../src/adapters/repositories/practice-session-params.ts#L15)), so the read path re-validates immutable historical data against mutable business rules. A read failure becomes [`CorruptPracticeSessionRowError`](../../src/adapters/repositories/drizzle-practice-session-repository.ts#L188): skipped-and-logged out of history lists ([#L290](../../src/adapters/repositories/drizzle-practice-session-repository.ts#L290), [#L349](../../src/adapters/repositories/drizzle-practice-session-repository.ts#L349) — the DEBT-439 behavior) and `INTERNAL_ERROR` on direct open. Nothing documents the coupling: [`validation-limits.ts`](../../src/adapters/shared/validation-limits.ts#L9) describes the constants purely as input-abuse bounds, and no test parses fixtures at the historical maxima. An innocuous-looking limit reduction or enum rename ships with green CI (fixtures stay within the new limits; the 0027 CHECK only guards `jsonb_typeof = 'object'`) and makes completed sessions vanish from history — or silently resets an oversized active session — with no data actually corrupt. The same mechanism fires in reverse on rollback after a limit increase. The class has one prior real occurrence: the DEBT-428 `zUuid`/count-match tightening reclassified a real dev row as corrupt and needed repair migration 0026 plus multi-environment proof; that archived doc resolved the instance, not the pattern.

### 2. Effective-selection rule triplicated across use cases

The derivation deciding which choice counts as a question's answer — `session.mode === 'exam' && session.endedAt === null ? (draftSelectedChoiceId ?? latestSelectedChoiceId) : latestSelectedChoiceId` — is maintained as three byte-identical private functions: [`getIncompleteSelectedChoiceId`](../../src/application/use-cases/get-incomplete-practice-session.ts#L20) (resume-card answered count), [`getReviewSelectedChoiceId`](../../src/application/use-cases/get-practice-session-review.ts#L56) (review-grid answeredCount/isAnswered), and [`getSessionSelectedChoiceId`](../../src/application/use-cases/get-next-question.ts#L87) (next-unanswered navigation). The natural shared home, [`src/application/shared/practice-session-state.ts`](../../src/application/shared/practice-session-state.ts#L7), is already imported by these use cases but hosts no selection helper; each site's tests pin only its own copy, so nothing ties the three together. The rule is recorded prose-only in [master_spec.md §4.5](../../docs/specs/master_spec.md#L1077). A future change to what counts as "answered" for an active exam (a BUG-254-style grace-window tweak, stale-draft exclusion) applied to one copy and missed on the others keeps every per-site suite green while the resume card, review grid, and next-unanswered navigation disagree for the same session. (The sweep candidate said two sites; verification found three — `get-next-question.ts` is the third.)

### 3. Dead `AttemptWriter.deleteById` since the BUG-197 transaction fix

[`AttemptWriter.deleteById(id, userId)`](../../src/application/ports/attempt-repository.ts#L61) has zero production or test callers: its only consumer was the manual submit-answer rollback removed by the BUG-197 transaction fix ("The manual rollback pattern... has been fully removed" — [archived BUG-197](../_archive/bugs/bug-197-submit-answer-two-phase-write-without-transaction.md)). The Drizzle implementation ([drizzle-attempt-repository.ts#L214](../../src/adapters/repositories/drizzle-attempt-repository.ts#L214)) deletes only the `attempts` row, unwrapped in any transaction and with no compensating update to `practice_session_question_states`, whose [`latest_selected_choice_id`/`latest_is_correct`](../../db/schema.ts#L494) columns are dual-written derived state that every live writer maintains transactionally. A future feature (attempt retraction, GDPR-style deletion, admin cleanup) that calls the already-present method on a session-linked attempt recreates exactly the attempts↔states divergence BUG-197's transaction was introduced to prevent — Summary/History still count the question answered while Dashboard counts and accuracy drop — with no compile-time or runtime signal that a compensating state write was required. Today the cost is hygiene only: dead port method, dead adapter code, dead fake method ([fake-attempt-repository.ts#L83](../../src/application/test-helpers/fakes/fake-attempt-repository.ts#L83)), and [architecture-layers.md#L117](../../docs/practice-engine/architecture-layers.md#L117) still advertising `AttemptWriter — insert, deleteById` as live API.

### 4. Difficulty literal `['easy','medium','hard']` re-encoded at 6+ sites

The difficulty value set is independently hardcoded in: the canonical [`AllDifficulties`](../../src/domain/value-objects/question-difficulty.ts#L4); [`zDifficulty`](../../src/adapters/shared/zod-schemas.ts#L6) (hardcoded, even though line 8's `zQuestionProgressStatus` correctly derives via `z.enum(AllQuestionProgressStatuses)`); a local [`questionDifficultySchema`](../../src/adapters/repositories/practice-session-params.ts#L15) that ignores `zDifficulty` despite importing `zUuid` from the same barrel two lines up; an inline `z.enum` in [review-controller.ts#L24](../../src/adapters/controllers/review-controller.ts#L24); inline TS literal types in [question-view-controller.ts#L31](../../src/adapters/controllers/question-view-controller.ts#L31), [get-practice-session-review.ts#L25](../../src/application/use-cases/get-practice-session-review.ts#L25), and [get-completed-session-questions-with-feedback.ts#L34](../../src/application/use-cases/get-completed-session-questions-with-feedback.ts#L34); the [`pgEnum` in db/schema.ts#L30](../../db/schema.ts#L30); and app-layer copies like [history-search-params.ts#L8](<../../app/(app)/app/history/history-search-params.ts#L8>). This re-duplicates the exact class [DEBT-172](../_archive/debt/debt-172-duplicate-zod-schemas-across-controllers.md) resolved in 2026-02 (its resolution created `zod-schemas.ts`); the two zod re-encodings postdate that consolidation.

**Verifier correction — the candidate's corruption path is refuted.** The claimed cascade (stale persisted-params validator → rows persisted with a new difficulty → read-time `INTERNAL_ERROR` → sessions silently hidden) cannot happen: (1) widening `AllDifficulties` fails `pnpm typecheck` inside the cited file itself ([practice-session-params.ts#L85](../../src/adapters/repositories/practice-session-params.ts#L85) assigns `readonly QuestionDifficulty[]` into the narrower schema-inferred return type) and at [get-practice-session-review.ts#L144](../../src/application/use-cases/get-practice-session-review.ts#L144); (2) `create()` parses `params_json` with the same schema before insert ([#L372](../../src/adapters/repositories/drizzle-practice-session-repository.ts#L372)), so the app can never persist a value its own read path rejects. What remains is co-evolution burden (~8 encodings per enum change) plus two compiler-silent, fail-closed input-side copies: a stale `zDifficulty` rejects the new difficulty with `VALIDATION_ERROR` (caught when first exercised), and a stale `review-controller.ts` inline enum can ship unnoticed — the attempted-questions review filter silently cannot filter by the new difficulty (optional param; no test would fail). The `pgEnum` + frozen migration SQL copies are intentional history and do not count as drift risk on their own.

## Impact

Today: zero user-visible breakage from any part — no persisted row trips part 1 (post-0026/0027 proofs), all three part-2 copies are identical, part 3 has zero callers, and part 4's copies all agree. All cost is latent and triggers only on a future edit:

- **Part 1** is the sharpest edge within P4: a green-CI limit tweak silently vanishes historical sessions (the DEBT-439 skip-and-log behavior makes list-read failures invisible), with a proven prior occurrence (DEBT-428 → migration 0026).
- **Part 2** produces user-visible cross-surface disagreement (resume count vs review grid vs next-unanswered) if the rule is ever edited at fewer than all three sites; per-site tests cannot catch it.
- **Part 3** is comprehension/hygiene today; if resurrected it silently breaks the attempts↔session-state invariant with no signal.
- **Part 4** is a developer scavenger hunt per enum change plus one narrow, compiler-silent user-facing filter gap that can outlive a feature launch. No data-corruption path exists (verifier-refuted; severity downgraded P3 → P4 accordingly).

## Proposed Resolution

**Part 1 — write/read schema coupling:**
- **Option 1 (RECOMMENDED, cheapest, matches the in-file DEBT-433 precedent):** add a load-bearing comment block in `practice-session-params.ts` (plus a one-line cross-reference in `validation-limits.ts`) stating the schema is also the read-time compatibility contract for all persisted `params_json` rows — any tightening of an imported limit or the difficulty enum retroactively reclassifies conforming historical rows as corrupt and MUST be paired with a data audit/repair migration per the DEBT-428 playbook.
- Option 2 (structural, if the schema is touched anyway): split into a strict write-side schema (business limits + enum) used by `create()`/controllers and a permissive read-side schema (structural checks only: types, `zUuid`, uniqueness, `count === questionIds.length`), so persisted data can never be invalidated by product-limit changes.
- Option 3 (pinning test): a characterization test round-tripping fixtures at the exact historical maxima (count=200, 50 tagSlugs, 3 difficulties, 255-char slug, every enum value) through `parsePracticeSessionParamsJson`, named/commented to direct anyone who breaks it to write a repair migration first.

**Part 2 — effective-selection rule:**
- **Option 1 (RECOMMENDED):** extract one exported helper — e.g. `getEffectiveSelectedChoiceId(session: Pick<PracticeSession, 'mode' | 'endedAt'>, state: Pick<PracticeSessionQuestionState, 'latestSelectedChoiceId' | 'draftSelectedChoiceId'>)` — into `src/application/shared/practice-session-state.ts` (already imported by all three use cases; zero new dependency edges), replace the three private copies, and unit-test the helper directly.
- Option 2 (minimal): export the three copies and add a single test asserting identical outputs over a branch-covering input matrix.
- Option 3: do nothing and accept documented drift risk (the rule lives prose-only in `master_spec.md`).

**Part 3 — dead `deleteById`:**
- **Option 1 (RECOMMENDED):** delete `deleteById` from the port, `DrizzleAttemptRepository`, and `FakeAttemptRepository`; update `architecture-layers.md` to `AttemptWriter — insert`. Zero callers means a pure deletion verified by typecheck.
- Option 2: if a retraction/deletion feature is genuinely imminent, keep it but add a port doc comment requiring callers to run inside a transaction that also compensates `practice_session_question_states`, plus a lint/test guard against direct use.
- Option 3: move it to a separate `AttemptDeleter` port not extended by `AttemptRepository`, so any future consumer opts in explicitly and confronts the invariant.

**Part 4 — difficulty literals:**
- **Option 1 (RECOMMENDED):** derive and consolidate — `zDifficulty = z.enum(AllDifficulties)` (mirroring the `zQuestionProgressStatus` pattern); import shared `zDifficulty` in `practice-session-params.ts` and `review-controller.ts`; replace inline `'easy' | 'medium' | 'hard'` TS types with `QuestionDifficulty` imports; derive the pgEnum via `pgEnum('question_difficulty', [...AllDifficulties])`, leaving migration SQL as the one intentional frozen copy.
- Option 2 (minimal): fix only the three zod copies — this closes the only compiler-silent, potentially-shipped gap (the review-controller filter) while leaving compiler-guarded TS literals and the migration-guarded pgEnum alone.
- Option 3 (tripwire only): a unit test asserting `zDifficulty.options`, `questionDifficultySchema.options`, and `questionDifficultyEnum.enumValues` each deep-equal `AllDifficulties`, converting future drift into a red test without refactoring.

## Verification

- **Part 1:** the comment block exists in `practice-session-params.ts` and `validation-limits.ts` cross-references it; if Option 3 is taken, the historical-maxima characterization test passes and its name references the repair-migration requirement.
- **Part 2:** three private copies gone, one exported helper in `practice-session-state.ts` with a unit test covering active-exam-draft / ended-exam / tutor branches; existing per-site tests still green.
- **Part 3:** `grep -r 'deleteById' src/ docs/practice-engine/` returns no `AttemptWriter` hits; `pnpm typecheck` passes; `architecture-layers.md:117` reads `AttemptWriter — insert`.
- **Part 4:** `grep -rn "'easy', 'medium', 'hard'" src/` returns only `question-difficulty.ts` (and frozen migration SQL under `db/migrations/`); or, for Option 3, the enum-parity test exists and passes.
