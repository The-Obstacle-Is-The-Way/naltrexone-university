# DEBT-443: Idempotency Cache Durability and Evolution Gaps — Schema-Drift Replay Poisoning, Lossy Error Records, Production-Dead Lifecycle Cache Branch

**Status:** Active
**Priority:** P3
**Date:** 2026-07-09

---

## Description

The idempotency cache (`idempotency_keys` + `withIdempotency`) treats stored outcomes as durable data but has no evolution story for them: replayed results are validated against whatever schema the *current* deploy ships, cached errors persist only a subset of `ApplicationError`'s payload channels, and one of the cache's dedicated policy branches is exercised only by fabricated test fixtures. Three constituent findings, adversarially verified 2026-07-09.

### 1. Replay validates cached `result_json` against the CURRENT `.strict()` schema — no version stamp, no invalidation

[`executeIdempotent`](../../src/adapters/controllers/shared/execute-idempotent.ts#L56) unconditionally passes `parseResult: (value) => outputSchema.parse(value)` into `withIdempotency`, and every controller output schema is `z.object({...}).strict()` (~20 across practice/billing/bookmark/feedback/question controllers — e.g. [`FinalizeExamAnswersOutputSchema`](../../src/adapters/controllers/practice-schemas.ts#L173), [`CreatePortalSessionOutputSchema`](../../src/adapters/controllers/billing-controller.ts#L49)). On replay of a completed row ([`with-idempotency.ts:319-333`](../../src/adapters/shared/with-idempotency.ts#L319)), the pre-deploy `result_json` is parsed with the post-deploy schema: an ADDED required field fails (missing key) and a REMOVED field also fails (`.strict()` rejects unknown keys) — brittle in both evolution directions, a backward-compatibility violation for stored data. The parse-failure catch throws `ApplicationError('INTERNAL_ERROR', 'Cached idempotency result is invalid')` without deleting or aborting the row, and [`idempotency_keys`](../../db/schema.ts#L300) has no schema-version column, so the row stays poisoned until `expiresAt` ([24h default TTL](../../src/adapters/shared/with-idempotency.ts#L16)).

Failure scenario: a deploy changes any idempotent action's output shape; request 1 completes pre-deploy and stores `result_json` under the old shape; a duplicate/retry with the same key arrives post-deploy within the TTL — e.g. an exam-finalize retry after the "concurrent request still processing" branch (which deliberately does NOT rotate the key, [practice-session-page-logic.ts:277-283](<../../app/(app)/app/practice/[sessionId]/practice-session-page-logic.ts#L277>)), or a double-submit of a billing form rendered pre-deploy. The replay parses the old payload with the new schema, parse throws, and the user gets INTERNAL_ERROR. The verifier narrowed the blast radius: server-side the row is never invalidated, but shipped clients rotate the key after any non-CONFLICT error ([practice-session-page-logic.ts:285](<../../app/(app)/app/practice/[sessionId]/practice-session-page-logic.ts#L285>)) or regenerate `useRef` keys on reload, so user-facing impact per incident is typically one visible INTERNAL_ERROR followed by recovery (for finalize, re-execution into CONFLICT and the summary-fetch fallback) — hence P3, not P2. The gap is invisible to the test suite because write and replay always run the same schema version. [BUG-218](../_archive/bugs/bug-218-idempotency-parse-error-loses-cause.md) touched this exact throw site but only added `{ cause }` for diagnosability, explicitly leaving schema drift unresolved.

### 2. Idempotency error cache is a lossy encoding: `fieldErrors` never persisted, read path drops unrecognized `details` keys

`ApplicationError` carries four payload channels ([`fieldErrors` at application-errors.ts:82](../../src/application/errors/application-errors.ts#L82)), but the cache persists only three: [`toErrorRecord`](../../src/adapters/shared/with-idempotency.ts#L39) and the [`IdempotencyKeyError` port type](../../src/application/ports/idempotency-key-repository.ts#L8) omit `fieldErrors`, and the [replay path](../../src/adapters/shared/with-idempotency.ts#L308) reconstructs the error with `fieldErrors` undefined. Additionally, [`DrizzleIdempotencyKeyRepository.toApplicationErrorDetails`](../../src/adapters/repositories/drizzle-idempotency-key-repository.ts#L17) discards every persisted `details` key except a recognized `ApplicationConflictReason`, so any future `ApplicationErrorDetails` enrichment silently round-trips to nothing.

Blast radius today is narrow, and the verifier refuted the obvious scenario: user-form VALIDATION `fieldErrors` are produced by [`createAction`'s `safeParse`](../../src/adapters/controllers/create-action.ts#L45) BEFORE `executeIdempotent`, so they are never cached, and no UI currently consumes `ActionResult.error.fieldErrors`. The only in-execute producer is [`CorruptPracticeSessionRowError`](../../src/adapters/repositories/drizzle-practice-session-repository.ts#L40)'s INTERNAL_ERROR diagnostics for corrupt `params_json` rows (the DEBT-428 anomaly class): the first request's `ActionResult` includes them via [`handleError`](../../src/adapters/controllers/action-result.ts#L52), but a same-key retry replays with `fieldErrors` gone — degraded diagnostics only. The latent cost: any future fieldErrors-bearing error thrown inside an idempotent execute, or any new `ApplicationErrorDetails` key, makes replays silently diverge from first-execution responses with no test or type error flagging it. The [DEBT-435](../_archive/debt/debt-435-practice-session-conflict-and-test-hygiene-follow-ups.md) resolution deliberately made `details` persist/replay but left `fieldErrors` out with no recorded ruling — the narrowing is an undocumented implicit decision. P4.

### 3. Lifecycle idempotency cache branch is production-dead: end-path already-ended CONFLICTs are reasonless while fakes and policy tests fabricate reason-bearing errors

[`shouldCachePracticeSessionLifecycleError`](../../src/adapters/controllers/shared/practice-session-idempotency-policy.ts#L20) — the BUG-278 fix wired to `practice:endPracticeSession` and `practice:discardPracticeSession` ([practice-controller.ts:279](../../src/adapters/controllers/practice-controller.ts#L279), [:317](../../src/adapters/controllers/practice-controller.ts#L317)) — caches only CONFLICTs carrying `details.reason` `AlreadyEnded`/`ExamTimeExpired`. But no production emitter on either action ever attaches a reason: [`EndPracticeSessionUseCase` throws bare CONFLICT](../../src/application/use-cases/end-practice-session.ts#L29), [`DrizzlePracticeSessionRepository.end()` throws bare CONFLICT at line 576](../../src/adapters/repositories/drizzle-practice-session-repository.ts#L576) and [599-602](../../src/adapters/repositories/drizzle-practice-session-repository.ts#L599), and [`DiscardPracticeSessionUseCase`](../../src/application/use-cases/discard-practice-session.ts#L34) throws no CONFLICT at all. The cache-true branch never fires in production; BUG-278's documented "terminal conflicts replay with structured reasons" semantics are certified only by tests fabricating `practiceSessionAlreadyEndedError()` at the use-case seam ([practice-controller-session-lifecycle-idempotency-policy.test.ts:73](../../src/adapters/controllers/practice-controller-session-lifecycle-idempotency-policy.test.ts#L73), [with-idempotency-practice-session-conflicts.test.ts:138](../../src/adapters/shared/with-idempotency-practice-session-conflicts.test.ts#L138)), and [`FakePracticeSessionRepository.end()`](../../src/application/test-helpers/fakes/fake-practice-session-repository.ts#L372)/[`getActiveSession()`](../../src/application/test-helpers/fakes/fake-practice-session-repository.ts#L103) over-promise a reason the real end path never emits — an LSP break in the test double's error contract. [BUG-282](../_archive/bugs/bug-282-tutor-two-tab-ended-session-dead-end-loop.md) annotated only the submit/load paths and left the end path bare.

No wrong observable behavior today: a duplicate end gets a bare CONFLICT, the policy declines to cache, the claim aborts, and each retry re-executes to the same monotone CONFLICT; the client end flow recovers ANY end CONFLICT via catch-all summary fetch. The verifier confirmed `ExamTimeExpired` cannot make the branch live on these actions (exam mode is rejected with VALIDATION_ERROR before `end()`, and discard emits no CONFLICT). The trap is latent: any future client or policy change branching on `details.reason === AlreadyEnded` for the end/discard surface will pass all fake-backed unit tests and silently take the generic path in production. P4.

## Impact

- **Part 1 (P3, drives the doc priority):** every output-shape change to an idempotent action across a deploy turns straddling-key replays into INTERNAL_ERROR for up to 24h per key. Today's shipped clients contain it to one visible error per incident via key rotation; a future client that legitimately reuses a key (the concurrent-request branch already does) would fail repeatedly until TTL expiry. Zero test coverage of the cross-version replay path.
- **Part 2 (P4):** degraded replay diagnostics for corrupt-row INTERNAL_ERRORs today; silent replay-vs-first-execution divergence for any future fieldErrors/details consumer, with the port type structurally unable to express the loss.
- **Part 3 (P4):** dead policy code certified by fabricated fixtures — every "terminal" end conflict is re-executed, not replayed — plus a fake-contract trap for the natural next step of the DEBT-426/BUG-282 reason contract.

## Proposed Resolution

**Part 1:**
- **Option 1 (RECOMMENDED):** on replay parse failure in `withIdempotency`, best-effort delete the poisoned row (new repo method keyed on userId/action/key + `completedAt` to avoid racing an in-flight claim) before throwing, so the NEXT retry with the same key re-executes instead of failing for the remaining TTL; keep the INTERNAL_ERROR + `cause` for the current request. Small; contains blast radius to exactly one error per straddling key.
- **Option 2:** stamp each stored result with a version discriminator (per-action schema version constant, or the app build/commit id) at `storeResult` and treat a version mismatch on replay as a cache-miss that re-claims and re-executes — the full evolution story, more plumbing.
- **Option 3 (NOT recommended):** relax replay-only validation (non-strict parse or raw-`resultJson` fallback) — silently returns stale-shaped payloads to new callers, trading a loud narrow failure for a quiet type lie.

**Part 2:**
- **Option 1 (recommended, smallest honest fix):** make the narrowing explicit — comment on `toErrorRecord` and `IdempotencyKeyError` that `fieldErrors` is intentionally not persisted (form-validation fieldErrors never reach the cache; in-execute fieldErrors are diagnostic-only), plus a pinning unit test in `with-idempotency.test.ts` asserting the replayed error has `fieldErrors` undefined.
- **Option 2:** full-fidelity encoding symmetrical with the DEBT-435 details work — add `fieldErrors` to `IdempotencyKeyError`, persist in `toErrorRecord`, thread through `storeError`/`find` in the Drizzle repo and `FakeIdempotencyKeyRepository`, reconstruct in the replay throw. Modest, but schema/serialization weight for a channel with zero current consumers.
- **Option 3 (read-side only):** relax `toApplicationErrorDetails` to pass through unknown-but-JSON-safe details keys instead of dropping everything except a recognized `reason`; keep the strict reason type-guard at the consumer that branches on it.

**Part 3:**
- **Option 1 (recommended):** annotate the end-path already-ended conflicts with `practiceSessionAlreadyEndedError()` at both real emitters (`end-practice-session.ts:29`; `drizzle-practice-session-repository.ts:576`, `599-602`), completing the BUG-282 treatment — makes the fake's contract truthful, makes the BUG-278 cache branch live, and is behavior-compatible because the client already recovers any end CONFLICT to the summary.
- **Option 2 (if reasonless-by-design is preferred):** align `FakePracticeSessionRepository.end()` to throw the bare CONFLICT the real path emits, rewrite the lifecycle-policy/cache-replay tests to use production-shaped conflicts, and document in the policy that the cache branch is reserved for a future reason-wired end path.
- **Option 3 (either way):** add a fake-vs-real contract test pinning that both repositories' `end()` throw the same error shape (code AND `details.reason`) for an already-ended session.

## Verification

- **Part 1:** a `with-idempotency.test.ts` case where `parseResult` throws on a completed row proves (Option 1) the row is deleted and a subsequent same-key call re-executes, or (Option 2) a version-mismatched row is treated as a cache miss; current behavior (row persists, every retry fails) is the red baseline.
- **Part 2:** the pinning test asserting replayed-error `fieldErrors === undefined` (Option 1), or round-trip tests through Drizzle + fake repos proving `fieldErrors`/unknown-details persistence (Options 2/3); a comment on `toErrorRecord`/`IdempotencyKeyError` recording the ruling.
- **Part 3:** an integration or contract test where a real (or production-shaped) already-ended `end()` conflict flows through `shouldCachePracticeSessionLifecycleError` and is cached-and-replayed (Option 1) — or the rewritten tests proving the branch is declined for production-shaped bare CONFLICTs (Option 2); either way the fabricated-fixture certification gap is closed.
