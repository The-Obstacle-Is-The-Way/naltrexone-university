The 24-hour TTL makes permanent cached-result version infrastructure disproportionate, but it does not justify deleting or re-executing a completed outcome. Compatibility is therefore a release-time obligation, while public-error parity is a current correctness and information-boundary fix. No part changes the cluster cleanup ruling: expired idempotency rows remain owned by the existing request-path pruner, simplified under DEBT-444.

## Description

The idempotency cache (`idempotency_keys` + `withIdempotency`) treats stored outcomes as durable data but has no evolution story for them: replayed results are validated against whatever schema the *current* deploy ships, cached errors can lose structured fields or replay a different public error than the first request, and one of the cache's dedicated policy branches is exercised only by fabricated test fixtures. Three constituent findings, independently re-verified against current source and tests on 2026-07-10.

### 1. Replay validates cached `result_json` against the CURRENT `.strict()` schema — no version stamp, no invalidation

[`executeIdempotent`](../../src/adapters/controllers/shared/execute-idempotent.ts#L56) unconditionally passes `parseResult: (value) => outputSchema.parse(value)` into `withIdempotency`. There are 11 production `executeIdempotent` call sites across the practice, billing, bookmark, feedback, and question controllers, and all 11 output schemas are strict objects (for example, [`FinalizeExamAnswersOutputSchema`](../../src/adapters/controllers/practice-schemas.ts#L173) and [`CreatePortalSessionOutputSchema`](../../src/adapters/controllers/billing-controller.ts#L49)). On replay of a completed row ([`with-idempotency.ts:319-333`](../../src/adapters/shared/with-idempotency.ts#L319)), the pre-deploy `result_json` is parsed with the post-deploy schema. An incompatible change such as adding a required field or removing a field fails in opposite directions (missing key vs. `.strict()` unknown key); compatible changes such as adding an optional/defaulted field need not fail. The parse-failure catch throws `ApplicationError('INTERNAL_ERROR', 'Cached idempotency result is invalid')` without deleting or aborting the row, and [`idempotency_keys`](../../db/schema.ts#L291) has no schema-version column, so the completed row remains unreadable through the current parser until `expiresAt` ([24h default TTL](../../src/adapters/shared/with-idempotency.ts#L16)).

Failure scenario: a deploy makes an incompatible change to an idempotent action's output shape; request 1 completes pre-deploy and stores `result_json` under the old shape; a duplicate/retry with the same key arrives post-deploy within the TTL — e.g. an exam-finalize retry after the "concurrent request still processing" branch (which deliberately does NOT rotate the key, [practice-session-page-logic.ts:279-285](<../../app/(app)/app/practice/[sessionId]/practice-session-page-logic.ts#L279>) as of PR #640; previously :277-283), or a second submission of a billing form rendered pre-deploy. The replay parses the old payload with the new schema, parse throws, and the user gets `INTERNAL_ERROR`. Server-side the row is not invalidated; shipped practice clients rotate the key after a non-`CONFLICT` error ([practice-session-page-logic.ts:287](<../../app/(app)/app/practice/[sessionId]/practice-session-page-logic.ts#L287>) as of PR #640; previously :285), while form-backed billing surfaces navigate or can be reloaded to render a fresh hidden key. The usual honest-client recovery therefore requires a new key and may re-execute an operation whose first outcome already committed. Existing tests do cover the loud parse-failure behavior with deliberately invalid cached payloads ([`with-idempotency.test.ts:619-666`](../../src/adapters/shared/with-idempotency.test.ts#L619), [`execute-idempotent.test.ts:193-230`](../../src/adapters/controllers/shared/execute-idempotent.test.ts#L193)); what is missing is a deploy-evolution contract that can decode a previous valid shape without converting a committed outcome into a fresh execution. [BUG-218](../_archive/bugs/bug-218-idempotency-parse-error-loses-cause.md) touched this exact throw site but only added `{ cause }` for diagnosability, explicitly leaving schema drift unresolved.

### 2. Cached error records lose structured fields and can expose raw execute-error messages on replay

`ApplicationError` exposes `code`, `message`, `fieldErrors`, and `details` to `ActionResult` callers ([`fieldErrors` at application-errors.ts:82](../../src/application/errors/application-errors.ts#L82)), but the cache persists only the first, second, and fourth: [`toErrorRecord`](../../src/adapters/shared/with-idempotency.ts#L39) and the [`IdempotencyKeyError` port type](../../src/application/ports/idempotency-key-repository.ts#L8) omit `fieldErrors`, and the [replay path](../../src/adapters/shared/with-idempotency.ts#L308) reconstructs the error with `fieldErrors` undefined. [`DrizzleIdempotencyKeyRepository.toApplicationErrorDetails`](../../src/adapters/repositories/drizzle-idempotency-key-repository.ts#L17) also returns only a recognized `ApplicationConflictReason`, discarding every other persisted key. `ApplicationErrorDetails` currently defines only `reason`, so today's recognized values survive; a future typed enrichment would be written by `storeError` but silently dropped on Drizzle read unless this decoder changed with it.

Non-`ApplicationError` failures that an action's policy elects to cache have the opposite problem: [`toErrorRecord`](../../src/adapters/shared/with-idempotency.ts#L39) stores `INTERNAL_ERROR` with the original error's truncated message. The first request rethrows the original, so [`handleError`](../../src/adapters/controllers/action-result.ts#L45) returns `VALIDATION_ERROR` plus flattened fields for a `ZodError`, or the generic `INTERNAL_ERROR` / `Internal error` response for any other unknown error. A replay instead constructs an `ApplicationError` from the cached record ([`with-idempotency.ts:308-316`](../../src/adapters/shared/with-idempotency.ts#L308)), and `handleError` forwards the stored message as public text. The existing wrapper test pins this raw-message replay (`unexpected failure`) at [`with-idempotency.test.ts:668-693`](../../src/adapters/shared/with-idempotency.test.ts#L668); it does not compare the first and replayed controller responses.

Input validation itself is outside the cache because [`createAction`'s `safeParse`](../../src/adapters/controllers/create-action.ts#L45) runs before `executeIdempotent`, and no UI currently reads `ActionResult.error.fieldErrors`. But two keyed actions parse fresh use-case output *inside* `execute`: portal creation ([`billing-controller.ts:160-172`](../../src/adapters/controllers/billing-controller.ts#L160)) and exam finalization ([`practice-controller.ts:335-342`](../../src/adapters/controllers/practice-controller.ts#L335)). An invalid output is therefore `VALIDATION_ERROR` with fields on the first response but cached as `INTERNAL_ERROR` with Zod's raw message for replay. Existing tests cover invalid fresh output only without an idempotency key ([`billing-controller.test.ts:404-424`](../../src/adapters/controllers/billing-controller.test.ts#L404), [`practice-controller-session-lifecycle.test.ts:733-759`](../../src/adapters/controllers/practice-controller-session-lifecycle.test.ts#L733)). Separately, [`CorruptPracticeSessionRowError`](../../src/adapters/repositories/drizzle-practice-session-repository.ts#L38)'s `fieldErrors` survive the first `ActionResult` but disappear on replay. The fake also diverges from the real adapter: [`FakeIdempotencyKeyRepository.find()`](../../src/application/test-helpers/fakes/fake-idempotency-key-repository.ts#L64) returns stored `details` verbatim, while the Drizzle repository validates/narrows them. The [DEBT-435](../_archive/debt/debt-435-practice-session-conflict-and-test-hygiene-follow-ups.md) resolution added `details` persistence/replay but recorded no ruling for these other channels. P3: a same-key replay can change the public code/shape and expose raw internal error text that the first response deliberately hid.

### 3. Lifecycle idempotency cache branch is production-dead: end-path already-ended CONFLICTs are reasonless while fakes and policy tests fabricate reason-bearing errors

[`shouldCachePracticeSessionLifecycleError`](../../src/adapters/controllers/shared/practice-session-idempotency-policy.ts#L20) — the BUG-278 fix wired to `practice:endPracticeSession` and `practice:discardPracticeSession` ([practice-controller.ts:279](../../src/adapters/controllers/practice-controller.ts#L279), [:317](../../src/adapters/controllers/practice-controller.ts#L317)) — caches only CONFLICTs carrying `details.reason` `AlreadyEnded`/`ExamTimeExpired`. But no production emitter on either action ever attaches a reason: [`EndPracticeSessionUseCase` throws bare CONFLICT](../../src/application/use-cases/end-practice-session.ts#L29), [`DrizzlePracticeSessionRepository.end()` throws bare CONFLICT at line 576](../../src/adapters/repositories/drizzle-practice-session-repository.ts#L576) and [599-602](../../src/adapters/repositories/drizzle-practice-session-repository.ts#L599), and `DiscardPracticeSessionUseCase` throws no reason-bearing terminal CONFLICT (since [BUG-292's fix, PR #627](../_archive/bugs/bug-292-discard-unowned-serialization-failure-internal-error.md), it can surface a typed `StateChangedConcurrently` CONFLICT on retry exhaustion — a reason this lifecycle policy correctly declines to cache, so the conclusion is unchanged). The cache-true branch never fires in production; BUG-278's documented "terminal conflicts replay with structured reasons" semantics are certified only by tests fabricating `practiceSessionAlreadyEndedError()` at the use-case seam ([practice-controller-session-lifecycle-idempotency-policy.test.ts:73](../../src/adapters/controllers/practice-controller-session-lifecycle-idempotency-policy.test.ts#L73), [with-idempotency-practice-session-conflicts.test.ts:138](../../src/adapters/shared/with-idempotency-practice-session-conflicts.test.ts#L138)), and [`FakePracticeSessionRepository.end()`](../../src/application/test-helpers/fakes/fake-practice-session-repository.ts#L372) over-promises a reason the real repository's `end()` never emits — an LSP break in the test double's error contract. [BUG-282](../_archive/bugs/bug-282-tutor-two-tab-ended-session-dead-end-loop.md) annotated only the submit/load paths and left the end path bare.

No wrong observable behavior today: an end request made with a fresh key after the session has already ended gets a bare `CONFLICT`; the policy declines to cache it, aborts the claim, and a same-key retry re-executes to the same monotone conflict. (A retry of the key that originally ended the session replays its cached success.) The client end flow recovers any end `CONFLICT` via catch-all summary fetch. The verifier confirmed `ExamTimeExpired` cannot make the branch live on these actions (exam mode is rejected with `VALIDATION_ERROR` before `end()`, and discard emits no `CONFLICT`). The trap is latent: any future client or policy change branching on `details.reason === AlreadyEnded` for the end/discard surface can pass the reason-bearing policy/controller tests and silently take the generic path in production. P4.

## Impact

- **Part 1 (P3, drives the doc priority):** an incompatible output-schema change across a deploy turns a straddling-key replay into `INTERNAL_ERROR` for the row's remaining TTL. Honest clients can obtain a fresh key, but that recovery can re-execute an operation whose completed cache record says the first outcome committed. Tests pin the fail-loud parser branch but provide no previous-version decode/upcast contract.
- **Part 2 (P3):** first and replayed controller responses can disagree today: keyed output-validation failures change from structured `VALIDATION_ERROR` to cached `INTERNAL_ERROR`, corrupt-row fields disappear, and cached unknown execute failures replay their raw message instead of the first response's generic text. The port cannot express `fieldErrors`, and the fake over-promises arbitrary typed `details` round trips.
- **Part 3 (P4):** dead policy code certified by fabricated fixtures — every "terminal" end conflict is re-executed, not replayed — plus a fake-contract trap for the natural next step of the DEBT-426/BUG-282 reason contract.

## Proposed Resolution

**Part 1:**
- **Option 1 (REJECTED BY DIRECTION REVIEW):** define a per-action, versioned cached-result envelope and version-specific decoders/upcasters. Treat existing unversioned rows as the baseline version; decode the stored version and map it to the current output contract before returning it. Unknown/invalid versions stay fail-loud with the completed row intact. This is valid for a long-lived ledger, but permanent envelope/version/upcaster machinery is disproportionate for this 24-hour cache.
- **Option 2 (CHOSEN, minimal form):** for each incompatible output change, ship a replay parser that accepts and maps the previous valid shape, with a fixture produced by the pre-deploy schema. Retain it until at least 24 hours after the last old-version writer is no longer serving traffic. This is a binding release rule, not optional cleanup. It avoids persistence changes and handles only the explicitly supported prior shape.
- **Rejected:** deleting the completed row, treating a version mismatch as a cache miss, or falling back to raw/unvalidated JSON. The first two can re-execute a committed effect; the last returns a payload that violates the current controller contract.

**Part 2:**
- **Option 1 (REJECTED BY DIRECTION REVIEW):** define a versioned public-error envelope with legacy upcasters. The validation and normalization seam is sound, but permanent version machinery repeats Part 1's disproportionate cache infrastructure.
- **Option 2 (CHOSEN, minimal form):** define one unversioned, validated durable public-error codec and use it for both first-response mapping and cache serialization. Preserve `code`, safe public `message`, `fieldErrors`, and allowlisted `details`; normalize `ZodError` to `VALIDATION_ERROR` / `Invalid input` / flattened fields and every other unknown error to `INTERNAL_ERROR` / `Internal error`, retaining raw diagnostics only in logs or causes. Extend the port/stored record only as needed to preserve those current safe fields, and make the fake apply the same details decoder as Drizzle. Existing rows without newly preserved optional fields remain valid for their remaining TTL; no legacy-version framework is required.
- **Rejected:** passing arbitrary JSONB keys through as `ApplicationErrorDetails`. That would trade the current explicit allowlist for an unchecked type assertion at the persistence boundary.

**Part 3:**
- **Option 1 (REJECTED BY DIRECTION REVIEW):** annotate the real end-path conflicts solely to make BUG-278's cache-true branch live. No end/discard consumer needs that reason, so this adds behavior to justify dead policy rather than removing the dead policy.
- **Option 2 (CHOSEN, minimal form):** align `FakePracticeSessionRepository.end()` to the real bare `CONFLICT`, reduce the lifecycle-cache policy to explicitly decline end/discard execution errors, and rewrite the lifecycle-policy/cache tests with production-shaped conflicts. Do not retain a dormant `AlreadyEnded`/`ExamTimeExpired` branch “for later”; add it only with a real emitter and consumer.
- **Option 3 (REQUIRED VERIFICATION):** add a fake-vs-real contract test pinning that both repositories' `end()` throw the same error shape (code and absent `details.reason`) for an already-ended session.

## Verification

- **Part 1:** a pre-deploy cached fixture is replayed through the post-deploy decoder and mapped to the current output without calling `execute`; unknown/invalid versions still produce the existing `INTERNAL_ERROR` with `cause`, preserve the completed row, and never re-execute. For the compatibility-window option, pin both the previous and current strict shapes.
- **Part 2:** controller-level same-key tests prove first and replayed `ActionResult`s are identical for an `ApplicationError` with fields/details and for invalid keyed portal/finalize output. A raw execute error yields generic public text on both requests, and its cached public record contains no raw message. Drizzle/fake round trips accept and reject the same detail shapes; an existing row without newer optional fields remains replayable.
- **Part 3:** rewritten controller/policy tests prove production-shaped bare end/discard conflicts are declined and re-executed, and a fake-vs-real contract test pins code, message, and absent `details.reason`.
