# DEBT-450: Hot-Path Query Efficiency — Finalize Round-Trip Amplification, History/Bookmark Over-Hydration and Missing Bounds, Unindexed Lifetime Counts, Doubled Window-Rank Scans

**Status:** Active
**Priority:** P3
**Date:** 2026-07-09

---

## Description

Five verified query-efficiency gaps on the app's hottest authenticated paths (exam finalize, session history, bookmarks, dashboard stats, history questions tab). None produces wrong observable behavior today — every part is a counted, linear-or-worse cost that grows with session size, bookmark count, or lifetime attempt history on Neon serverless Postgres. Parts 1–3 are P3; parts 4–5 are P4.

### 1. Exam finalize issues ~5 sequential statements per question (~1,000 round trips at the 200-question cap)

[`FinalizeExamAnswersUseCase`](../../src/application/use-cases/finalize-exam-answers.ts#L212) loops over every question state and, per question, sequentially awaits `tx.attempts.insert` ([:252](../../src/application/use-cases/finalize-exam-answers.ts#L252)) then `tx.sessions.finalizeDraftAnswer` ([:263](../../src/application/use-cases/finalize-exam-answers.ts#L263)), which delegates to [`updatePracticeSessionQuestionState`](../../src/adapters/repositories/drizzle-practice-session-repository.ts#L502) — a nested [`db.transaction`](../../src/adapters/repositories/practice-session-question-state-updater.ts#L137) that Drizzle executes as SAVEPOINT + SELECT-join snapshot + version-checked UPDATE…RETURNING + RELEASE (the no-op short-circuit never fires because the updateFn always mutates state). At [`MAX_PRACTICE_SESSION_QUESTIONS = 200`](../../src/adapters/shared/validation-limits.ts#L34) that is roughly 1,000 sequential driver round trips inside one REPEATABLE READ transaction ([`lib/container/use-cases.ts:41-44`](../../lib/container/use-cases.ts#L41)), holding row locks on the session row and every already-updated state row until commit. A 40001 anywhere in the loop rolls back and re-runs the entire loop (up to 3 attempts, 25–250 ms backoff); at 3–5 ms/round-trip the request holds locks 3–6+ seconds, pressing toward the route's [`maxDuration = 30`](<../../app/(app)/app/layout.tsx#L20>) — a timeout strands the client in finalize-recovery. No data corruption in any outcome (attempts unique constraint + idempotency + AlreadyEnded mapping keep finalize safe). The 2026-06-23 audit rulings ("finalization uses set-based question fetches", "no counted N+1") predate Track A's per-question row normalization (PR #537) that created this write shape and covered read-path fetches only; archived [DEBT-441](../_archive/debt/debt-441-updater-dead-stale-retry-paths-under-rr.md) documents the nested-SAVEPOINT semantics but not the round-trip cost. The equivalent set-based write is 2–3 statements.

### 2. Session history hydrates every question-state row (up to 20,000/request) to derive counts a GROUP BY could return in ≤100 rows

[`DrizzlePracticeSessionRepository.findCompletedByUserId`](../../src/adapters/repositories/drizzle-practice-session-repository.ts#L330) loads ALL `practice_session_question_states` rows — 14 columns each, via unqualified [`db.select()`](../../src/adapters/repositories/drizzle-practice-session-repository.ts#L123) — for every session on a history page, because the port returns full domain entities. Its only list consumer, [`GetSessionHistoryUseCase`](../../src/application/use-cases/get-session-history.ts#L78), reduces those rows to `questionCount`, `questionIds[0]`, and answered/correct tallies ([`computeSessionStats`](../../src/domain/services/session-stats.ts#L15) reads just `latestSelectedChoiceId`/`latestIsCorrect`). With [`?limit=` clamped at 100](<../../app/(app)/app/history/history-search-params.ts#L47>) ([`MAX_PAGINATION_LIMIT`](../../src/adapters/shared/validation-limits.ts#L14)) and sessions capped at 200 questions, one request can transfer up to 20,000 state rows (default limit 20 ⇒ up to 4,000) inside a REPEATABLE READ transaction and immediately discard nearly all of them. The verifier confirmed the `inArray` fetch is index-supported (the session/question unique index), so this is pure transfer/hydration amplification, not scan cost. The [dashboard's limit-3 call](<../../app/(app)/app/dashboard/page.tsx#L263>) pays a smaller version on every load. Constraint: the current full hydration feeds the DEBT-433 position-drift fail-loud check and per-row corrupt-row skip logging — an aggregate projection must preserve or consciously waive that behavior.

### 3. Bookmarks read path is unbounded and over-hydrated on both its callers

[`DrizzleBookmarkRepository.listByUserId`](../../src/adapters/repositories/drizzle-bookmark-repository.ts#L53) runs `findMany` with no LIMIT, and [`GetBookmarksUseCase`](../../src/application/use-cases/get-bookmarks.ts#L34) feeds every bookmarked questionId into [`findPublishedByIds`](../../src/adapters/repositories/drizzle-question-repository.ts#L128), which hydrates each question with [`questionRelations`](../../src/adapters/repositories/drizzle-question-repository.ts#L40) — all choices (each with explanation markdown) plus tags — even though the output row projects only slug/stem/difficulty/bookmarkedAt ([get-bookmarks.ts:43](../../src/application/use-cases/get-bookmarks.ts#L43)). Two callers pay: the [bookmarks server page](<../../app/(app)/app/bookmarks/page.tsx#L249>) renders the full list with no pagination ([`maxDuration = 30`](<../../app/(app)/app/bookmarks/page.tsx#L39>) is the only backstop), and the quick-practice client effect consumes only a [`Set` of questionIds](<../../app/(app)/app/practice/practice-page-bookmarks.ts#L80>) — with a 2-retry loop on timeout, so a slow response triggers up to 3 full re-fetches. At 500 bookmarks (nothing caps `add`), each visit hydrates ~3,000+ rows and multiple MB of markdown, ~95% discarded. Verifier nuance vs. the raw candidate: on `/app/bookmarks` the heavy markdown is discarded server-side after projection, so the MBs flow Neon→function, not function→browser; the browser over-fetch (full `stemMd` per bookmark for an id Set) is on the quick-practice surface.

### 4. Dashboard lifetime stats scan the user's entire append-only attempts history with a forced join (P4)

[`GetUserStatsUseCase`](../../src/application/use-cases/get-user-stats.ts#L89) fires `countByUserId` and `countCorrectByUserId` with no time bound on every dashboard render ([`getUserStats({})`](<../../app/(app)/app/dashboard/page.tsx#L262>), uncached dynamic page). Both funnel into [`DrizzleAttemptRepository.countWhere`](../../src/adapters/repositories/drizzle-attempt-repository.ts#L327), which LEFT JOINs `practice_sessions` because [`getActiveExamVisibilityCondition()`](../../src/adapters/repositories/shared/active-exam-visibility.ts#L17) references session columns. Neither [`attempts_user_answered_at_idx` nor `attempts_user_is_correct_answered_at_idx`](../../db/schema.ts#L599) includes `practice_session_id`, so every matching attempt row needs a heap fetch — no index-only scan. Attempts are append-only in production (verified: [`deleteById`](../../src/application/ports/attempt-repository.ts#L61) has zero production callers; no pruning job), so cost grows monotonically (~18k rows/year for a 50-questions/day user) with no rollup, cache, or bounded rewrite. Verifier correction to the candidate: only the two lifetime counts are unbounded — the two 7-day counts carry a `gte(answered_at, since)` bound and are well served by the existing indexes, though they share the same join.

### 5. History questions tab materializes the latest-attempt window-rank subquery twice per request (P4)

[`listAttemptedQuestionsByUserId`](../../src/adapters/repositories/drizzle-attempt-repository.ts#L425) and [`countAttemptedQuestionsByUserId`](../../src/adapters/repositories/drizzle-attempt-repository.ts#L479) each independently materialize [`latestAttemptRowsSubquery`](../../src/adapters/repositories/drizzle-attempt-repository.ts#L59) — a [`row_number() OVER (PARTITION BY question_id ORDER BY answered_at DESC, id DESC)`](../../src/adapters/repositories/shared/latest-attempt-rank-sql.ts#L9) rank over ALL the user's visible attempts joined to `practice_sessions` — and [`GetAttemptedQuestionsUseCase`](../../src/application/use-cases/get-attempted-questions.ts#L76) runs both via `Promise.all` on every questions-tab render. No index serves the partition ordering, so each request performs two per-user history scans + window sorts before `attempt_rank = 1`, filters, and LIMIT/[OFFSET](../../src/adapters/repositories/drizzle-attempt-repository.ts#L458) apply — plus up to [`MAX_PAGINATION_OFFSET = 10,000`](../../src/adapters/shared/validation-limits.ts#L17) discarded ranked rows on deep pages. Verifier corrections: (1) the scan is per-user index-scoped via `attempts_user_answered_at_idx`, not table-wide; (2) `Promise.all` runs the queries concurrently, so wall-clock latency does not literally double — total DB work does. Archived [DEBT-214](../_archive/debt/debt-214-drizzle-query-duplication-attempt-repository.md) deduplicated the two methods' query-construction code but deliberately left the double execution intact.

## Impact

Today: no wrong behavior anywhere — all five parts are latency/compute costs. Part 1 is the sharpest: it sits on the product's single most important write (exam finalize), holds a REPEATABLE READ transaction and row locks for seconds at near-cap sizes, widens the 40001 window (a mid-loop serialization failure discards all completed work and re-runs the full loop), and at the extreme risks the 30 s route timeout → finalize-recovery. Parts 2–3 are linear read amplification on history/dashboard/bookmarks/quick-practice — Neon compute/IO and serverless time scale with total questions or bookmarks per page instead of rows rendered, with the bookmarks list additionally unbounded. Parts 4–5 are monotonically growing per-render costs on the dashboard and history questions tab, invisible until a heavy long-lived user notices pages slowing month over month. Severity: parts 1–3 P3 (real, counted, but user-visible harm needs stacked preconditions — near-cap sessions, heavy bookmarkers, elevated per-statement latency); parts 4–5 P4 (bounded in practice by finite question-bank / realistic attempt cardinality).

## Proposed Resolution

**Part 1** — Option 1 (recommended): convert finalize's write phase to set-based statements — grade in memory (reads are already set-based via `fetchSessionOwnedQuestionsById`), then one multi-row INSERT into `attempts` and one `UPDATE practice_session_question_states … FROM (VALUES …)` carrying per-row version predicates and the `ended_at IS NULL` guard, keeping the BUG-254 single-question flush and `tx.sessions.end` unchanged (~5N statements → ~3–4 total). Option 2 (smaller): a tx-bound fast path or bulk `finalizeDraftAnswers` port method that skips the nested SAVEPOINT wrapper and per-question SELECT when already inside the composition-root RR transaction (DEBT-441 established the inner retry/stale machinery is dead code there) — roughly halves statements. Option 3 (measure-first, per the DEBT-349 precedent): instrument finalize duration and act only if production p95 shows material latency — noting the statement count is already counted, not speculative.

**Part 2** — Option A (recommended): a summary-projection port method, e.g. `findCompletedSummariesByUserId(userId, limit, offset, mode)`, implemented as one SQL query joining `practice_sessions` to a `GROUP BY practice_session_id` aggregate (COUNT(*), COUNT(latest_selected_choice_id), COUNT(*) FILTER (WHERE latest_is_correct), MIN(question_id) at position 0) — ≤100 rows, drops entity hydration, update `FakePracticeSessionRepository` in lockstep. Option B (smaller): narrow `loadQuestionStateRowsBySessionIds` for the list path to five columns — roughly halves transfer without a port change. Option C (defer): document as accepted cost until history-page latency is observed. Option A must preserve or explicitly waive the DEBT-433 position-drift fail-loud check that rides on full hydration.

**Part 3** — Option A (recommended): a narrow read model — `BookmarkRepository.listRowsByUserId(userId, { limit, offset })` or a joined query selecting only `bookmarks.createdAt` + `questions.id/slug/stem_md/difficulty` where `status='published'`, plus page-level pagination mirroring the history-tab pattern (BUG-162/DEBT-206 precedent) — fixes row count and column width in one seam. Option B (minimal, no UI change): a lean `QuestionRepository.findPublishedSummariesByIds` without `with:` relations, accepting the unpaginated list as bounded by bank size. Option C (companion): `listBookmarkedQuestionIds(userId)` returning ids only, so `createBookmarksEffect` stops shipping every stem's markdown to the client and re-fetching it on retries.

**Part 4** — Option 1 (recommended): rewrite `countWhere`'s visibility check as an anti-join (`practice_session_id IS NULL OR practice_session_id NOT IN (SELECT id FROM practice_sessions WHERE user_id = $1 AND mode = 'exam' AND ended_at IS NULL)`) so the tiny subquery runs once; pair with a covering index (e.g. `INCLUDE (practice_session_id, is_correct)`) so the counts become index-only scans — semantics-preserving, applies to all `countWhere` callers. Option 2: per-user stats rollup (counter table / materialized view) — overkill at current scale. Option 3: short-TTL cache of GetUserStats output — hides the cost, least preferred.

**Part 5** — Option A (recommended): merge count into the list query with `count(*) OVER ()` on the already-filtered ranked rows, eliminating the second subquery materialization — one scan per request, low-risk given DEBT-214's shared `buildAttemptedQuestionsConditions` helper. Option B: composite index `(user_id, question_id, answered_at DESC, id DESC)` or a `DISTINCT ON (question_id)` rewrite so the rank/dedup is index-served. Option C: accept and monitor — per-user attempt cardinality on a finite board-prep bank is realistically low thousands, where a window sort is single-digit milliseconds.

## Verification

- **Part 1:** an integration test asserting finalize of an N-question exam executes a bounded statement count (statement-counting driver wrapper or `pg_stat_statements` delta), plus existing finalize behavior suites staying green (omitted-answer outcomes, BUG-254 flush, AlreadyEnded mapping, idempotent replay).
- **Part 2:** unit tests pinning the summary projection's answered/correct/questionCount/first-question values against the fake; an integration test proving a limit-100 history request issues the aggregate (not per-state hydration) and that corrupt/position-drift rows still fail loud or are skipped-and-logged per the chosen DEBT-433 posture.
- **Part 3:** tests pinning the bookmarks page query selects no choice/tag relations and respects a limit; a quick-practice test pinning the ids-only payload shape; pagination UI covered per the history-tab precedent.
- **Part 4:** `EXPLAIN` evidence (or integration assertion) that lifetime counts use an index-only scan with no per-row `practice_sessions` join; count parity tests across the anti-join rewrite including the active-exam-hidden case.
- **Part 5:** a repository test proving one request materializes the window subquery once (merged count column returns the same total as the old count method across filters/offsets).
