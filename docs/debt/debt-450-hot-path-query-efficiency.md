# DEBT-450: Hot-Path Query Efficiency — Finalize Statement Amplification, History/Bookmark Over-Hydration, Lifetime Counts, and Duplicate Window Ranking

**Status:** Active
**Priority:** P3
**Date:** 2026-07-09

---

## Description

Five source-verifiable query-efficiency gaps exist on authenticated exam-finalize, history, bookmark, and dashboard paths. The repository proves statement/row cardinalities and query shapes; it does not contain production query plans, byte counts, p95 latency, or Neon compute measurements. Parts 1–3 remain P3 because their amplification can reach the app's explicit request/session bounds or lacks request pagination. Parts 4–5 remain P4 because their work grows with one user's surviving attempt history but no current latency failure is demonstrated.

### 1. Exam finalize executes up to `4F` sequential loop statements (`800` when all 200 questions need finalization)

Let `F` be the number of session states that still need an attempt and state finalization. [`FinalizeExamAnswersUseCase`](../../src/application/use-cases/finalize-exam-answers.ts#L212) processes those states sequentially; a state with no draft and an already-finalized `latestSelectedChoiceId` skips at [lines 219–220](../../src/application/use-cases/finalize-exam-answers.ts#L219). Each of the remaining states awaits two repository calls:

1. `tx.attempts.insert` ([lines 223–241 and 252–270](../../src/application/use-cases/finalize-exam-answers.ts#L223)) emits one `INSERT … RETURNING` statement ([`drizzle-attempt-repository.ts:170-188`](../../src/adapters/repositories/drizzle-attempt-repository.ts#L170)).
2. `tx.sessions.finalizeDraftAnswer` delegates to [`updatePracticeSessionQuestionState`](../../src/adapters/repositories/drizzle-practice-session-repository.ts#L494). Because the repository is bound to the outer transaction, Drizzle 0.45.2 implements its nested `transaction()` with postgres.js `savepoint()` ([Drizzle's installed-version source](https://github.com/drizzle-team/drizzle-orm/blob/0.45.2/drizzle-orm/src/postgres-js/session.ts#L203-L215)). The updater then performs one snapshot `SELECT` and one version-checked `UPDATE … RETURNING` ([`practice-session-question-state-updater.ts:137-177`](../../src/adapters/repositories/practice-session-question-state-updater.ts#L137)). postgres.js 3.4.9 emits the opening `SAVEPOINT` but, on success, does not emit `RELEASE SAVEPOINT`; only the outer scope commits ([postgres.js v3.4.9 source](https://github.com/porsager/postgres/blob/v3.4.9/src/index.js#L251-L289); exact Drizzle and postgres.js versions are pinned at [`pnpm-lock.yaml:3531`](../../pnpm-lock.yaml#L3531) and [`pnpm-lock.yaml:4821`](../../pnpm-lock.yaml#L4821)). This leg is therefore three successful statements, not four.

The successful loop cost is consequently `F × (1 INSERT + 1 SAVEPOINT + 1 SELECT + 1 UPDATE) = 4F` sequential driver statements. With [`MAX_PRACTICE_SESSION_QUESTIONS = 200`](../../src/adapters/shared/validation-limits.ts#L34), `F ≤ 200`, so the loop maximum is `800`, not the previously claimed `~1,000`. That count excludes fixed transaction/session reads, the set-based drafted-question fetch at [lines 204–210](../../src/application/use-cases/finalize-exam-answers.ts#L204), `sessions.end`, `BEGIN`/isolation/`COMMIT`, and the optional single-question BUG-254 flush. An error can add rollback statements. A retryable `40001` or `40P01` restarts the whole outer REPEATABLE READ transaction up to three attempts with 25–250 ms capped jitter ([`lib/container/use-cases.ts:41-108`](../../lib/container/use-cases.ts#L41)), so completed loop work in the failed attempt is discarded and repeated.

The row locks acquired by repeated state updates and the uncommitted attempt inserts remain until the outer transaction completes, widening the conflict window as `F` grows. The app segment has [`maxDuration = 30`](<../../app/(app)/app/layout.tsx#L20>), but the repository contains no production per-statement latency or finalize-duration distribution; it cannot establish the prior “3–6+ seconds” estimate or that cap proximity occurs in production. The direction and `4F` count are source facts. Archived [DEBT-441](../_archive/debt/debt-441-updater-dead-stale-retry-paths-under-rr.md) documents why the inner stale retry is dead in this transaction context, not this statement cost. The 2026-06-23 “no counted N+1” audit concerned set-based question reads and predates PR #537's normalized per-question write shape.

### 2. A history page can hydrate 20,000 fourteen-column state rows to return at most 100 summaries

[`findCompletedByUserId`](../../src/adapters/repositories/drizzle-practice-session-repository.ts#L300) first fetches at most `S` session rows, then calls [`loadQuestionStateRowsBySessionIds`](../../src/adapters/repositories/drizzle-practice-session-repository.ts#L113), whose unqualified `select()` returns all 14 columns from every matching `practice_session_question_states` row. If session `i` has `Qᵢ` questions, that statement returns `ΣQᵢ` rows. The production action caps `S` at [`MAX_PAGINATION_LIMIT = 100`](../../src/adapters/controllers/practice-schemas.ts#L112), and persisted session `questionIds` cap each `Qᵢ` at [`MAX_PRACTICE_SESSION_QUESTIONS = 200`](../../src/adapters/repositories/practice-session-params.ts#L31), so the current application-contract maximum is `100 × 200 = 20,000` state rows. The default page limit is 20, hence at most 4,000 under the same contract ([`history-search-params.ts:47-50`](<../../app/(app)/app/history/history-search-params.ts#L47>)). The database has no cross-table constraint enforcing the 200 count by itself; the strict persisted-params parser and read mapper enforce the application contract.

[`GetSessionHistoryUseCase`](../../src/application/use-cases/get-session-history.ts#L48) consumes that full entity graph only to derive `questionCount`, the first question ID, and answered/correct counts; [`computeSessionStats`](../../src/domain/services/session-stats.ts#L12) reads only `latestSelectedChoiceId` and `latestIsCorrect`. The state predicate can use the unique index whose leading column is `practice_session_id` ([`db/schema.ts:509-518`](../../db/schema.ts#L509)); the actual live plan remains unverified without `EXPLAIN`. The proven issue is row/column transfer and mapping amplification, not an N+1 query.

A smaller second amplification follows: up to `S` first-question IDs go through `findPublishedByIds`, which hydrates all question choices/tags, merely to populate a slug ([`get-session-history.ts:55-68`](../../src/application/use-cases/get-session-history.ts#L55); [`drizzle-question-repository.ts:125-139`](../../src/adapters/repositories/drizzle-question-repository.ts#L125)). The dashboard's `S = 3` call pays the same shapes at lower cardinality ([`dashboard/page.tsx:260-268`](<../../app/(app)/app/dashboard/page.tsx#L260>)). Any summary projection must preserve the current list behavior around corrupt normalized state: exact count/order drift throws inside mapping and that row is then skipped and logged ([`drizzle-practice-session-repository.ts:80-110`](../../src/adapters/repositories/drizzle-practice-session-repository.ts#L80), [lines 336–355](../../src/adapters/repositories/drizzle-practice-session-repository.ts#L336)); archived [DEBT-433](../_archive/debt/debt-433-question-order-invariant-unenforced-at-db-level.md) accepted this read-time invariant.

### 3. Bookmark loading has no request pagination and hydrates relation data unused by every consumer

[`DrizzleBookmarkRepository.listByUserId`](../../src/adapters/repositories/drizzle-bookmark-repository.ts#L52) returns all `B` bookmark rows for a user with no `LIMIT`. `B` is not literally unbounded: the `(user_id, question_id)` primary key and question FK bound it by the number of extant question rows ([`db/schema.ts:648-670`](../../db/schema.ts#L648)). It is, however, unpaginated at the request boundary and can grow with the question catalog.

[`GetBookmarksUseCase`](../../src/application/use-cases/get-bookmarks.ts#L29) passes up to `B` IDs to `findPublishedByIds`. That repository selects all nine question columns plus all choice and question-tag/tag relations ([`drizzle-question-repository.ts:40-47`](../../src/adapters/repositories/drizzle-question-repository.ts#L40), [lines 125–139](../../src/adapters/repositories/drizzle-question-repository.ts#L125)); each choice includes `textMd` and `explanationMd`, and each question includes its own `explanationMd` and `referenceMd` ([`db/schema.ts:320-365`](../../db/schema.ts#L320)). The output projection retains only question ID, slug, stem, difficulty, and bookmark timestamp for available rows ([`get-bookmarks.ts:39-55`](../../src/application/use-cases/get-bookmarks.ts#L39)). Thus the server hydrates up to `B` questions and all of their `Σchoices + Σtags` relation objects while discarding every relation and five of the nine question fields. Exact bytes and discard percentage depend on content and are not derivable from source; the prior “~3,000 rows, multiple MB, ~95%” example was unsupported.

Three production consumption paths—not two—share this DTO:

- The [bookmarks server page](<../../app/(app)/app/bookmarks/page.tsx#L235>) renders all rows with no pagination. It uses stem/difficulty/date but not choice/tag relations; discarded relation data travels database→function, not function→browser.
- [`usePracticeQuestionBookmarks`](<../../app/(app)/app/practice/hooks/use-practice-question-bookmarks.ts#L46>) is reused by practice surfaces and converts the response to a `Set` of all IDs. Its timeout retry policy permits the initial request plus two retries ([`practice-page-bookmarks.ts:6-8`](<../../app/(app)/app/practice/practice-page-bookmarks.ts#L6>), [lines 60–82](<../../app/(app)/app/practice/practice-page-bookmarks.ts#L60>)), so an ID-only consumer can request the same full stem-bearing DTO up to three times.
- The standalone review-question hook calls the same action and scans the full returned array merely to test whether one question ID is present ([`use-question-page-bookmarks.ts:97-120`](<../../app/(app)/app/questions/[slug]/hooks/use-question-page-bookmarks.ts#L97>)).

The two client paths receive the projected stems/difficulty/timestamps but not the already-discarded choice/tag objects; their over-fetch is narrower than the server's relation hydration.

### 4. Dashboard lifetime counts perform two unbounded aggregates through the session-visibility join (P4)

Every dashboard request starts `getUserStats` ([`dashboard/page.tsx:260-268`](<../../app/(app)/app/dashboard/page.tsx#L260>)). [`GetUserStatsUseCase`](../../src/application/use-cases/get-user-stats.ts#L76) concurrently requests total lifetime attempts and total lifetime correct attempts alongside bounded recent metrics ([lines 81–95](../../src/application/use-cases/get-user-stats.ts#L81)). Both lifetime methods delegate to [`countWhere`](../../src/adapters/repositories/drizzle-attempt-repository.ts#L317), which has no time predicate and must `LEFT JOIN practice_sessions` because the active-exam visibility condition reads session ID/mode/end state ([`active-exam-visibility.ts:5-20`](../../src/adapters/repositories/shared/active-exam-visibility.ts#L5)). The 7-day count methods add `answered_at >= since`; they are not part of this unbounded-lifetime claim.

Let `A` be the user's stored attempt rows and `C ≤ A` the correct subset. Before the active-exam visibility predicate removes anything, the two lifetime aggregates have candidate cardinalities `A` and `C`, for total work scaling with `A + C` (worst case `2A`), not an unspecified “large scan.” A purely illustrative 50-attempt/day user creates 18,250 attempts/year, so the two predicates can consider at most 36,500 attempt candidates after one year if every attempt is correct. This is arithmetic, not a measured workload.

The three user-leading indexes are `(user_id, answered_at)`, `(user_id, question_id, answered_at)`, and `(user_id, is_correct, answered_at)`; none contains `practice_session_id` ([`db/schema.ts:599-608`](../../db/schema.ts#L599)). Therefore none covers the visibility join's required attempt columns, and an attempt-side index-only plan is not available from those indexes alone. The actual planner choice and buffer cost depend on production statistics and visibility maps and are unverifiable from git. There is no application-level attempt prune/delete caller, but attempts can still disappear through the user/question `ON DELETE CASCADE` FKs and session deletion sets `practice_session_id` null ([`db/schema.ts:571-586`](../../db/schema.ts#L571)); “append-only” and “monotonically growing” were therefore overclaims. The accurate statement is that surviving-user history has no time bound or rollup on this request path.

### 5. History questions executes the per-user latest-attempt rank twice; an existing index is a near-match, not absent (P4)

[`listAttemptedQuestionsByUserId`](../../src/adapters/repositories/drizzle-attempt-repository.ts#L419) and [`countAttemptedQuestionsByUserId`](../../src/adapters/repositories/drizzle-attempt-repository.ts#L475) each build and execute [`latestAttemptRowsSubquery`](../../src/adapters/repositories/drizzle-attempt-repository.ts#L59). That subquery left-joins sessions for visibility and computes [`row_number() OVER (PARTITION BY question_id ORDER BY answered_at DESC, id DESC)`](../../src/adapters/repositories/shared/latest-attempt-rank-sql.ts#L4) across the user's visible attempt candidates before the outer filters and page limit. [`GetAttemptedQuestionsUseCase`](../../src/application/use-cases/get-attempted-questions.ts#L65) runs the count and list statements concurrently with `Promise.all` ([lines 76–84](../../src/application/use-cases/get-attempted-questions.ts#L76)). For `Aᵥ` visible attempt candidates, the two statements each rank `Aᵥ` rows: total window input is `2Aᵥ`, although concurrency means wall-clock latency does not simply double.

The prior statement that no index serves the partition order was false. [`attempts_user_question_answered_at_idx`](../../db/schema.ts#L603) is `(user_id, question_id, answered_at DESC)`, so equality on `user_id` matches the partition key and the leading order. It lacks the final `id DESC` tie-breaker and does not include `practice_session_id`/`is_correct`, so it is not a full covering/order match; only an actual `EXPLAIN` can establish whether PostgreSQL uses it and whether an incremental/full sort remains. The list query applies `LIMIT/OFFSET` only after ranking/filtering ([`drizzle-attempt-repository.ts:454-458`](../../src/adapters/repositories/drizzle-attempt-repository.ts#L454)); the controller permits [`MAX_PAGINATION_OFFSET = 10,000`](../../src/adapters/controllers/review-controller.ts#L18), so a deep list page can additionally discard up to 10,000 filtered latest-question rows after the rank work. Archived [DEBT-214](../_archive/debt/debt-214-drizzle-query-duplication-attempt-repository.md) removed duplicated query-construction branches; its scope did not merge these two runtime statements.

## Impact

No wrong result or demonstrated production outage is attributed to these five parts. Part 1 proves up to 800 sequential success-path loop statements plus fixed transaction work and full-transaction retry, but production duration/cap proximity is unmeasured. Part 2 proves up to 20,000 fourteen-column state rows under current input/persisted-session limits, plus relation-heavy first-question reads, to emit at most 100 summaries. Part 3 proves an unpaginated `B`-row bookmark read, relation hydration proportional to all referenced choices/tags, and ID-only client consumers receiving the wider DTO; exact bytes are unmeasured. Parts 4–5 scale with `A + C` and `2Aᵥ` attempt candidates respectively; production plans and latency are unverified. Severity remains P3 overall: parts 1–3 are bounded/unpaginated hot-path amplification, while parts 4–5 are P4 scale debt without a measured user-visible trigger.

## Proposed Resolution

**Part 1** — Option 1 (recommended): replace the per-state write loop with one multi-row `INSERT … RETURNING` into `attempts` and one set-based `UPDATE practice_session_question_states … FROM (VALUES …)` carrying row IDs/versions and the `ended_at IS NULL` guard. Verify the number of returned attempts and updated state rows equals `F`; preserve the attempts unique-conflict mapping, BUG-254 final-draft flush, omitted outcomes, and `sessions.end`. This reduces the loop from `4F` statements to two, plus fixed reads/end/transaction commands. Option 2: add a transaction-bound bulk repository method that at least avoids one SAVEPOINT and snapshot `SELECT` per state while leaving standalone updater semantics intact; DEBT-441 explains why standalone READ COMMITTED callers cannot blindly share that fast path. Option 3: instrument and defer implementation until production finalize duration shows material harm, following [DEBT-349's](../_archive/debt/debt-349-cross-request-published-content-caching.md) measure-before-scale-optimization rule.

**Part 2** — Option A (recommended): add a history-specific summary read port returning at most `S` rows. Aggregate state counts and `array_agg(question_id ORDER BY position)` per session; compare that ordered array with parsed `params_json.questionIds` so DEBT-433's exact count/order invariant and skip/log behavior remain intact. Join only the position-0 published question slug, avoiding the second relation-heavy question fetch. Update `FakePracticeSessionRepository` with the same summary contract. Option B: keep the current port but select only the state columns the mapper needs; this reduces column width but still returns `ΣQᵢ` rows. Option C: accept the current shape until production history metrics establish a bottleneck.

**Part 3** — Option A (recommended): split read models by consumer. Give the bookmarks page a paginated summary query selecting only bookmark timestamp plus published question ID/slug/stem/difficulty, and give client membership checks an IDs-only endpoint (or a single-question `exists` endpoint for review). Preserve unavailable-bookmark rows and choose a stable cursor/order. Option B: first add `findPublishedSummariesByIds` without choices/tags or unused question fields, then separately paginate; this fixes width before cardinality. Option C: accept no UI pagination only if the catalog-size bound is documented, while still moving ID-only consumers off the full DTO.

**Part 4** — Option 1 (recommended): replace the four count calls with one stats-summary port query using conditional aggregates for lifetime total/correct and 7-day total/correct, so lifetime attempt candidates are processed once rather than `A + C`. Express active-exam hiding with a `NOT EXISTS`/active-session-ID predicate instead of an unconditional outer join, and evaluate whether adding `practice_session_id` as an included column to the relevant user-leading index makes the attempt scan index-only eligible; do not claim the planner will choose it without `EXPLAIN`. Option 2: retain separate ports but at least combine the two lifetime values in one aggregate. Option 3: add a per-user rollup only after write-amplification/reconciliation requirements are designed; a short-TTL cache merely hides the query cost.

**Part 5** — Option A (recommended): replace the separate list/count port calls with one statement that ranks once. A materialized ranked/filtered CTE can feed both a scalar total and a lateral paged result, returning the total even when the requested offset has no rows; a bare `count(*) OVER ()` on page rows is insufficient because an out-of-range page would lose the total. Option B: complete the near-match index as `(user_id, question_id, answered_at DESC, id DESC) INCLUDE (practice_session_id, is_correct)` and compare a `DISTINCT ON (question_id)` rewrite; preserve final sort/filter semantics. Option C: move to keyset pagination to remove deep OFFSET work, while treating total-count policy as a separate product decision.

## Verification

- **Part 1:** use an instrumented real-postgres integration client (for example, postgres.js's query debug hook) to assert `4F` current loop statements and a bounded constant after the rewrite, including transaction/savepoint commands. Existing finalize suites must retain omitted-answer grading, BUG-254 flush, conflict mapping, and full-transaction retry behavior.
- **Part 2:** unit tests pin summary answered/correct/questionCount/first-slug values and exact ordered-ID drift handling. A real-Postgres test proves one row per session rather than one row per state, including a 100-session/200-state fixture only if test runtime remains within the global policy (no per-test timeout override).
- **Part 3:** repository tests assert the summary query omits choice/tag relations and enforces page bounds; browser tests for `usePracticeQuestionBookmarks` and `useQuestionPageBookmarks` assert IDs-only/single-ID payloads and preserve retry/membership behavior.
- **Part 4:** parity tests cover standalone, tutor, ended-exam, and active-exam attempts. Capture before/after `EXPLAIN (ANALYZE, BUFFERS)` on production-like sanitized cardinalities to report actual plan/heap access; do not make a brittle CI assertion that PostgreSQL must select one plan.
- **Part 5:** a repository integration test proves one driver statement returns both total and rows for ordinary and out-of-range offsets across every filter shape. SQL/query-debug evidence must show one `row_number()` evaluation path. Compare plans before accepting the wider composite index.
