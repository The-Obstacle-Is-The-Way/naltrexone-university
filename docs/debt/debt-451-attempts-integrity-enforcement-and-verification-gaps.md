# DEBT-451: `attempts` Integrity — User-Session and Retry-Provenance Invariants Unenforced at the DB, Dual-Store Divergence Undetected, Constraint Backstop Untested Against Real Postgres

**Status:** Active
**Priority:** P4
**Date:** 2026-07-09

---

## Description

The DEBT-440 arc DB-promoted the choice↔question linkage invariant on `attempts`, and DEBT-435 aligned fake/real CONFLICT contracts for the state-persist path. This item collects the four remaining app-only integrity seams around the `attempts` table that survived adversarial verification: two unenforced cross-table invariants (user↔session, retry provenance), one undetected dual-store value invariant (`is_correct` vs `latest_is_correct`), and one constraint mapping that no test exercises against real Postgres. All four share the DEBT-440 posture — every live code path is correct today; the exposure is direct SQL writers, repair scripts, migrations, or future writer bugs.

### 1. `attempts.is_correct` vs `latest_is_correct` divergence has no detection path

Correctness is dual-written to `attempts` and `practice_session_question_states` in one transaction ([submit-answer.ts#L222-L233](../../src/application/use-cases/submit-answer.ts#L222), [finalize-exam-answers.ts#L252-L270](../../src/application/use-cases/finalize-exam-answers.ts#L252)), but every existing integrity mechanism is structural or intra-row: the hydration guard checks row count/position only ([drizzle-practice-session-repository.ts#L81-L108](../../src/adapters/repositories/drizzle-practice-session-repository.ts#L81)), and the `latest_answer_chk` CHECK at [db/schema.ts#L542-L547](../../db/schema.ts#L542) aligns nulls within a state row. Nothing anywhere compares `latest_is_correct` against `attempts.is_correct`. Readers are split — review/summary/next-question read states ([get-practice-session-review.ts#L129](../../src/application/use-cases/get-practice-session-review.ts#L129), [session-stats.ts#L21](../../src/domain/services/session-stats.ts#L21)); dashboard/attempted-questions read attempts — and the one use case touching both, [get-completed-session-questions-with-feedback.ts#L148](../../src/application/use-cases/get-completed-session-questions-with-feedback.ts#L148) (`attempt?.isCorrect ?? state.latestIsCorrect`), prefers the attempt and falls back without logging. If the stores ever diverge (out-of-band write, manual repair, future writer bug — the DEBT-428 real dev `params_json` anomaly proves out-of-band corruption occurs on these tables), users see contradictory correctness across surfaces permanently, with zero operator signal. Not reducible to the DEBT-437 ACCEPT ruling, which settled tutor-submit-vs-end timestamp write-skew, a different invariant.

### 2. No DB enforcement that `attempts.user_id` matches `practice_sessions.user_id`

`practice_sessions` has no unique `(id, user_id)` composite-FK target ([db/schema.ts#L425-L428](../../db/schema.ts#L425)); `attempts` carries independent single-column FKs to `users` and `practice_sessions` ([db/schema.ts#L575-L586](../../db/schema.ts#L575)); and the BUG-105 partial unique index `attempts_session_question_uq` is on `(practice_session_id, question_id)` with no user column ([db/schema.ts#L629-L631](../../db/schema.ts#L629)). The only enforcement is application-level ownership verification ([submit-answer.ts#L167-L173](../../src/application/use-cases/submit-answer.ts#L167); finalize derives userId from the owner). Failure scenario: a direct writer inserts an attempt with (session S owned by user A, user_id=B). The user-agnostic UQ slot is now consumed by the foreign row; A's tutor submit maps the unique violation to CONFLICT "AlreadyAnsweredInSession" ([drizzle-attempt-repository.ts#L190-L197](../../src/adapters/repositories/drizzle-attempt-repository.ts#L190)) while A's UI shows the question unanswered. Exam finalize is worse: [finalize-exam-answers.ts#L212-L231](../../src/application/use-cases/finalize-exam-answers.ts#L212) walks the state table (still unanswered for A) and re-attempts the insert on every retry, so the session is permanently unfinalizable — and every owner-scoped read filters by user_id (index comment at [db/schema.ts#L613](../../db/schema.ts#L613)) and cannot see the blocking row, making the incident undiagnosable without manual SQL. `question_feedback` ([db/schema.ts#L672-L696](../../db/schema.ts#L672)) shares the same independent-FK shape at lower blast radius.

### 3. Retry-provenance columns have no FKs and no CHECK

[db/schema.ts#L591-L593](../../db/schema.ts#L591) declares `retry_of_attempt_id` / `retry_origin` / `retry_session_id` as bare nullable columns with only an index ([db/schema.ts#L624](../../db/schema.ts#L624)), while the same table declaration DB-enforces its other invariants (`attempts_selected_choice_or_omitted_chk`, `attempts_omitted_incorrect_chk`, and the DEBT-440 composite FK at [db/schema.ts#L632-L645](../../db/schema.ts#L632)). The cross-field invariant lives solely in [`isValidAttemptProvenance`](../../src/domain/entities/attempt.ts#L24) and is re-checked per-writer in [submit-answer.ts#L106-L165](../../src/application/use-cases/submit-answer.ts#L106) (including ownership lookups). [Migration 0013](../../db/migrations/0013_quick_xavin.sql#L2) added the columns unconstrained; none of 0021–0027 hardened them. No FK means a deleted referent leaves a permanently dangling id with no SET NULL signal, unlike the FK'd `practice_session_id`. Downstream, [validate-feedback-context.ts#L70-L71](../../src/application/use-cases/validate-feedback-context.ts#L70) branches on `attempt.retryOrigin`/`retrySessionId` to classify feedback context. Same pattern for `time_spent_seconds` ([db/schema.ts#L590](../../db/schema.ts#L590)): app-clamped to 0..86400 ([submit-answer.ts#L46](../../src/application/use-cases/submit-answer.ts#L46), [#L193-L201](../../src/application/use-cases/submit-answer.ts#L193)) but un-CHECKed, unlike the BETWEEN-checked `draft_cumulative_ms` ([db/schema.ts#L538-L541](../../db/schema.ts#L538)). Verifier corrections: migration 0018's attempt backfill omits the retry columns, producing valid NULL/NULL/NULL provenance — it illustrates the bypassing-writer class, not a violation; and the verified retry-column consumer is validate-feedback-context, not the BUG-274 modality-split readers.

### 4. Single-incomplete-session constraint backstop never exercised against real Postgres; fake does not emulate it

`DrizzlePracticeSessionRepository.create()` maps a 23505 on `practice_sessions_user_incomplete_uq` ([db/schema.ts#L445-L447](../../db/schema.ts#L445)) to the actionable CONFLICT resume-or-abandon message ([drizzle-practice-session-repository.ts#L410-L419](../../src/adapters/repositories/drizzle-practice-session-repository.ts#L410)), but that mapping is pinned only by a hand-built driver-error object in a mocked-driver unit test ([drizzle-practice-session-repository-session-writes.test.ts#L142-L149](../../src/adapters/repositories/drizzle-practice-session-repository-session-writes.test.ts#L142)). No integration test inserts two incomplete sessions for one user against real Postgres — the only real-DB practice-session CONFLICT assertion is the double-end path ([session-attempt-repository.integration.test.ts#L592-L594](../../tests/integration/session-attempt-repository.integration.test.ts#L592)) — and grep-verified, no integration test anywhere triggers a real 23505 through `postgres-errors.ts`, so the driver error-shape assumption (`constraint` vs `constraint_name`) is mock-pinned repo-wide. Meanwhile [`FakePracticeSessionRepository.create()`](../../src/application/test-helpers/fakes/fake-practice-session-repository.ts#L206) appends unconditionally, so fake-backed tests exercise only the [start-practice-session.ts#L38-L46](../../src/application/use-cases/start-practice-session.ts#L38) pre-check, never the constraint backstop — the same fake/real conflict-contract drift class DEBT-435 fixed for the state-persist path, at the `create()` seam. Two regressions would pass every tier green: a postgres-js/Drizzle upgrade changing how constraint names surface (production duplicate-start races then surface as INTERNAL_ERROR instead of CONFLICT), or a refactor removing/reordering the pre-check (fake happily creates a second incomplete session). Mitigating: `postgres-errors.ts` already handles both key spellings plus cause-nesting, and the pre-check makes the sequential path correct and unit-tested today.

## Impact

Today: none user-facing — all four parts are hygiene/defense-in-depth; every live writer is same-value, ownership-verified, provenance-validated, and pre-checked. At scale or under out-of-band writes: part 1 yields permanent, invisible cross-surface correctness contradictions; part 2's triggered outcome is P2-grade (permanently unfinalizable session, undiagnosable from app-level queries) behind a writer-bug/manual-SQL precondition; part 3 lets dangling or shape-invalid provenance silently misclassify feedback context and break retry-chain traversal; part 4 means the race backstop's real behavior is verified nowhere but production. P4 matches the direct precedent: DEBT-440 was filed P4 with the identical app-path-proof posture.

## Proposed Resolution

1. **Divergence detection** — Option A (recommended, smallest): in `GetCompletedSessionQuestionsWithFeedbackUseCase`, when both an attempt row and a graded state exist and `attempt.isCorrect !== state.latestIsCorrect`, emit a structured `logger.warn` (sessionId/questionId, both values) before preferring the attempt — the only dual-store reader becomes a free detector on a read path users actually hit. Option B: a read-only invariant query (script or admin/cron endpoint, mirroring the DEBT-442 preflight pattern) joining attempts to question states on (practice_session_id, question_id) and reporting value mismatches. Option C: document the invariant (persistence WHY header or ADR note) — cheapest but detection-free.
2. **User↔session FK** — Option 1 (recommended, DEBT-440's exact playbook): add unique `practice_sessions(id, user_id)` as a composite-FK target, replace the plain session FK on `attempts` with a composite FK `(practice_session_id, user_id)`, with a fail-loud zero-violation preflight. ON DELETE nuance: `user_id` is NOT NULL while the current session FK is ON DELETE SET NULL, so the composite FK needs PG 15+ column-list form `ON DELETE SET NULL (practice_session_id)` (Neon runs PG 15+; verify before writing the migration). Optionally extend to `question_feedback`. Option 2 (cheaper, weaker): a scheduled/preflight audit query (`attempts JOIN practice_sessions ON id WHERE attempts.user_id <> practice_sessions.user_id` must be 0), converting the undiagnosable incident into a loud one. Option 3: owner ACCEPT with documentation (DEBT-408/437 precedent) naming Option 1 as the pre-decided hardening — defensible, but DEBT-440's own resolution rejected this posture for the analogous choice/question invariant.
3. **Provenance constraints** — Option 1 (recommended): additive migration mirroring the DEBT-440 shape — self-FK `retry_of_attempt_id → attempts(id)` and FK `retry_session_id → practice_sessions(id)` (choose ON DELETE deliberately: SET NULL breaks the provenance CHECK for non-session_review rows, so RESTRICT or compound SET NULL of the whole triple), plus a CHECK encoding `isValidAttemptProvenance` — `(retry_origin IS NULL AND both ids NULL) OR (retry_origin = 'session_review' AND retry_session_id IS NOT NULL) OR (retry_origin NOT IN ('session_review') AND retry_of_attempt_id IS NOT NULL AND retry_session_id IS NULL)` — with a fail-loud zero-violation preflight per the DEBT-427 migration-authoring rules. Optionally add `time_spent_seconds BETWEEN 0 AND 86400` in the same migration. Option 2: CHECK-only, deferring FK delete-semantics. Option 3: ACCEPT with documentation, noting submit-answer is the sole writer today.
4. **Backstop empiricism** — (1) Recommended: one integration test (alongside the double-end case) calling `create()` twice for the same user without ending the first, asserting the second rejects CONFLICT with the exact resume-or-abandon message — validating the partial unique index, live postgres-js error shape, and constraint-name mapping in one cheap test. (2) Emulate the constraint in `FakePracticeSessionRepository.create()` (throw the same CONFLICT when an un-ended session exists) with a fake behavior test, per the DEBT-435 alignment precedent. (3) Optional: fold into a broader "no real 23505 exercised anywhere" coverage item covering the user/stripe unique-violation mappings.

## Verification

1. A unit test pinning the new `logger.warn` on attempt/state disagreement in `get-completed-session-questions-with-feedback.test.ts` (or the invariant query's zero-mismatch output against dev/prod, per Option B).
2. Migration preflight logs zero user↔session mismatches on dev and prod; an integration test proving an INSERT with mismatched user_id fails the composite FK; existing session-flow integration tests stay green.
3. Integration tests proving INSERTs with dangling retry ids and shape-invalid provenance triples are rejected; existing retry-submit unit/integration tests stay green; preflight logs zero violations on both environments.
4. The new integration test observing a real 23505 → CONFLICT through `postgres-errors.ts`; a `fake-practice-session-repository.test.ts` case pinning the fake's CONFLICT on duplicate incomplete create.
