## Description

The DEBT-440 arc DB-promoted the choice↔question linkage invariant on `attempts`, and DEBT-435 aligned fake/real CONFLICT contracts for the state-persist path. This item collects four remaining integrity and verification seams around the `attempts` table: two unenforced cross-table invariants (user↔session, retry provenance), one undetected dual-store value invariant (`is_correct` vs `latest_is_correct`), and one constraint mapping that no test exercises against real Postgres. Current application paths are correct, but the direction review distinguishes DEBT-440's cheap complete invariant from Parts 2/3's heavier bypass-only migrations: detect Part 1 cheaply, ACCEPT and pre-decide Parts 2/3, and align real/fake semantics in Part 4.

### 1. `attempts.is_correct` vs `latest_is_correct` divergence has no detection path

For session-backed answers, correctness is dual-written to `attempts` and `practice_session_question_states` in one transaction: tutor submit passes the same `grade.isCorrect` to both writes ([submit-answer.ts#L202-L233](../../src/application/use-cases/submit-answer.ts#L202)), and exam finalize does the same for answered and omitted states ([finalize-exam-answers.ts#L212-L270](../../src/application/use-cases/finalize-exam-answers.ts#L212)). Existing database and hydration checks are structural or intra-row: `toOrderedDomainQuestionStates` checks state-row count/order/question identity ([drizzle-practice-session-repository.ts#L81-L108](../../src/adapters/repositories/drizzle-practice-session-repository.ts#L81)), while `practice_session_question_states_latest_answer_chk` aligns selected/correct/answered nullability within one state row ([db/schema.ts#L542-L547](../../db/schema.ts#L542)). No constraint, trigger, query, or job compares a session attempt's `is_correct` with the matching state's `latest_is_correct`.

Readers are split: review/summary/next-question project state rows ([get-practice-session-review.ts#L121-L129](../../src/application/use-cases/get-practice-session-review.ts#L121), [session-stats.ts#L12-L23](../../src/domain/services/session-stats.ts#L12)), while dashboard/history statistics read attempts. The one production use case found that loads both representations, [`GetCompletedSessionQuestionsWithFeedbackUseCase`](../../src/application/use-cases/get-completed-session-questions-with-feedback.ts#L115), silently prefers `attempt.isCorrect` and falls back to `state.latestIsCorrect` only when no matching attempt exists ([lines 136-149](../../src/application/use-cases/get-completed-session-questions-with-feedback.ts#L136)). If a direct write, repair, migration, or future writer bug makes the values diverge, contradictory correctness persists across surfaces until the data is repaired, with no operator signal. DEBT-428 proves that malformed legacy Development data existed in `practice_sessions`; it does **not** establish that the row was produced by an out-of-band writer or that attempts/state rows have already diverged. This invariant is also distinct from the DEBT-437 ACCEPT ruling, which settled tutor-submit-vs-end timestamp write-skew.

### 2. No DB enforcement that `attempts.user_id` matches `practice_sessions.user_id`

`practice_sessions` has no unique `(id, user_id)` composite-FK target ([db/schema.ts#L422-L453](../../db/schema.ts#L422)); `attempts` carries independent single-column FKs to `users` and `practice_sessions` ([db/schema.ts#L571-L597](../../db/schema.ts#L571)); and the BUG-105 partial unique index `attempts_session_question_uq` is on `(practice_session_id, question_id)` with no user column ([db/schema.ts#L627-L631](../../db/schema.ts#L627)). The current application enforces ownership before writing: tutor submit loads the session by `(sessionId, userId)` ([submit-answer.ts#L167-L173](../../src/application/use-cases/submit-answer.ts#L167)), while finalize loads the owner-scoped session and uses that same input `userId` for each attempt.

Failure scenario: a direct writer inserts an attempt for question Q with session S owned by user A but `user_id=B`. The user-agnostic `(S,Q)` unique slot is consumed by B's row. A's tutor submit then maps the resulting unique violation to the typed already-answered CONFLICT ([drizzle-attempt-repository.ts#L189-L204](../../src/adapters/repositories/drizzle-attempt-repository.ts#L189)) while A's state row remains unanswered. Exam finalize also walks that unanswered state and attempts the blocked insert ([finalize-exam-answers.ts#L212-L270](../../src/application/use-cases/finalize-exam-answers.ts#L212)); the mapped typed CONFLICT is outside `runPracticeSessionStateWriteTransaction`'s `40001`/`40P01` retry set, so the invocation returns that conflict rather than rerunning the transaction, and each later finalize invocation re-encounters the foreign row until it is repaired. `AttemptRepository.findBySessionId` scopes by both session and user, so A's app-level attempt reads cannot expose B's blocking row ([drizzle-attempt-repository.ts#L245-L255](../../src/adapters/repositories/drizzle-attempt-repository.ts#L245)). `question_feedback` also stores independent user/session FKs ([db/schema.ts#L672-L696](../../db/schema.ts#L672)), but it has no analogous session-question unique slot and therefore a lower blast radius.

### 3. Retry-provenance columns have no FKs and no CHECK

[db/schema.ts#L591-L593](../../db/schema.ts#L591) declares `retry_of_attempt_id` / `retry_origin` / `retry_session_id` as nullable columns; only `retry_of_attempt_id` has an index ([db/schema.ts#L624-L626](../../db/schema.ts#L624)). There is no FK or provenance CHECK, although the same table DB-enforces selected-choice/omission shape and the DEBT-440 choice-question relationship ([db/schema.ts#L627-L645](../../db/schema.ts#L627)). The cross-field shape is checked before the only provenance-bearing writer in [`SubmitAnswerUseCase`](../../src/application/use-cases/submit-answer.ts#L102), including owner/question lookups for referenced attempts or sessions ([lines 126-165](../../src/application/use-cases/submit-answer.ts#L126)); exam finalize writes the valid all-NULL shape. Reads also fail loud on malformed triples through [`toAttemptDomain`](../../src/adapters/repositories/attempt-row-mappers.ts#L54), which calls `isValidAttemptProvenance` and maps failure to `INTERNAL_ERROR` ([lines 60-71](../../src/adapters/repositories/attempt-row-mappers.ts#L60)). Thus the invariant is app-enforced at both write and hydration boundaries, but not DB-enforced.

[Migration 0013](../../db/migrations/0013_quick_xavin.sql#L2) added the columns without constraints, and no later migration hardened them. A direct deletion can therefore leave a dangling retry attempt/session id with no FK signal. [`validateFeedbackContext`](../../src/application/use-cases/validate-feedback-context.ts#L55) consumes `retryOrigin`/`retrySessionId` when deciding whether an attempt belongs to a supplied review session ([lines 93-110](../../src/application/use-cases/validate-feedback-context.ts#L93)). `time_spent_seconds` has the same boundary split: the column is unconstrained ([db/schema.ts#L590](../../db/schema.ts#L590)), while submit clamps it to 0..86400 ([submit-answer.ts#L193-L201](../../src/application/use-cases/submit-answer.ts#L193)); `draft_cumulative_ms` is DB-checked by contrast ([db/schema.ts#L538-L541](../../db/schema.ts#L538)). Migration 0018 omits the retry columns and therefore creates the valid all-NULL shape; it is a bypassing-writer example, not a known violation.

### 4. Single-incomplete-session constraint backstop never exercised against real Postgres; fake does not emulate it

`DrizzlePracticeSessionRepository.create()` maps a 23505 on `practice_sessions_user_incomplete_uq` ([db/schema.ts#L445-L447](../../db/schema.ts#L445)) to the actionable resume-or-abandon CONFLICT ([drizzle-practice-session-repository.ts#L409-L425](../../src/adapters/repositories/drizzle-practice-session-repository.ts#L409)), but the mapping test supplies a hand-built driver-error object ([drizzle-practice-session-repository-session-writes.test.ts#L142-L149](../../src/adapters/repositories/drizzle-practice-session-repository-session-writes.test.ts#L142)). No integration test inserts two incomplete sessions for one user through the real repository; the nearby real-DB practice-session CONFLICT assertion covers double-end instead ([session-attempt-repository.integration.test.ts#L592-L594](../../tests/integration/session-attempt-repository.integration.test.ts#L592)). Repository-wide grep also found no integration test that drives a real 23505 through `postgres-errors.ts`, so live `constraint`/`constraint_name` extraction remains unit-pinned rather than empirically pinned.

[`FakePracticeSessionRepository.create()`](../../src/application/test-helpers/fakes/fake-practice-session-repository.ts#L178) appends without emulating the partial unique index ([line 206](../../src/application/test-helpers/fakes/fake-practice-session-repository.ts#L206)). Fake-backed start-session tests do correctly pin the sequential pre-check in [`StartPracticeSessionUseCase`](../../src/application/use-cases/start-practice-session.ts#L38), so deleting that pre-check would **not** pass every tier unnoticed. The uncovered seam is the race after two callers both pass the pre-check: only the real partial unique index can arbitrate it, and fake-backed tests cannot exercise its error mapping. A driver/ORM error-shape change could therefore turn that race into `INTERNAL_ERROR` while current tests stay green. Mitigating, `postgres-errors.ts` already accepts both `constraint` and `constraint_name` plus cause nesting.

## Impact

Today: no confirmed user-facing failure — all four parts are defense-in-depth, and current application writers use same-value grades, owner-scoped sessions, validated provenance, and a sequential incomplete-session pre-check. Under direct writes, repair scripts, migrations, or future writer bugs: part 1 can create persistent cross-surface correctness contradictions; part 2 can make a session unfinalizable until manual repair; part 3 can create hydration failures or incorrect feedback-context classification; part 4 leaves the duplicate-start race's real mapping unproved. P4 remains appropriate because every trigger first requires bypassing or racing a currently-correct application path, matching the resolved DEBT-440 P4 precedent.

## Proposed Resolution

1. **Divergence detection — Option A (CHOSEN, minimal form):** in `GetCompletedSessionQuestionsWithFeedbackUseCase`, when both an attempt and a graded state exist and `attempt.isCorrect !== state.latestIsCorrect`, emit a best-effort structured `logger.warn` with sessionId/questionId and both booleans before preserving the existing attempt-preferred result. **Option B's script/admin/cron scanner and Option C's detection-free documentation are REJECTED BY DIRECTION REVIEW.**
2. **User↔session FK — Option 3 (ACCEPTED):** keep current app-enforced ownership and document this concrete accepted failure: direct SQL or a future bypass writer can insert an attempt whose `user_id` differs from the session owner, consume the user-agnostic `(session, question)` slot, and leave the owner's session unfinalizable until repair. **Option 1 is the pre-decided hardening only after a mismatch or new bypass writer exists:** add the non-partial `(id, user_id)` unique target, prove `server_version_num >= 150000`, preflight zero mismatches, and replace the plain FK with `(practice_session_id, user_id)` while preserving column-list `ON DELETE SET NULL (practice_session_id)`. **Option 2's scheduled detector and shipping Option 1 now are REJECTED BY DIRECTION REVIEW as machinery for a writer that does not exist.**
3. **Provenance constraints — Option 3 (ACCEPTED):** keep validation at the sole write boundary and fail-loud hydration, and document this concrete accepted failure: direct SQL or a future bypass writer can persist an invalid/dangling provenance triple that fails hydration or misclassifies feedback context. **Option 2's CHECK is the first pre-decided hardening after an invalid row or new bypass writer exists;** FKs follow only after delete behavior and full same-user/same-question/session semantics are designed. **Option 1's immediate CHECK/FKs/preflights and a scheduled detector are REJECTED BY DIRECTION REVIEW** because simple existence FKs add machinery while still not proving the full application invariant.
4. **Backstop empiricism — Options 1 + 2 (CHOSEN, minimal form):** add one integration test calling `create()` twice for the same user without ending the first and assert the exact CONFLICT message/reason through the live postgres-js 23505 shape. Make `FakePracticeSessionRepository.create()` enforce the same one-incomplete-session rule and pin it with one fake behavior test. **Option 3's broader repository-wide 23505 campaign is REJECTED BY DIRECTION REVIEW.**

## Verification

1. A unit test pins one best-effort warning on attempt/state disagreement and the unchanged attempt-preferred output; equal values, missing attempt, and ungraded state do not warn, and logger failure cannot change the user result.
2. **ACCEPTED — no migration, remote preflight, or scheduled detector.** The source documentation must state the accepted mismatched-owner failure and Option 1's exact pre-decided hardening trigger/direction.
3. **ACCEPTED — no migration, remote preflight, or scheduled detector.** The source documentation must state the accepted invalid-provenance failure, CHECK-first hardening trigger, and why simple FKs are incomplete.
4. The focused integration test observes real 23505 → exact CONFLICT message/reason through `postgres-errors.ts`; a fake repository test proves the identical duplicate-incomplete-create rule while existing sequential start-session coverage stays green.
