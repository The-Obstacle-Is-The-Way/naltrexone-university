# DEBT-466: Checkout Idempotency Replay-Chain Exhaustion (Subscription Recovery Bound Stops Traversal)

**Status:** Open
**Priority:** P3
**Date:** 2026-08-13
**Source:** Live diagnosis of repeated `trial-start.spec.ts` E2E failures on 2026-08-13 (server-log signature captured), reverified by a read-only Stripe test-mode census on 2026-08-14, plus a design-history sweep of the checkout idempotency arc (BUG-148 → DEBT-305 → DEBT-410 §B.11 item 8 → BUG-245 → DEBT-414 H10) and a 2026-08-14 isolated setup create/replay/expire/replay latency spike.
**Scope:** Before Part A, `createStripeCheckoutSession` and `createStripeTrialPaymentMethodSetupSession` in `src/adapters/gateways/stripe/stripe-checkout-sessions.ts` shared `CHECKOUT_SESSION_RECOVERY_ATTEMPT_LIMIT = 3` without a comment or documented rationale. Part A splits those meanings: subscription replay traversal uses `SUBSCRIPTION_CHECKOUT_REPLAY_TRAVERSAL_LIMIT = 10`; setup defective-response replacement keeps `TRIAL_SETUP_SESSION_RESPONSE_RECOVERY_ATTEMPT_LIMIT = 3`. Both exhaustion tests now derive their boundaries from the applicable constant. A live setup-mode probe proved that setup replay is a distinct stale-URL defect, not this replay-chain exhaustion mechanism.

---

## Description

The checkout gateway creates Stripe Checkout Sessions under a **deterministic** primary idempotency key — `checkout_session:{userId}:{plan}[:trial:{days}]` — a load-bearing BUG-245 decision that collapses concurrent same-plan creates so two tabs cannot double-bill. ADR-015 §4's dated 2026-08-14 amendment now licenses that later subscription-Checkout exception under explicit live-retrieval, bounded-recovery, variant-scoping, and request-fingerprint conditions; it does not license every short-lived redirect artifact. [Stripe's idempotency documentation](https://docs.stripe.com/api/idempotent_requests) says it saves the first request's status code and body, returns that same result on reuse, and can prune keys only after they are **at least 24 hours old**; it does not promise an exact 24-hour expiry. The repo's Stripe vendor doc now records those semantics.

The subscription path creates and then retrieves the Session. If that merged live snapshot is **inactive** (`isSessionInactive`: a present `status` is not `open`, or `expires_at` is at or before `nowMs()`), it retries under `checkout_session_recovery:{userId}:{plan}:{staleSessionId}[:trial:{days}]`, up to `SUBSCRIPTION_CHECKOUT_REPLAY_TRAVERSAL_LIMIT` recovery creates, then throws `STRIPE_ERROR: "Stripe Checkout Session is expired or inactive"`. A failed create is not charged to this counter: `callStripeWithRetry` owns its own three-attempt transient retry policy, and an exhausted or non-transient create error exits the ladder immediately. The setup path is different: it does not retrieve after create; it loops on a missing URL or inactive create response under `TRIAL_SETUP_SESSION_RESPONSE_RECOVERY_ATTEMPT_LIMIT` and uses `trial_setup_session_recovery:{userId}:{externalSubscriptionId}:{sessionId}:attempt:{attempt}:{requestFingerprint}`. In a 2026-08-14 test-mode probe, the first setup create returned `open` with a URL; same-key replay returned the same Session and saved body with `Idempotent-Replayed: true`; after the live Session was expired, replay still returned that saved `open` body and URL while retrieve returned `expired`. Therefore the setup loop's inactive check does not traverse retained replay state; it can instead accept a stale URL.

**The pre-Part-A subscription flaw:** Stripe's documented create example returns an `open` Session, and a reused key returns the saved create response; this adapter then retrieves the Session and can observe that the old Session is now `complete` or `expired`. Each retained key whose live Session had become terminal consumed one of the three permitted recovery creates. Chain walk: primary resolved to terminal session A; rung 1 (`f(A)`) resolved to terminal B; rung 2 (`f(B)`) resolved to terminal C; rung 3 could create fresh session D, so four consecutive completions succeeded. After D completed, the next invocation reached `attempt === 4` and threw before creating another Session. A terminal post-retrieval snapshot is not *definitionally* a replay echo — a Session could change state between fresh creation and retrieval — but the observed E2E chain was the retained-key replay case.

> **Before Part A, once four completed checkouts for one `(user, plan, variant)` remained reachable through retained Stripe idempotency keys, the fifth and later checkout attempts for that tuple failed hard until Stripe pruned a key.** Stripe documents only that pruning may occur after a key is at least 24 hours old. Failed attempts created no new Session, so they did not deepen the chain.

Observed server-log signature (2026-08-13): repeated `"Retrying checkout session creation with recovery idempotency key"` with `"status":"complete"` at `recoveryAttempt` 1→2→3, then `"Stripe checkout failed"` with `"errorMessage":"Stripe Checkout Session is expired or inactive"` → user lands on `/pricing?checkout=error`.

**Who hits it:**

- **Local E2E, deterministically while the keys remain retained.** `trial-start.spec.ts` is the only spec that completes a real hosted checkout, and it does so for a *stable* identity: `pnpm test:e2e` reuses the per-clone Docker test database; only manual `pnpm db:test:reset` runs `down -v`. The user UUID minted by `gen_random_uuid()` on the clone's first run therefore persists, while `resetE2EUserToFirstTimer()` cancels subscriptions without changing the customer or user identity. Before Part A, after four successful same-tuple completions, the fifth and later full-gate E2E runs failed `trial-start` with `checkout=error` until Stripe pruned a chain key — a false red that read like a billing regression. Five consecutive focused completions now pass under the raised bound.
- **CI: not exposed across jobs.** Each GitHub Actions job gets a fresh Postgres service and therefore a fresh app-user UUID, even though the owner-scoped Stripe test customer can be reused; because `userId` is in every checkout-chain key, keys do not repeat across CI jobs. The job runs the hosted completion once.
- **Production: narrow but nonzero path.** A completed Session implies a subscription, and `ALREADY_SUBSCRIBED` blocks further checkouts — a real user can fill the bounded retained chain only through repeated subscribe→lose-subscription→resubscribe loops while all chain keys remain retained. Part A raises that traversal capacity from the primary plus three recoveries to the primary plus ten; exhaustion still fails closed with `checkout=error`.

## Impact before Part A

- Local full-gate cadence was silently capped at four successful same-tuple completions while all chain keys remained retained; later gates reported the `trial-start` failure indistinguishably (at Playwright level) from a checkout regression.
- The warn logs reached `recoveryAttempt: 3`, `status: "complete"` without explaining that the next loop check threw before another create.
- Latent production edge (above) — same subscription root cause; Part A covers it with the raised, logged bound.

## Resolution — settled by replay-semantics spike (2026-08-14)

**Owner design re-review is complete:** apply a subscription-only replay-traversal limit of **10**, split the setup loop onto its own defective-response replacement limit of **3**, and keep the setup stale-URL finding out of this item's implementation scope. The subscription value is a measured healthy-service planning cap, not an absolute request timeout; the pricing route's 30-second `maxDuration` remains the hard backstop.

**Constraints honored (all deliberate, all keep):** deterministic Stripe primary key and concurrency collapse (BUG-245; tests `stripe-checkout-sessions-concurrency.test.ts`); the caller key remains application-level idempotency while `StripePaymentGateway` deliberately ignores it for Checkout (BUG-245; pinned in `stripe-payment-gateway.test.ts`); `:trial:{days}` variant scoping (DEBT-410 §B.11 item 8); parameter-mismatch recovery via request-fingerprint keys (BUG-245 for subscription Checkout; DEBT-414 H10 for setup Checkout); open-session inspection/expiry reconciliation (DEBT-305). The depth has no source comment or recorded rationale. Git history shows BUG-245 commit `be50dda7` introduced both the 20-rung bound and the post-create live retrieve in the same change; DEBT-414 commit `a4464f2f` later reduced the shared value to 3 while adding setup recovery. The setup exhaustion test hardcodes the current depth.

**Part A — split the bounds and raise subscription traversal (TDD).**

Implemented 2026-08-15. The new six-replay test first failed at the old guard with `STRIPE_ERROR`, then the focused Checkout contract run passed 8 files / 101 tests after the split. Five consecutive test-mode `pnpm test:e2e tests/e2e/trial-start.spec.ts` runs against the same per-clone database each completed successfully (58 s, 56 s, 59 s, 57 s, 57 s; setup plus focused spec reported 2 passed each), including the fifth completion that exhausted the old bound.

1. Red test first in `stripe-checkout-sessions-recovery.test.ts`: a chain of **6** completed retained-key replays followed by a fresh `open` Session must succeed. It failed at the pre-Part-A limit of 3. Add exact limit-relative boundaries too, phrased in primary-plus-recovery counts because the limit counts **recovery creates** and the primary create sits outside it: with limit `L`, `L` terminal snapshots (the primary plus recovery creates 1 through `L − 1`) followed by a fresh `open` on recovery create `L` succeeds; `L + 1` terminal snapshots (the primary plus all `L` recovery creates) exhaust the ladder and throw without issuing recovery create `L + 1`.
2. Replace the shared constant with `SUBSCRIPTION_CHECKOUT_REPLAY_TRAVERSAL_LIMIT = 10` and `TRIAL_SETUP_SESSION_RESPONSE_RECOVERY_ATTEMPT_LIMIT = 3`. The setup name and comment must say it bounds replacement of missing-URL or otherwise defective create responses; it is not replay-chain capacity. Retain 3 because the provider probe supplied no replay-depth reason to spend more attempts, preserving the existing fail-closed ceiling for anomalous create bodies. This 3 is the bound **before [DEBT-467](./debt-467-trial-setup-checkout-stale-session-url-replay.md)'s strict live retrieval lands**: its Resolution step 3 re-decides the setup bound with measured receipts once retrieval changes the constant's meaning from defective-response replacement to genuine replay traversal — do not treat 3 as the final post-retrieval value. Make its exhaustion test limit-relative instead of hardcoding four calls and attempts 1, 2, and 3.
3. Preserve low-depth subscription warns and add `error` logging at depth ≥ 5 without failing early. The hard stop remains only after the tenth recovery create.
4. Do not add live retrieval or stale-Session recovery to the trial-payment-method setup path under this item. The live probe proved that replay after expiration returns the saved `open` body and URL, so the current setup inactivity loop cannot detect that terminal live state. That distinct defect is now filed as [DEBT-467](./debt-467-trial-setup-checkout-stale-session-url-replay.md); the only setup edit in DEBT-466 is splitting and naming its existing defensive bound.

The subscription cap uses this implementation comment receipt:

```typescript
// WHY 10: each retained-key rung is cached create + live retrieve. The 2026-08-14
// test-mode probe measured 120.5 ms and 99.2 ms medians (5 samples each).
// At the repository retry envelope, a third-attempt success for both calls is
// 3×120.5 + 300 + 3×99.2 + 300 = 1,259.1 ms/rung. Primary + 10 recoveries
// budgets 13.850 s, below half the pricing route's 30 s maxDuration; 11 would
// budget 15.109 s. This is a healthy-service planning cap, not a request timeout.
```

Candidate receipts using the same formula (`primary + cap` rungs): cap 6 = 8.814 seconds, cap 10 = 13.850 seconds, and cap 20 = 26.441 seconds when every create and retrieve succeeds only on the repository wrapper's third attempt. Twenty leaves only 3.559 seconds for subscription/session preflight, final open-Session reconciliation, application/DB work, and variance, so it is rejected. The installed `stripe@22.4.0` client separately defaults to an 80-second transport timeout and two network retries, and `lib/stripe.ts` does not override them; therefore no traversal-depth constant can prove an absolute sub-30-second outage bound. A hard per-call deadline would be a separate retry-policy decision, not a property silently attributed to this fix.

**Part B — write the missing vendor knowledge down (completed 2026-08-15).** Stripe's saved-response semantics and at-least-24-hour key retention are now in `docs/vendor-docs/stripe.md`; `docs/dev/testing-infrastructure.md` records that completed `trial-start` Sessions remain chain rungs while their keys are retained, together with the local volume-persistence fact (`pnpm test:e2e` reuses the per-clone database; only `pnpm db:test:reset` drops its volume). ADR-015 §4 is reconciled by its dated 2026-08-14 amendment: deterministic subscription Checkout keys are a narrow, conditioned exception; the setup path is not licensed as precedent while it lacks live post-create retrieval.

**Rejected alternatives (each is the hack, with receipts):**

- **Entropy in the primary key** (per-run salt, timestamps, random component) — reopens BUG-245's double-billing hole and violates the current deterministic provider-key contract.
- **Rotate the Stripe customer in `resetE2EUserToFirstTimer()`** — does not change the key (`customer` is not a key component) and introduces avoidable provider-identity churn while leaving old-customer objects and events, contrary to the ownership discipline established by DEBT-386.
- **Test-only env salt read by production key-builders** — adds a test-only branch to production billing code without correcting production behavior.
- **Drop the DB volume per E2E run** — rotates the app-user UUID and therefore masks this key-chain defect, even though `seed-test-user.ts` re-finds the owner-matched Stripe customer. It is destructive, discards the stable-state test property, and substitutes test cleanup for a production-path fix.
- **Silently raise 3 → 10 without renaming** — leaves the bound's semantics and latency budget unexplained.
- **Depend on an `Idempotent-Replayed` response header** — Stripe does document the header ([advanced error handling](https://docs.stripe.com/error-low-level): "To identify a previously executed response that's being replayed from the server, look for the header `Idempotent-Replayed: true`"), and the installed SDK exposes `lastResponse.headers`, but the repo's deliberately narrow `StripeClient` type does not — and the subscription ladder's live retrieve already observes the terminal state, so the header adds nothing this fix needs. Optional future assertion only; not a fix dependency.
