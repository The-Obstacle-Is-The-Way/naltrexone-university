# DEBT-444: Hot-Path Prune Transactions Contend Without SKIP LOCKED and Lack Real-Postgres Coverage (`idempotency_keys` + `rate_limits`)

**Status:** Active
**Priority:** P3
**Date:** 2026-07-09

---

## Description

Both self-cleaning tables (`idempotency_keys` per ADR-015/BUG-103/104, `rate_limits` per BUG-102) prune opportunistically inside user-facing requests using the same select-then-delete transaction shape — a plain ordered `SELECT ... LIMIT 100` with **no `FOR UPDATE SKIP LOCKED`**, followed by an OR-list `DELETE`. Concurrent pruners therefore target the identical oldest-expired rows and serialize on each other's row locks, with the lock-wait awaited on user mutations. Prior rulings ([DEBT-167](../_archive/debt/debt-167-idempotency-key-prune-select-delete-race.md) delete-correctness guard, [DEBT-157](../_archive/debt/debt-157-hot-path-prune-failures-are-not-observable.md) warn-observability, [BUG-103](../_archive/bugs/bug-103-idempotency-key-pruning-never-wired.md)/[BUG-104](../_archive/bugs/bug-104-double-pruning-webhook-and-hot-paths.md) wiring) never evaluated latency or lock contention. A third, narrower gap: the rate-limiter prune has no real-Postgres verification at all.

### 1. Idempotency prune runs synchronously on every keyed mutation, without SKIP LOCKED

`withIdempotency` unconditionally awaits [`repo.pruneExpiredBefore(now, 100)`](../../src/adapters/shared/with-idempotency.ts#L141) before claiming, so every idempotent mutation (submit-answer, bookmark toggle, feedback, billing, session lifecycle — all routed through `executeIdempotent`) first pays a full interactive transaction against Neon: `BEGIN` + ordered `SELECT` on `idempotency_keys_expires_at_idx` ([db/schema.ts:315](../../db/schema.ts#L315)) + `COMMIT` — 3 sequential postgres-js round trips ([lib/db.ts:2](../../lib/db.ts#L2) uses the interactive `drizzle-orm/postgres-js` driver, not neon-http) even when zero rows are expired, plus a 100-condition OR-list `DELETE` (4th round trip) when rows exist. This is the **sole** prune site for `idempotency_keys` (BUG-104 removed the webhook-side prune), and the `SELECT` at [drizzle-idempotency-key-repository.ts:246-256](../../src/adapters/repositories/drizzle-idempotency-key-repository.ts#L246-L256) uses no `FOR UPDATE SKIP LOCKED` — so after an expiry backlog accumulates (e.g. a quiet period following a busy day), N concurrent requests all select the same 100 oldest rows (`ORDER BY expiresAt ASC`), and requests 2..N block on request 1's row locks, delete 0, and repeat wave-by-wave until the backlog drains at ≤100 rows per winning transaction. The fail-open catch at [with-idempotency.ts:140-152](../../src/adapters/shared/with-idempotency.ts#L140-L152) means no errors surface — only silent latency stacked onto user mutations exactly at peak load.

Magnitude caveat recorded by the verifier: same-region round trips are single-digit ms and prune transactions commit fast, so this is a per-mutation tax plus burst amplification, not an outage risk — hence P3 debt, not P2.

### 2. Rate-limiter prune: minute-boundary-synchronized stampede on the same unlocked rows

`DrizzleRateLimiter.limit()` computes [`windowStartMs = nowMs - (nowMs % windowMs)`](../../src/adapters/gateways/drizzle-rate-limiter.ts#L45), and every configured limit in [`src/adapters/shared/rate-limits.ts`](../../src/adapters/shared/rate-limits.ts) (webhook, checkout, portal, submit-answer, start-session, session-mutation, bookmark, rating, report) uses `ONE_MINUTE_MS` — so all keys reset at the identical UTC minute boundary. The first request on each key then satisfies `count === 1` ([line 76](../../src/adapters/gateways/drizzle-rate-limiter.ts#L76)) and synchronously awaits [`pruneExpiredWindows`](../../src/adapters/gateways/drizzle-rate-limiter.ts#L81) inside the user request (e.g. `startPracticeSession` at [practice-controller.ts:199](../../src/adapters/controllers/practice-controller.ts#L199)). The prune transaction does a plain `SELECT ... WHERE windowStart < cutoff ORDER BY windowStart ASC LIMIT 100` with no locking clause ([lines 106-115](../../src/adapters/gateways/drizzle-rate-limiter.ts#L106-L115)) followed by a composite-eq OR-list `DELETE` ([lines 119-131](../../src/adapters/gateways/drizzle-rate-limiter.ts#L119-L131)).

Whenever a ≥90-day-expired backlog exists (`PRUNE_RETENTION_DAYS = 90`), concurrent pruners target the same rows: one wins, the losers block on its row locks until commit — latency landing on submit-answer/start-session/bookmark/rating/checkout requests — then delete 0 rows; and because the OR-list `DELETE` has no fixed lock-acquisition order, they can also deadlock. Verifier refinements kept faithful here: (a) the try/catch at [lines 80-92](../../src/adapters/gateways/drizzle-rate-limiter.ts#L80-L92) **does** contain the deadlock variant (warn + skipped prune), so only the plain lock-wait latency reaches users; (b) contention requires a non-empty expired backlog — the `rows.length === 0` fast path makes steady-state prunes lock-free; (c) the composite `(key, windowStart)` exact-match `DELETE` cannot delete a live row (`rate_limits_key_window_start_pk`, [0002_curious_firelord.sql:5](../../db/migrations/0002_curious_firelord.sql#L5)), so the pre-fix DEBT-167 reclaimed-row race does **not** apply — this leg is contention/latency-only.

### 3. `pruneExpiredWindows` has no real-Postgres verification

The rate-limiter upsert's `ON CONFLICT (key, window_start)` increment path **is** covered against real Postgres — the original candidate claim that it wasn't was refuted: the frozen clock in [rate-limiter.integration.test.ts:24](../../tests/integration/rate-limiter.integration.test.ts#L24) makes all three `limit()` calls share one `window_start`, so calls 2-3 exercise the real conflict path, and a composite-PK-breaking migration would raise `42P10`. What survives is narrower: `pruneExpiredWindows` — the transaction that keeps `rate_limits` bounded (the BUG-102 fix) — is verified only against a hand-built mock of the Drizzle call chain ([drizzle-rate-limiter.test.ts:194](../../src/adapters/gateways/drizzle-rate-limiter.test.ts#L194) mocks `insert`/`select`/`delete`/`transaction` entirely, asserting call shape rather than SQL behavior). It does run incidentally during the integration test's first `limit()` call, but errors there route to the constructor-default `NOOP_LOGGER` ([drizzle-rate-limiter.ts:15-20, 30](../../src/adapters/gateways/drizzle-rate-limiter.ts#L15-L20)) and no assertion checks that expired rows are actually deleted or non-expired rows preserved. A Drizzle upgrade or refactor that breaks the prune's SQL emission or delete predicate would ship green and surface only as silent `rate_limits` growth in production warn logs — the failure mode DEBT-157 made loggable but nothing makes test-visible. P4 contribution: prune is best-effort/non-blocking and the hot-path upsert is in fact covered.

## Impact

Today: steady-state overhead only — every idempotent mutation pays ~3 extra sequential Neon round trips of pure prune-transaction overhead even with zero expired rows (part 1), and rate-limiter prunes are lock-free while the table has no expired backlog (part 2). At scale / after backlogs: burst-amplified lock-wait queues land directly on user-facing mutation latency, synchronized across all rate-limit keys at every UTC minute boundary, draining at ≤100 rows per winning transaction with wasted transactions and deadlock warnings in logs. No data corruption and no wrong rate-limit decisions in any leg — parts 1 and 2 are P3 latency/contention debt, part 3 is a P4 regression-detection gap whose failure mode is slow unbounded `rate_limits` growth (a BUG-102 recurrence detectable only by operators reading production warn logs).

## Proposed Resolution

**Part 1 (idempotency prune):**
- **(1a) RECOMMENDED:** move pruning off the request path — a scheduled Vercel cron (matching the existing cron-auth pattern; precedent: the [BUG-244](../_archive/bugs/bug-244-reconciliation-cron-never-scheduled.md) reconciliation cron) prunes `idempotency_keys` (and `rate_limits`, same pattern), with the hot-path call removed or reduced to probabilistic sampling (~1/64 of calls); update ADR-015's self-cleaning section.
- (1b) No-cron alternative: collapse `pruneExpiredBefore` to a single statement — `DELETE FROM idempotency_keys WHERE ctid IN (SELECT ctid FROM idempotency_keys WHERE expires_at < $cutoff ORDER BY expires_at LIMIT 100 FOR UPDATE SKIP LOCKED)` — one round trip instead of 3-4, no explicit transaction, concurrent pruners skip each other's rows. Fixes contention but keeps one round trip of per-mutation tax.
- (1c) Minimal: keep the current SQL but sample the hot-path prune probabilistically; cheapest, leaves the SKIP LOCKED gap for sampled callers that do collide.

**Part 2 (rate-limiter prune):**
- **(2a) RECOMMENDED:** replace the select-then-delete transaction with a single atomic `DELETE ... WHERE (key, window_start) IN (SELECT key, window_start FROM rate_limits WHERE window_start < $cutoff ORDER BY window_start LIMIT $n FOR UPDATE SKIP LOCKED)` (via Drizzle `sql` or a subquery builder). Concurrent pruners take disjoint batches: no blocking, no deadlock, faster drain. Apply the identical shape to `pruneExpiredBefore` (same defect class), ideally as one shared pattern next to `PRUNE_BATCH_LIMIT` ([prune-constants.ts:1](../../src/adapters/shared/prune-constants.ts#L1)).
- (2b) Move pruning to the existing daily Vercel cron, leaving `limit()` write-only — larger design change that reverses the BUG-102/104 hot-path-owner decision, so it needs an owner ruling.
- (2c) Mitigation only: fire-and-forget the hot-path prune — rejected as primary because dangling promises on Vercel serverless risk being frozen at response end unless wrapped in `waitUntil`, and it hides rather than removes the contention.

**Part 3 (coverage gap):**
- **(3a) RECOMMENDED:** extend `tests/integration/rate-limiter.integration.test.ts` with a direct `pruneExpiredWindows` case — insert expired and non-expired rows for two keys (tracked in `cleanup.rateLimitKeys`), call `limiter.pruneExpiredWindows(cutoff, N)`, assert the returned count, that expired rows are gone, and that non-expired rows survive. Closes the real gap at trivial cost.
- (3b) Optional add-on: a `Promise.all` of ~10 concurrent `limit()` calls on one key asserting the final stored count equals 10, as a cheap `ON CONFLICT` atomicity smoke (low marginal value).
- (3c) Alternative: explicitly ACCEPT the gap with a register note that prune breakage is production-log-detectable per DEBT-157 — defensible given best-effort semantics, but 3a is cheaper than the documentation.

Note recorded by the verifier: parts 1 and 2 are the same defect class on the same hot paths and were merged into this one item deliberately; a single shared SKIP-LOCKED prune helper (or a single cron) resolves both.

## Verification

- **Part 1:** the prune no longer opens an interactive transaction on the request path (cron route + test asserting the hot path issues no prune statements, or a single-statement `ctid ... FOR UPDATE SKIP LOCKED` delete pinned by an integration test); an integration test with two concurrent pruners against a >100-row expired backlog observes disjoint deletions (combined deleted count equals rows pruned, no lock-wait serialization). ADR-015's self-cleaning section updated to record the chosen owner.
- **Part 2:** same concurrent-pruner integration proof against `rate_limits`; the shared prune pattern (if extracted) covered once and referenced from both repositories.
- **Part 3:** named integration test in `tests/integration/rate-limiter.integration.test.ts` directly asserting `pruneExpiredWindows` deletes expired rows, preserves non-expired rows, and returns the deleted count against real Postgres.
