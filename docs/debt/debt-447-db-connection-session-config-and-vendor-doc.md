# DEBT-447: DB Connection/Session Configuration Unhardened — No Statement/Lock Timeouts, Unsized Pool, Unenforced `-pooler` Convention, Stale Vendor Doc Recommending Banned `push`

**Status:** Active
**Priority:** P3
**Date:** 2026-07-09

---

## Description

The production database connection seam — [`lib/db.ts`](../../lib/db.ts#L17) plus its designated vendor reference [`docs/vendor-docs/postgres.md`](../../docs/vendor-docs/postgres.md) — runs on driver defaults and unenforced conventions at three points. None is an active bug; each is a silent-until-load (or silent-until-misconfiguration) gap in the one client every DB-touching route shares.

### 1. No `statement_timeout` or `lock_timeout` anywhere in the DB path

The singleton postgres-js client at [`lib/db.ts:17-20`](../../lib/db.ts#L17) configures only `idle_timeout: 20` plus [`POSTGRES_CONNECTION_PARAMETERS`](../../lib/db-connection-options.ts#L1), which is `{ TimeZone: 'UTC' }` and nothing else. `statement_timeout` and `lock_timeout` appear nowhere in the repo — not in the app client, not in the drizzle migration runner, and not in [`docs/dev/migration-authoring.md`](../dev/migration-authoring.md), which reviews lock scope but prescribes no lock timeout. SPEC-029/BS-017 evaluated and settled `connect_timeout` (30s driver default, [ruled good](../_archive/specs/spec-029-dev-environment-resilience.md#L138), [BS-017 §Non-issue](../_archive/brainstorming/bs-017-dev-environment-resilience.md#L319)) and shipped client-side `withTimeout` + `maxDuration = 30` (e.g. [question page](<../../app/(app)/app/questions/[slug]/page.tsx#L9>)) — but those bound only the user-visible wait and the function invocation. Neither cancels the in-flight Postgres query, so on Fluid Compute the surviving singleton pool keeps a blocked connection pinned (default `max` 10) while client retries stack additional hung queries.

**Failure scenario:** [`vercel.json`](../../vercel.json#L3) runs `pnpm db:migrate && pnpm build` on every deploy while the previous deployment serves live traffic. A migration like [0027's `ALTER TABLE "attempts" DROP CONSTRAINT`](../../db/migrations/0027_early_wallow.sql#L47) needs ACCESS EXCLUSIVE on `attempts`; if a long-lived transaction (idle-in-transaction session, slow analytics query) holds a conflicting lock, the ALTER queues behind it and every answer-submit write on `attempts` queues behind the ALTER's lock request. With no `statement_timeout`, each blocked query pins one of the 10 pool connections indefinitely: users get 15s TimeoutErrors with a Retry button, each retry stacks another hung server-side query, functions die at `maxDuration` 30 without cancelling the Postgres query, and once all 10 connections are pinned every DB-touching route on the warm instance queues in postgres-js with no bound — an outage whose duration equals the lock-holder's lifetime, with no `lock_timeout` to make the migration itself fail fast either.

**Verifier corrections:** the "no connect timeout tuning" half of the original candidate is refuted — `connect_timeout` defaults to 30s and BS-017/SPEC-029 explicitly ruled it good, so only statement/lock duration is unbounded. "Users see 504s until platform kill" is also softened by the shipped mitigations (withTimeout 10–15s client errors with retry; `maxDuration` 30 on DB-touching routes); the verified residual cost is server-side pool pinning. Preconditions are narrow (conflicting long-lived lock during a deploy migration, or a Neon compute stall), hence P3.

### 2. Pool never sized; Neon `-pooler` endpoint requirement is convention-only

The production singleton inherits postgres.js's default `max = 10` connections per serverless instance. SPEC-029 [waved this through](../_archive/specs/spec-029-dev-environment-resilience.md#L138) ("`max` (10 is appropriate for serverless)") without arithmetic against instance-count × per-instance-pool vs. pooler/compute limits, while [`scripts/seed.ts:23`](../../scripts/seed.ts#L23) sets `max: 1` explicitly — the knob was known, but never deliberately sized for the one client that matters. Safety against Neon direct-endpoint connection exhaustion rests entirely on the unenforced convention that `DATABASE_URL` carries the `-pooler` suffix: [`lib/env.ts:40`](../../lib/env.ts#L40) validates only `z.string().url()`, no test or boot check asserts the pooler hostname (the string `-pooler` appears nowhere in `lib/`, `src/`, `tests/`, or `scripts/`), and the vendor doc itself both documents a [direct non-pooler endpoint for schema operations](../../docs/vendor-docs/postgres.md#L40) and [admits a single `DATABASE_URL` serves both roles](../../docs/vendor-docs/postgres.md#L69), making a silent swap plausible. Archived [DEBT-432](../_archive/debt/debt-432-postgres-js-prepared-statements-vs-neon-pooler-unconfirmed.md#L30) ruled only on prepared statements over this connection and explicitly left other pooler concerns open for refiling.

**Failure scenario:** an operator or a Neon/Vercel integration re-provision repoints production `DATABASE_URL` at the direct (non-`-pooler`) endpoint — nothing in build, boot, env validation, or tests objects, and the app works normally at low traffic. Under a burst, Vercel scales instances; each instance's pool lazily opens up to 10 connections, so ~12+ concurrently-busy instances exceed a 0.25–1 CU Neon compute's `max_connections` ([~112 observed on this project's compute](../_archive/debt/debt-411-local-e2e-flakiness-and-error-masking.md#L86)), and new requests fail with FATAL 53300 "remaining connection slots are reserved". Even on the correct pooler path, N instances × 10 connections contend for PgBouncer backend slots with no per-instance cap ever sized against expected concurrency. The misconfiguration is invisible until the burst — that silence is the core of the debt. P3 because the 53300 path requires misconfiguration plus a burst this niche app's current traffic makes hard.

### 3. Vendor doc recommends the banned `drizzle-kit push` and misdescribes the real connection config (P4)

[`docs/vendor-docs/postgres.md:40`](../../docs/vendor-docs/postgres.md#L40) instructs "Use for `drizzle-kit push`, schema operations" — directly contradicting the four-fold project ban ([`CLAUDE.md:93`](../../CLAUDE.md#L93), [`AGENTS.md:470`](../../AGENTS.md#L470), [`migration-authoring.md:83`](../dev/migration-authoring.md#L83), [`integration-tests.md:28`](../dev/integration-tests.md#L28)). The doc's ["Our Setup" sample (lines 15-24)](../../docs/vendor-docs/postgres.md#L20) is stale versus `lib/db.ts` — it omits `idle_timeout: 20` and inlines the connection params instead of importing `POSTGRES_CONNECTION_PARAMETERS` — and the doc self-contradicts on `DIRECT_URL` (recommended at [lines 38-44](../../docs/vendor-docs/postgres.md#L38), disclaimed at [line 69](../../docs/vendor-docs/postgres.md#L69) as not used).

**Failure scenario:** an agent or developer consulting the vendor doc for this exact seam runs `npx drizzle-kit push`. Nothing blocks it: no `db:push` package script exists, but drizzle-kit is installed and `drizzle.config.ts` resolves `DATABASE_URL` from `.env.local` (the shared remote Neon dev branch). Push applies DDL without migration files or ledger rows — skipping `pgcrypto`, CHECK constraints, and partial indexes, the exact failure class of archived [BUG-240](../_archive/bugs/bug-240-question-feedback-migrations-not-applied-to-dev-prod.md) — creating drift on a database shared by multiple clones, which the E2E migration-ledger preflight (DEBT-391/442) then flags on every subsequent run. Separately, anyone auditing connection behavior from the doc's sample reasons about a config without `idle_timeout: 20`. P4 per rubric — comprehension/hygiene; the destructive path requires following the vendor doc over the auto-loaded CLAUDE.md/AGENTS.md ban, but the vendor doc is the one reference dedicated to this seam.

## Impact

Today: no user-visible defect. Part 1 is the sharpest edge — every git-triggered deploy runs migrations against live traffic, and one long-lived conflicting lock converts to an unbounded warm-instance outage (pinned pool + retry stacking) instead of a bounded, retriable error. Part 2 is latent capacity risk: a silent endpoint swap or an unplanned burst turns an unsized default into FATAL 53300 or pooler queueing, with zero pre-burst signal. Part 3 costs comprehension and, in the worst path, shared-dev-branch schema drift requiring manual reconciliation. Severity contributions: Part 1 P3 (narrow preconditions, high blast when hit), Part 2 P3 (misconfiguration + burst required, but silent), Part 3 P4 (doc hygiene with a guarded-by-convention destructive path).

## Proposed Resolution

**Part 1:**
- **Option 1 (recommended):** add `statement_timeout` (e.g. `'25s'`, below the 30s `maxDuration`) to `POSTGRES_CONNECTION_PARAMETERS` in [`lib/db-connection-options.ts`](../../lib/db-connection-options.ts) — postgres-js passes `connection` entries as session GUCs at connect time, converting an indefinite lock wait into a bounded, retriable DB error that frees the pooled connection.
- **Option 2 (pairs with 1):** prescribe `SET lock_timeout` for migration execution (drizzle migrator session or a per-migration `SET LOCAL` preamble) and codify it in `docs/dev/migration-authoring.md`, so a deploy-time ALTER blocked behind a long transaction fails fast instead of queueing all traffic behind its ACCESS EXCLUSIVE waiter.
- **Option 3 (weakest):** owner-ACCEPT with a register entry documenting reliance on withTimeout + maxDuration and the accepted pool-pinning window.

**Part 2:**
- **Option 1 (recommended):** set an explicit, documented `max` in `lib/db.ts` sized for Vercel serverless concurrency (e.g. env-tunable `DB_POOL_MAX` defaulting to a small value like 5, with the sizing arithmetic — instances × max vs pooler/compute limits — recorded in `docs/vendor-docs/postgres.md`), plus a unit test pinning the options object so future edits are deliberate.
- **Option 2:** add a production-runtime guard in `lib/env.ts` (gated on `VERCEL_ENV === 'production'`, mirroring the existing Clerk key checks at [`lib/env.ts:118-175`](../../lib/env.ts#L118)): fail-closed if the `DATABASE_URL` hostname matches Neon's pattern (`.neon.tech`) but lacks the `-pooler` suffix, so a direct-endpoint swap breaks the build/boot instead of the next traffic burst.
- **Option 3 (minimum):** document the invariant and its arithmetic in `docs/vendor-docs/postgres.md` as an operational rule, replacing the pooler/direct description that offers no warning about the consequence of swapping them.

**Part 3:**
- **Recommended:** rewrite the "Direct Connection (Migrations)" section of `docs/vendor-docs/postgres.md` to name only `pnpm db:migrate` (drizzle-kit migrate) as the schema-operation path, add an explicit "never `drizzle-kit push`" line pointing to `docs/dev/migration-authoring.md`, and reconcile the `DIRECT_URL` block with the line-69 note that only `DATABASE_URL` is used; in the same patch, sync the "Our Setup" sample with the real `lib/db.ts` (`idle_timeout: 20`, `POSTGRES_CONNECTION_PARAMETERS` import).
- **Alternative 1:** replace the doc's code samples with a pointer to `lib/db.ts` as source of truth so they cannot go stale again (per the doc's own Upgrade Checklist).
- **Alternative 2 (optional):** add a repo-level guard rejecting `drizzle-kit push` (a doc-scan test or wrapper script), mirroring the DEBT-398 doc-drift enforcement pattern.

## Verification

- **Part 1:** a unit test pinning `POSTGRES_CONNECTION_PARAMETERS` to include `statement_timeout` (and its value's relation to `maxDuration`); an integration test observing that a query exceeding the timeout fails with Postgres error 57014 rather than hanging; `docs/dev/migration-authoring.md` updated with the `lock_timeout` prescription.
- **Part 2:** unit test pinning the `postgres()` options object (explicit `max`); if Option 2 is taken, an env-validation test proving a `.neon.tech` hostname without `-pooler` fails closed under `VERCEL_ENV=production` and passes for the pooler host and for local/Docker URLs; sizing arithmetic recorded in `docs/vendor-docs/postgres.md`.
- **Part 3:** `docs/vendor-docs/postgres.md` contains no `drizzle-kit push` recommendation, its setup sample matches `lib/db.ts` (or defers to it), and the `DIRECT_URL` contradiction is resolved; optionally a doc-scan test failing on the string `drizzle-kit push` outside ban-context lines.
