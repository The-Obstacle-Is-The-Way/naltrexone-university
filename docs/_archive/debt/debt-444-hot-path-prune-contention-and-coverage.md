# DEBT-444: Hot-Path Prune Transactions Can Contend Without SKIP LOCKED and Lack Direct Real-Postgres Coverage (`idempotency_keys` + `rate_limits`)

**Status:** Resolved
**Priority:** P3
**Date:** 2026-07-09
**Re-verified accurate against `ddad8eee` on 2026-07-18.**
**Resolved:** 2026-07-22 — FW-4 replaced both select-then-delete transactions with their pinned table-specific, bounded, deterministic `FOR UPDATE SKIP LOCKED` candidate-delete statements. Direct real-PostgreSQL tests cover expired deletion, live preservation, batch limits, and held oldest-candidate locks for both tables; ADR-015 records the retained request-path owner and one-statement shape. ## Description

Both self-cleaning tables (`idempotency_keys` per ADR-015/BUG-103/104, `rate_limits` per BUG-102) prune opportunistically inside user-facing requests using the same select-then-delete transaction shape: a plain ordered `SELECT ... LIMIT 100` with no row-locking clause, followed by an OR-list `DELETE`. Concurrent pruners can select overlapping expired batches; their `DELETE`s then wait on one another's row locks, and the request awaits that wait. Selection is not necessarily identical because each `ORDER BY` is non-unique, so losers do not necessarily delete zero rows. No concrete opposite lock-order cycle was found, so this item does not claim these same-table pruners deadlock. Prior rulings ([DEBT-167](../_archive/debt/debt-167-idempotency-key-prune-select-delete-race.md) delete-correctness guard, [DEBT-157](../_archive/debt/debt-157-hot-path-prune-failures-are-not-observable.md) warn-observability, [BUG-103](../_archive/bugs/bug-103-idempotency-key-pruning-never-wired.md)/[BUG-104](../_archive/bugs/bug-104-double-pruning-webhook-and-hot-paths.md) wiring) never evaluated latency or lock contention. Both prune implementations also lack a direct real-Postgres test that inserts expired and live rows and asserts deletion behavior.

### 1. Idempotency prune runs synchronously on every keyed mutation, without SKIP LOCKED

`withIdempotency` awaits [`repo.pruneExpiredBefore(now, 100)`](../../src/adapters/shared/with-idempotency.ts#L141) before claiming, so every keyed idempotent mutation routed through `executeIdempotent` first pays a postgres-js transaction: `BEGIN`, an ordered `SELECT` supported (but not necessarily chosen by the planner) by `idempotency_keys_expires_at_idx` ([db/schema.ts:315](../../db/schema.ts#L315)), and `COMMIT` — three sequential driver statements ([lib/db.ts:2](../../lib/db.ts#L2) uses `drizzle-orm/postgres-js`) even when zero rows are expired, plus the OR-list `DELETE` when rows exist. This is the sole production prune site for `idempotency_keys` (BUG-104 removed the webhook-side prune). The `SELECT` at [drizzle-idempotency-key-repository.ts:246-256](../../src/adapters/repositories/drizzle-idempotency-key-repository.ts#L246-L256) uses no `FOR UPDATE SKIP LOCKED`; after an expiry backlog accumulates, concurrent requests can select overlapping batches. At PostgreSQL's default Read Committed isolation, an overlapping `DELETE` waits for the first updater and ignores a row if that transaction deleted it ([PostgreSQL transaction-isolation semantics](https://www.postgresql.org/docs/current/transaction-iso.html#XACT-READ-COMMITTED)), so overlap produces request-path lock waits and wasted delete work while each transaction can remove at most 100 rows. The fail-open catch at [with-idempotency.ts:140-152](../../src/adapters/shared/with-idempotency.ts#L140-L152) returns the primary operation normally and emits a warning only on an actual prune error; ordinary lock-wait latency has no dedicated signal.

Magnitude is not measured in this repository. The batch is bounded and the transaction contains no external work, so this is tracked as P3 request-latency/contention debt rather than a demonstrated outage, but the live Neon cost and lock-wait distribution remain unquantified.

### 2. Rate-limiter prune: aligned windows can concentrate overlapping prune work

`DrizzleRateLimiter.limit()` computes [`windowStartMs = nowMs - (nowMs % windowMs)`](../../src/adapters/gateways/drizzle-rate-limiter.ts#L45), and every configured limit in [`src/adapters/shared/rate-limits.ts`](../../src/adapters/shared/rate-limits.ts) — both webhooks, checkout, portal, submit-answer, start-session, session mutation, bookmark, rating, report, health, and reconciliation cron — uses `ONE_MINUTE_MS`. All active keys therefore roll to a new window at the same UTC minute boundary, although each key prunes only when its first request in that window actually arrives. That insert returns `count === 1` ([line 76](../../src/adapters/gateways/drizzle-rate-limiter.ts#L76)) and synchronously awaits [`pruneExpiredWindows`](../../src/adapters/gateways/drizzle-rate-limiter.ts#L81) inside the request (for example, `startPracticeSession` at [practice-controller.ts:199](../../src/adapters/controllers/practice-controller.ts#L199)). The prune transaction does a plain `SELECT ... WHERE windowStart < cutoff ORDER BY windowStart ASC LIMIT 100` with no locking clause ([lines 106-115](../../src/adapters/gateways/drizzle-rate-limiter.ts#L106-L115)) followed by a composite-equality OR-list `DELETE` ([lines 119-131](../../src/adapters/gateways/drizzle-rate-limiter.ts#L119-L131)).

When rows older than the **current** 90-day cutoff exist (`PRUNE_RETENTION_DAYS = 90`; DEBT-448 sets a **target** 24-hour rate-limit-specific horizon), near-concurrent first-in-window requests can select overlapping batches and wait at the `DELETE`; the try/catch at [lines 80-92](../../src/adapters/gateways/drizzle-rate-limiter.ts#L80-L92) contains statement errors as warn-and-skip, but it does not bound an ordinary lock wait. Contention requires a non-empty expired backlog: the `rows.length === 0` fast path avoids the `DELETE` and therefore avoids prune row-lock contention. The composite `(key, windowStart)` exact-match predicate and primary key (`rate_limits_key_window_start_pk`, [0002_curious_firelord.sql:5](../../db/migrations/0002_curious_firelord.sql#L5)) also mean this path does not reproduce DEBT-167's reclaimed-idempotency-row deletion race. No source-level evidence established the previously claimed deadlock among these same-table prune transactions; PostgreSQL deadlocks require a cycle of incompatible waits, while the proven overlap here establishes a one-way wait ([PostgreSQL deadlock guidance](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-DEADLOCKS)).

### 3. Neither prune implementation has a direct real-Postgres behavior test

The rate-limiter upsert's `ON CONFLICT (key, window_start)` increment path is covered against real Postgres: the frozen clock in [rate-limiter.integration.test.ts:24](../../tests/integration/rate-limiter.integration.test.ts#L24) makes all three `limit()` calls share one `window_start`, so calls 2-3 exercise the real conflict path. What is not directly covered is either prune transaction. `pruneExpiredWindows` is verified against a hand-built Drizzle call-chain mock ([drizzle-rate-limiter.test.ts:194](../../src/adapters/gateways/drizzle-rate-limiter.test.ts#L194); the integration test invokes it incidentally on the first `limit()` call, but the constructor-default `NOOP_LOGGER` ([drizzle-rate-limiter.ts:15-20, 30](../../src/adapters/gateways/drizzle-rate-limiter.ts#L15-L20)) and fail-open catch hide prune errors, and no expired/live rows are asserted. `DrizzleIdempotencyKeyRepository.pruneExpiredBefore` likewise has call-shape and delete-guard unit coverage ([drizzle-idempotency-key-repository.test.ts:572-759](../../src/adapters/repositories/drizzle-idempotency-key-repository.test.ts#L572)), but [`idempotency-key-repository.integration.test.ts`](../../tests/integration/idempotency-key-repository.integration.test.ts) never calls that method; controller integration tests can invoke it only incidentally and do not assert its effect. A SQL-emission or predicate regression in either prune path can therefore remain green while expired rows accumulate. DEBT-157 makes production failures warn-visible when a logger is injected, but no direct integration assertion makes the behavior test-visible. P4 contribution: both prunes are best-effort and their primary claim/upsert paths already have real-Postgres coverage.

## Impact

Today: every keyed idempotent mutation pays three sequential prune-transaction statements even with zero expired rows (part 1); first-in-window rate-limit requests also perform the transaction, but an empty result avoids the `DELETE` and its row locks (part 2). With an expired backlog, overlapping batches can add lock-wait latency and wasted delete work directly to user-facing requests; the rate-limit windows align at UTC minute boundaries, but actual first requests need not arrive simultaneously. No data corruption or wrong rate-limit decision is established in either leg. Parts 1 and 2 remain P3 latency/contention debt; part 3 is a P4 regression-detection gap whose failure mode is renewed growth of either cleanup-owned table, warn-visible only when the production logger observes a thrown prune error.

## Proposed Resolution

**Part 1 (idempotency prune):**
- **(1a) REJECTED BY DIRECTION REVIEW:** move cleanup ownership off the request path to a dedicated scheduled maintenance job. That would add a schedule, authenticated route/task, capacity budget, monitoring surface, and overlapping-run policy to solve a bounded query-shape problem.
- **(1b) CHOSEN, minimal form:** collapse `pruneExpiredBefore` to one bounded `WITH candidates AS (SELECT ... ORDER BY expires_at, user_id, action, key LIMIT $n FOR UPDATE SKIP LOCKED) DELETE ... USING candidates RETURNING ...` statement joined on the real composite primary key. This removes the explicit transaction/read/delete sequence and lets overlapping workers skip row-locked candidates; PostgreSQL documents `SKIP LOCKED` for queue-like multi-consumer work ([locking-clause documentation](https://www.postgresql.org/docs/current/sql-select.html#SQL-FOR-UPDATE-SHARE)). It retains one request-path database statement and the existing owner.
- **(1c) REJECTED BY DIRECTION REVIEW:** sample the hot-path prune. Sampling adds tuning state, leaves the overlap shape intact, and needs a new keep-pace argument.

**Part 2 (rate-limiter prune):**
- **(2a) CHOSEN, minimal form:** replace the select-then-delete transaction with the same single-statement candidate-lock/delete shape, ordered by `window_start, key` and joined on `(key, window_start)`. `FOR UPDATE SKIP LOCKED` makes overlapping prune workers choose currently lockable candidates instead of waiting on rows another worker already locked; table-level locks still apply. Keep the two table-specific queries visibly parallel; do not add a generic helper for only two differently keyed tables.
- **(2b) REJECTED BY DIRECTION REVIEW:** move pruning to a scheduled maintenance job. It has the same disproportionate ownership and infrastructure cost as 1a.
- **(2c) REJECTED BY DIRECTION REVIEW:** fire-and-forget or request-lifecycle-extend the prune. It moves rather than removes contention and adds lifecycle machinery.

**Part 3 (coverage gap):**
- **(3a) CHOSEN, minimal form:** add one direct real-Postgres case per table. Extend `tests/integration/rate-limiter.integration.test.ts` with expired and non-expired rows for two keys, call `pruneExpiredWindows(cutoff, N)`, and assert count/deletion/preservation. Extend `tests/integration/idempotency-key-repository.integration.test.ts` analogously for `pruneExpiredBefore`, including preservation of a non-expired row and the batch limit. Add a bounded lock-holder case for each table (or one parameterized test only if that makes the concrete predicates clearer) proving locked candidates are skipped without waiting.
- **(3b) REJECTED AS OUT OF SCOPE:** a concurrent same-key `limit()` smoke tests the already-covered upsert, not either prune.
- **(3c) REJECTED BY DIRECTION REVIEW:** documentation-only acceptance costs less code but leaves both new one-statement predicates without real-Postgres behavior coverage.

Note recorded by the verifier: parts 1 and 2 are the same request-path cleanup/overlap class and belong in one item. A single maintenance owner can resolve both; if hot-path ownership remains, keep their SQL shapes visibly consistent without forcing an abstraction over different composite keys.

## Verification

- **Part 1:** the keyed request path emits one bounded candidate-lock/delete statement and no explicit prune transaction. A deterministic real-Postgres case uses separate PostgreSQL connections and transactions for the lock holder and pruner: behind a synchronization barrier, the holder locks the oldest candidates and keeps those row locks open until the pruner completes. The case separately asserts successful completion with no timeout/error, preservation of the locked candidates, and deletion of later unlocked expired rows. A local `lock_timeout` is only an auxiliary guard against a hanging regression; the successful outcome and row-state assertions prove `SKIP LOCKED` behavior. ADR-015 continues to name the request path as owner and records the one-statement shape.
- **Part 2:** the equivalent successful-completion proof covers `rate_limits`, again using separate PostgreSQL connections and transactions with the holder's row locks kept open until the pruner completes, directly exercising `(key, window_start)`, preserving locked candidates, deleting later unlocked expired rows, and using `lock_timeout` only as a hang guard; no generalized maintenance owner is introduced.
- **Part 3:** named real-Postgres integration tests directly assert each prune method's deleted count, limit, expired-row deletion, and live-row preservation.
