# BUG-286: Reconcile Phase 4 Inverts the Subscription-Writer Lock Order and Enables an AB-BA Deadlock (40P01)

**Status:** Resolved
**Severity:** P3
**Date:** 2026-07-09
**Confirmed:** 2026-07-09 (Cycle B2 independently re-derived the AB-BA cycle from source, installed driver behavior, and PostgreSQL lock semantics)
**Component:** Stripe webhook / checkout success / reconcile cron
**Resolution State:** Implemented on branch `fix/bug-285-286-stripe-failure-domain-lock-order` in [PR #626](https://github.com/The-Obstacle-Is-The-Way/naltrexone-university/pull/626), "Fix BUG-285/286: durable Stripe webhook failure state + canonical subscription-writer lock order" (merged and production-verified 2026-07-11 — see the Resolution section below). Phase B makes all three writers acquire advisory(user) → `stripe_subscriptions` → `stripe_customers`, pins the job call order in unit coverage, and proves both writer pairs complete under deterministic real-Postgres interleavings.

## Resolution (2026-07-11)

Fixed in PR #626 (squash `8e011843` to dev), promoted via PR #631 (main `c12d608b`); production deploy succeeded and `https://addictionboards.com/` returned HTTP/2 200. Reconcile Phase 4 was reordered to `subscriptions.upsert` before `stripeCustomers.insert`, so all three explicit writers share the canonical order advisory(user) → `stripe_subscriptions` → `stripe_customers`, documented with contract comments at each coordinator; pinned by the parameterized real-Postgres interleaving regression in `tests/integration/stripe-subscription-writer-lock-order.integration.test.ts`. Residual filed from the wave-close review as [BUG-294](../../bugs/bug-294-user-deletion-cascade-inverts-subscription-lock-order.md): the `ON DELETE CASCADE` writer on the user-deletion path is a fourth writer hard-wired to the inverse order and is not covered by this fix.


## Summary

Three production transaction paths write both `stripe_customers` and `stripe_subscriptions` for the same user, but they do not share one lock order. The webhook ([`stripe-webhook-controller.ts#L126-L142`](../../../src/adapters/controllers/stripe-webhook-controller.ts#L126)) and checkout-success eager-sync ([`checkout-success-sync.tsx#L241-L260`](<../../../app/(marketing)/checkout/success/checkout-success-sync.tsx#L241>)) transactions take the per-user advisory lock first — `subscriptions.upsert` executes `pg_advisory_xact_lock(hashtext(userId))` at [`drizzle-subscription-repository.ts#L82`](../../../src/adapters/repositories/drizzle-subscription-repository.ts#L82), held to top-level commit because each repository is constructed on its outer tx handle — then, when the subscription write persists, take the `stripe_customers(userId)` row lock via `INSERT .. ON CONFLICT DO UPDATE` ([`drizzle-stripe-customer-repository.ts#L33-L46`](../../../src/adapters/repositories/drizzle-stripe-customer-repository.ts#L33)). Reconcile Phase 4 ([`reconcile-stripe-subscriptions.ts#L232-L246`](../../../src/adapters/jobs/reconcile-stripe-subscriptions.ts#L232)) inverts this: `stripeCustomers.insert` row lock first, then the `subscriptions.upsert` advisory lock.

A webhook or checkout-success eager sync for user U overlapping the cron's Phase 4 transaction for U forms a hold-and-wait cycle; Postgres's deadlock detector aborts one victim with `40P01`. PostgreSQL's [`deadlock_timeout` default is one second](https://www.postgresql.org/docs/current/runtime-config-locks.html), although the deployed setting is not encoded in this repository. No lock-ordering guard, comment, or test exists. The rollback is atomic, so this does not create a partial database write, but a webhook-carried subscription transition can remain stale until a later Stripe delivery or successful reconciliation run repairs it, and a checkout-success victim loses that request's eager-sync result.

## Reachability

All three paths run in production: the webhook is Stripe-driven (renewals, portal actions, `subscription.updated`/`deleted` events), checkout success eagerly syncs a user's just-completed session before rendering its interstitial ([`checkout-success-sync.tsx#L73-L90`](<../../../app/(marketing)/checkout/success/checkout-success-sync.tsx#L73>)), and the reconcile cron ([`app/api/cron/reconcile-stripe-subscriptions/route.ts#L213-L219`](../../../app/api/cron/reconcile-stripe-subscriptions/route.ts#L213)) opens a Phase 4 transaction per reconciled user. The precondition is either independent webhook traffic or a checkout-success request for user U landing inside U's own short Phase 4 transaction window, with the subscription-first writer reaching its customer write. One narrowing correction verified during the sweep: the cron's Phase 5 cancels for user U fire only after U's Phase 4 has committed, so the run's *own* delayed `subscription.deleted` webhooks cannot collide with the same user's Phase 4 in the same run — the webhook trigger must be organic or retried traffic. [Stripe retries failed live-mode webhook deliveries for up to three days](https://docs.stripe.com/webhooks#automatic-retries), so retry traffic is a real source, but either overlap remains narrow.

## Reproduction

Exact interleaving for a shared user U:

1. Cron Phase 4 opens its transaction and acquires the `stripe_customers(U)` row lock via `INSERT .. ON CONFLICT DO UPDATE` ([`reconcile-stripe-subscriptions.ts#L233`](../../../src/adapters/jobs/reconcile-stripe-subscriptions.ts#L233) → [`drizzle-stripe-customer-repository.ts#L33`](../../../src/adapters/repositories/drizzle-stripe-customer-repository.ts#L33)).
2. Concurrently, either a Stripe webhook for U opens its transaction ([`lib/container/controllers.ts#L24-L31`](../../../lib/container/controllers.ts#L24)) or checkout-success eager sync opens its transaction ([`checkout-success-deps.ts#L35-L41`](<../../../app/(marketing)/checkout/success/checkout-success-deps.ts#L35>)); its `subscriptions.upsert` acquires `pg_advisory_xact_lock(hashtext(U))` ([`stripe-webhook-controller.ts#L126`](../../../src/adapters/controllers/stripe-webhook-controller.ts#L126) or [`checkout-success-sync.tsx#L243`](<../../../app/(marketing)/checkout/success/checkout-success-sync.tsx#L243>) → [`drizzle-subscription-repository.ts#L82`](../../../src/adapters/repositories/drizzle-subscription-repository.ts#L82)) before the cron reaches its own upsert.
3. After a persisted subscription write, that writer reaches `stripeCustomers.insert` ([`stripe-webhook-controller.ts#L137`](../../../src/adapters/controllers/stripe-webhook-controller.ts#L137) or [`checkout-success-sync.tsx#L253`](<../../../app/(marketing)/checkout/success/checkout-success-sync.tsx#L253>)) and blocks on the cron's row lock — while still holding the advisory lock.
4. The cron reaches `subscriptions.upsert` ([`reconcile-stripe-subscriptions.ts#L238`](../../../src/adapters/jobs/reconcile-stripe-subscriptions.ts#L238)) and blocks on the subscription-first writer's advisory lock.

Expected: both writers serialize on a consistent lock order; one waits briefly, both commit.

Actual: AB-BA cycle → after `deadlock_timeout` Postgres aborts one victim with `40P01`. If the cron is the victim, the per-row catch records the row as failed and the run reports `failed > 0`. If the webhook is the victim, the `40P01` aborts its outer transaction, the in-transaction `stripeEvents.markFailed` at [`stripe-webhook-controller.ts#L148`](../../../src/adapters/controllers/stripe-webhook-controller.ts#L148) then hits `25P02` (transaction aborted), and the route returns 500 until a later delivery succeeds. (That secondary `25P02` replacing the processing error as the top-level failure, while the original can survive in serialized query parameters, is filed separately as [BUG-285](./bug-285-stripe-webhook-markfailed-on-aborted-transaction.md), referenced here but not double-counted.) If checkout success is the victim, its transaction rejects before `runCheckoutSuccessPage` can render the success interstitial ([`page.tsx#L41-L47`](<../../../app/(marketing)/checkout/success/page.tsx#L41>)); a later webhook or reconcile run can still converge the database state.

## Root Cause

Classic AB-BA lock ordering inversion between independently built transaction coordinators:

- Subscription-first writer order: advisory(U) → `stripe_customers(U)` row lock. `subscriptions.upsert` runs before `stripeCustomers.insert`, gated on `write.persisted`, in both the webhook ([`stripe-webhook-controller.ts#L126-L142`](../../../src/adapters/controllers/stripe-webhook-controller.ts#L126)) and checkout-success eager sync ([`checkout-success-sync.tsx#L241-L260`](<../../../app/(marketing)/checkout/success/checkout-success-sync.tsx#L241>)).
- Reconcile Phase 4 order: `stripe_customers(U)` row lock → advisory(U). [`reconcile-stripe-subscriptions.ts#L232-L246`](../../../src/adapters/jobs/reconcile-stripe-subscriptions.ts#L232) writes the customer mapping first, then the subscription.
- Both lock acquisitions participate in one top-level transaction for each affected path: the repositories are constructed with the outer tx handle ([`controllers.ts#L24-L31`](../../../lib/container/controllers.ts#L24), [`checkout-success-deps.ts#L35-L41`](<../../../app/(marketing)/checkout/success/checkout-success-deps.ts#L35>), [`route.ts#L213-L219`](../../../app/api/cron/reconcile-stripe-subscriptions/route.ts#L213)), so the `db.transaction` inside `DrizzleSubscriptionRepository.upsert` ([`drizzle-subscription-repository.ts#L80`](../../../src/adapters/repositories/drizzle-subscription-repository.ts#L80)) is a postgres-js savepoint. On the successful path that savepoint is not rolled back, and the transaction-level advisory lock remains held until the outer transaction ends, matching [PostgreSQL's transaction-level advisory-lock semantics](https://www.postgresql.org/docs/current/explicit-locking.html#ADVISORY-LOCKS).
- Refuted leg, for completeness: checkout-session creation also writes `stripe_customers` at [`create-checkout-session.ts#L77`](../../../src/application/use-cases/create-checkout-session.ts#L77), but that call is a standalone repository write holding no subscription/advisory lock, so it cannot participate in this deadlock. Checkout-success eager sync is not part of that refutation: it is transaction-bound and has the same subscription-first order as the webhook.

## Impact

No partial database write survives: Postgres aborts one victim atomically. The cost is not only operational noise. A webhook victim produces a 500 with the secondary `25P02` promoted over the processing error, and the subscription transition carried by that webhook can remain unapplied until a redelivery succeeds; a checkout-success victim rejects that eager-sync request before its interstitial renders; a cron victim leaves that row unreconciled until another run. Severity remains P3 rather than P2 because each collision requires the same user's subscription-first write to overlap the short Phase 4 transaction and all affected paths have later convergence opportunities. It is not P4 because the inversion remains indefinitely reproducible in the payment path, can temporarily leave entitlement stale, and produces alert-worthy failures that cost real triage time.

## Proposed Fix

1. **(Recommended)** Reorder reconcile Phase 4 to call `subscriptions.upsert` before `stripeCustomers.insert`. The subscription repository already owns the per-user advisory lock, so this makes all three paths acquire advisory(user) → `stripe_subscriptions` row → `stripe_customers` row without duplicating raw SQL in the job. The customer mapping can still be written unconditionally after `upsert`; unlike the webhook and checkout-success path, reconcile does not need to gate that call on `write.persisted`. Both operations remain atomic in the existing outer transaction.
2. Document that canonical order beside all three multi-repository transaction coordinators and add real-Postgres regressions that orchestrate the old interleaving against each subscription-first writer. The tests must fail the pre-fix order with `40P01` and prove both writer pairs complete under the corrected order; mock call-order tests are useful but not sufficient for the lock claim.
3. **(Mitigation only — rejected as the primary fix)** Retry the whole failed transaction on `40P01` at each owning transaction boundary. This reduces incident noise but leaves the ordering defect in place; retrying only the repository savepoint is not sufficient when the webhook's direct customer statement aborts the outer transaction.
