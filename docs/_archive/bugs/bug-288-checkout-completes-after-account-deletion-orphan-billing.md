## Resolution (2026-07-13)

Fixed in [PR #634](https://github.com/The-Obstacle-Is-The-Way/naltrexone-university/pull/634) (squash `21fee665` to dev), promoted via PR #638 (main `438b84d8`, main/dev trees byte-identical); production deploy succeeded and `https://addictionboards.com/` returned HTTP/2 200. The account-deletion obligation now deletes the Stripe Customer (Proposed Fix Option 1): both the inline `user.deleted` completion and the daily durable drain call `customers.del` through the renamed customer-cleanup gateway ([`stripe-customer-deleter.ts`](../../../src/adapters/gateways/stripe-customer-deleter.ts)), treating already-deleted/missing-customer responses as idempotent success with the BUG-246-breadth done-state predicate, so a Checkout Session completing after deletion can no longer leave a subscription with no application-owned stop — Stripe documents that deleting a Customer cancels its active subscriptions, removes payment details, and prevents further operations. The drain processes bounded pages (25 rows × 3 pages per run) with this-run failure exclusion and a `hasMore` backlog warning; the customer-mapping read happens under the canonical advisory lock (TOCTOU closed — see the review notes below); paired fake/real contract coverage lives in `tests/integration/pending-stripe-customer-cleanup-contract.integration.test.ts`.

## Summary

The Clerk `user.deleted` flow ([`clerk-webhook-controller.ts#L325-L373`](../../../src/adapters/controllers/clerk-webhook-controller.ts#L325-L373)) deletes the local user (cascading `stripe_customers`/`stripe_subscriptions`), tombstones the Clerk id, runs a point-in-time `stripe.subscriptions.list({ status: 'all' })` cancel loop (`stripe-subscription-canceler.ts#L36-L40` at the audited head; the fix renamed that gateway to [`stripe-customer-deleter.ts`](../../../src/adapters/gateways/stripe-customer-deleter.ts)), then deletes the `pending_stripe_cancellations` row. It never expires open Checkout Sessions and never deletes the Stripe customer. This code does not set `expires_at`, so Stripe's [default 24-hour Checkout Session lifetime](https://docs.stripe.com/payments/checkout/how-checkout-works#expiration) applies. A Session opened before deletion can therefore still complete afterward, creating a new Stripe subscription carrying `subscription_data.metadata.user_id` = the now-deleted local UUID ([`stripe-checkout-sessions.ts#L678-L682`](../../../src/adapters/gateways/stripe/stripe-checkout-sessions.ts#L678-L682)).

The resulting `checkout.session.completed` webhook resolves that userId from metadata ([`stripe-subscription-normalizer.ts#L32`](../../../src/adapters/gateways/stripe/stripe-subscription-normalizer.ts#L32)) and calls `subscriptions.upsert` ([`stripe-webhook-controller.ts#L126`](../../../src/adapters/controllers/stripe-webhook-controller.ts#L126)). The INSERT violates the `stripe_subscriptions.user_id → users.id` FK named `stripe_subscriptions_user_id_users_id_fk` ([`db/schema.ts#L177-L179`](../../../db/schema.ts#L177-L179), [`0000_jazzy_vermin.sql#L112`](../../../db/migrations/0000_jazzy_vermin.sql#L112)); `23503` is not a unique violation, so the repository wraps it as `INTERNAL_ERROR` ([`drizzle-subscription-repository.ts#L135-L148`](../../../src/adapters/repositories/drizzle-subscription-repository.ts#L135-L148)). Because the failing statement ran inside the repository's nested postgres-js savepoint, the outer transaction remains usable: the controller durably marks the Stripe event failed ([`stripe-webhook-controller.ts#L148`](../../../src/adapters/controllers/stripe-webhook-controller.ts#L148)), then the route returns 500 ([`app/api/stripe/webhook/handler.ts#L97-L101`](../../../app/api/stripe/webhook/handler.ts#L97-L101)). [Stripe retries failed live-mode deliveries for up to three days](https://docs.stripe.com/webhooks#automatic-retries), but every retry reaches the same missing-user FK. The application has no later path that cancels this Stripe-only subscription.

## Reachability

The money-impacting path is a churned/returning user with a non-null terminal local subscription row: [`CreateCheckoutSessionUseCase`](../../../src/application/use-cases/create-checkout-session.ts#L130-L142) gives a trial only when no local subscription exists, so this returning-user Checkout is the ordinary paid flow. The user opens Checkout, deletes their Clerk account while the Session remains open, then completes within Stripe's default 24-hour lifetime. A true first-time user instead receives this app's no-card trial (`payment_method_collection: 'if_required'` plus `missing_payment_method: 'cancel'` at [`stripe-checkout-sessions.ts#L684-L701`](../../../src/adapters/gateways/stripe/stripe-checkout-sessions.ts#L684-L701)); that path still creates an untracked trial subscription, but normally does not create recurring card charges when no payment method exists. The sequence is unusual but production-reachable, and the codebase's own `checkout.sessions.expire` calls ([`stripe-checkout-sessions.ts#L253`](../../../src/adapters/gateways/stripe/stripe-checkout-sessions.ts#L253), [`#L606`](../../../src/adapters/gateways/stripe/stripe-checkout-sessions.ts#L606)) confirm that explicit expiration is the mechanism that makes an open Session uncompletable.

## Reproduction

1. A returning user whose prior local subscription is terminal opens paid Stripe Checkout — a Session is created with `customer: cus_X` and `subscription_data.metadata.user_id: <local UUID>` ([`stripe-checkout-sessions.ts#L669-L683`](../../../src/adapters/gateways/stripe/stripe-checkout-sessions.ts#L669-L683)).
2. User deletes their Clerk account. `user.deleted` processing succeeds: the local user row cascade-deletes `stripe_customers`/`stripe_subscriptions`, the Clerk id is tombstoned, `cancelStripeCustomerSubscriptions(cus_X)` cancels the point-in-time subscription list, and the `pending_stripe_cancellations` row is deleted ([`clerk-webhook-controller.ts#L361-L373`](../../../src/adapters/controllers/clerk-webhook-controller.ts#L361-L373)).
3. Within the Session's lifetime, the user completes payment. Stripe creates a new active subscription on `cus_X` and emits `checkout.session.completed`.
4. The webhook resolves userId from subscription metadata ([`stripe-subscription-normalizer.ts#L32`](../../../src/adapters/gateways/stripe/stripe-subscription-normalizer.ts#L32)); `subscriptions.upsert` INSERTs with the deleted UUID; Postgres raises FK violation `23503`; the repository throws `INTERNAL_ERROR` ([`drizzle-subscription-repository.ts#L143-L148`](../../../src/adapters/repositories/drizzle-subscription-repository.ts#L143-L148)); `stripeEvents.markFailed` records it ([`stripe-webhook-controller.ts#L148`](../../../src/adapters/controllers/stripe-webhook-controller.ts#L148)); the route returns 500 through Stripe's live retry window.

Expected: the Stripe subscription is canceled (or the checkout is prevented from completing) because the account no longer exists.

Actual: the Stripe-side subscription stays active with no local record or application-owned stop condition. On the paid path, recurring charges can continue until Stripe's own lifecycle or a customer/operator intervention stops them.

## Root Cause

Two seams combine:

1. **The deletion flow's Stripe cleanup is point-in-time and one-shot.** `cancelStripeCustomerSubscriptions` (`stripe-subscription-canceler.ts#L31-L40` at the audited head; now [`stripe-customer-deleter.ts`](../../../src/adapters/gateways/stripe-customer-deleter.ts)) cancels only the subscriptions that exist at that instant, and the `pending_stripe_cancellations` row is drained on success ([`clerk-webhook-controller.ts#L366-L373`](../../../src/adapters/controllers/clerk-webhook-controller.ts#L366-L373)), so the BUG-246 drain machinery cannot fire for a subscription created afterward. Open Checkout Sessions are never expired and the Stripe customer is never deleted, leaving the front door open.
2. **No recovery path sees the orphan.** The Stripe webhook write path never consults `deleted_clerk_users` tombstones; moreover, those tombstones are keyed by Clerk id while the Stripe subscription carries the deleted local UUID, so a safe lookup needs an explicit missing-user cleanup design rather than a direct tombstone query. The FK failure is treated as a generic internal error. The checkout-success eager-sync path cannot repair it either: a signed-out visitor is redirected to sign-in, and any different account fails the metadata-user equality check ([`checkout-success-sync.tsx#L129-L185`](<../../../app/(marketing)/checkout/success/checkout-success-sync.tsx#L129-L185>)). The reconcile cron iterates only local `stripeSubscriptions.findMany` rows ([`reconcile-stripe-subscriptions/route.ts#L197-L198`](../../../app/api/cron/reconcile-stripe-subscriptions/route.ts#L197-L198)), so a Stripe-only subscription is invisible to it. Even if the owner-configured Stripe Dashboard one-subscription-per-customer backstop recorded in [BUG-245](./bug-245-concurrent-two-tab-checkout-creates-duplicate-subscriptions.md) remains enabled, it does not apply because the customer has zero subscriptions after the deletion-time cancel.

## Impact

Money can move wrong: on the paid returning-user path, recurring charges can continue with no local subscription record and no automated remediation. The failure is observable in the durable `stripe_events.error` row and Stripe's failed-delivery tooling, but those signals do not stop billing and the deleted user has no in-product portal path. **Severity is P2:** the trigger is an unusual 24-hour account-deletion/Checkout sequence, but it is directly user-reachable, silently creates an untracked financial obligation, and has no application-owned bound. This matches the register's P2 precedent in BUG-246 for rare deleted-account billing leaks rather than treating narrow probability as sufficient for P3.

## Proposed Fix

- **Option 1 (recommended — close the lifecycle at its owner, if retention policy permits):** make the account-deletion obligation delete the Stripe Customer, not merely list-and-cancel the subscriptions visible at one instant. Stripe documents that [deleting a Customer immediately cancels its active subscriptions, removes payment details, and prevents further operations such as adding a subscription](https://docs.stripe.com/api/customers/delete). Treat already-deleted/missing Customer responses idempotently, and generalize/rename the durable `pending_stripe_cancellations` contract so it truthfully represents a customer-cleanup obligation. This gives the existing Clerk-event-backed queue a retryable operation that closes both pre-existing and complete-after-delete subscriptions without holding a database transaction across Stripe I/O.
- **Option 2 (if Customer deletion is rejected for product/accounting reasons):** during `user.deleted`, enumerate and expire every open Checkout Session before the subscription-cancel pass. Stripe documents that [an expired Session cannot be completed](https://docs.stripe.com/api/checkout/sessions/expire). Preserve auto-pagination and idempotent already-terminal handling. This order means an overlapping completion either loses to expiration or creates a subscription before the subsequent cancel listing; still pair it with a durable orphan-webhook recovery path for API/eventual-consistency failures.
- **Option 3 (defense in depth):** classify the specific missing-user FK at the repository boundary and create a durable Stripe-origin cleanup obligation before acknowledging the event. The current `pending_stripe_cancellations` table cannot be used as originally proposed: its `event_id` has an FK to `clerk_events.id` ([`db/schema.ts#L258-L265`](../../../db/schema.ts#L258-L265), [`0016_odd_gressill.sql#L7`](../../../db/migrations/0016_odd_gressill.sql#L7)), so inserting a Stripe event id would itself fail `23503`. Use a source-aware queue or a separate Stripe-event-backed cleanup table, then perform the external cancellation after commit and mark the Stripe event processed only when the obligation is durably represented.
- **Option 4 (broader backstop):** add an account-wide Stripe subscription scan that flags/cancels active subscriptions whose `metadata.user_id` has no local user. A per-known-customer scan is insufficient because the local `stripe_customers` row was cascade-deleted; this option requires Stripe-account pagination and materially more API volume.

Verification caveat carried from the finding: every code link was read and verified in a read-only audit (nothing executed). The load-bearing vendor premises are now linked to Stripe's official Checkout expiration, webhook retry, Session-expiration, and Customer-deletion documentation above; no live Stripe account or database was touched.

## Implementation Notes (fix branch)

**2026-07-11:** Phase B is implemented on branch `fix/bug-288-294-deletion-lifecycle` in [PR #634](https://github.com/The-Obstacle-Is-The-Way/naltrexone-university/pull/634), **“Fix BUG-288/294: deletion-owned Stripe customer lifecycle + conforming deletion lock order.”** Both the inline `user.deleted` completion and the daily durable-obligation drain now delete the Stripe Customer through the Stripe gateway; resolved deleted-customer responses and missing-customer 404s are idempotent success, while failures retain the obligation. Stripe retains deleted Customer history for accounting while removing payment details and preventing new subscriptions, matching the account-deletion request and data-minimisation posture. The physical table name `pending_stripe_cancellations` remains as an explicitly deferred rename residue; ports, adapters, fakes, and use-case names now describe customer cleanup. Merged and production-verified 2026-07-13 — see the Resolution section above.

**2026-07-12 (pre-merge adversarial review, same PR):**

- **Drain semantics disclosed and hardened.** The scheduled drain processes bounded pages (25 rows × 3 pages per run), excludes this-run failures between pages so a poisoned head cannot starve newer obligations, and reports a `hasMore` backlog flag with a warning log when stale work remains after the page budget — replacing an undisclosed single-batch 25-row cap that could silently defer newer cleanups for days. Cross-run poison beyond the page budget remains bounded-visible (daily 500 + backlog warning), with durable attempt-tracking left to the register's drain-lifecycle owner ([DEBT-449](../../debt/debt-449-webhook-event-ledger-lifecycle.md)).
- **Done-state predicate restored to BUG-246 breadth.** `resource_missing` invalid-request errors without a numeric 404 (e.g. re-wrapped by an intermediary) are again idempotent success rather than eternally retried failures.
- **Customer-mapping TOCTOU closed.** The deletion transaction reads the `stripe_customers` mapping only while holding the canonical advisory lock, so a concurrent reconcile/checkout repoint cannot cause the cleanup obligation to capture a stale customer id and orphan the real one (see BUG-294's Resolution State for the paired lock-order correction).
- **Explicitly deferred residue (needs its own register anchor if this doc is archived):** the missing-user FK path is untouched — after a committed deletion, a redelivered subscription write (including the `customer.subscription.deleted` events emitted by our own `customers.del`) still fails `23503` → generic `INTERNAL_ERROR` → durable failed `stripe_events` rows and 500s through the provider retry window. Option 3's repository-boundary classification was deliberately not implemented in this PR. Filed at archival as [BUG-296](../../bugs/bug-296-post-deletion-subscription-webhooks-fail-users-fk.md).
