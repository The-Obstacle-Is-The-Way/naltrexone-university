# BUG-290: State-Write Idempotency Policy Caches Transient INTERNAL_ERROR — Submit Re-Click and Mark Toggle Replay the Stale Failure

**Status:** Resolved
**Severity:** P3
**Date:** 2026-07-09
**Confirmed:** 2026-07-09 (multi-agent adversarial sweep; independently re-verified at source before filing)
**Component:** Idempotency / practice state writes

## Resolution (2026-07-14)

Fixed in [PR #640](https://github.com/The-Obstacle-Is-The-Way/naltrexone-university/pull/640) (squash `666097aa` to dev), promoted via PR #641 (main `7d94359b`); production deploy succeeded and `https://addictionboards.com/` returned HTTP/2 200. Rollback-certain statement cancellation is now classified at its transaction owners (Proposed Fix §1): `getPostgresErrorCode` accepts only SQLSTATE-shaped codes and traverses `cause` chains — so a `57014` wrapped by a repository as `ApplicationError('INTERNAL_ERROR', { cause })` classifies correctly, pinned with the production wrap shape and on the real-Postgres determinacy suite — and a vetted cancellation aborts the fenced claim so a same-key Submit re-click or mark toggle re-executes instead of replaying the stale failure. Terminal typed conflicts stay cacheable, and commit-indeterminate failures retain conservative fencing: submit retries were deliberately not broadened beyond rollback-certain classes because unscoped attempts still have no per-request uniqueness key (§2's ambiguous-outcome boundary, unchanged).

## Summary

[`shouldCachePracticeSessionStateWriteError`](../../../src/adapters/controllers/shared/practice-session-idempotency-policy.ts#L7-L15) is a denylist with exactly one exemption: it caches every execute error except `details.reason === StateChangedConcurrently`. `question:submitAnswer` runs through the composition-root transaction retry, but that runner recognizes only `40001` and `40P01` ([`use-cases.ts#L41-L50`](../../../lib/container/use-cases.ts#L41-L50)); a rollback-certain nonmember such as statement cancellation `57014` escapes after the transaction aborts. `practice:setPracticeSessionQuestionMark` does not use that composition-root runner: its updater retries zero-row version-CAS misses, while a SQL statement/transaction error escapes directly ([`practice-session-question-state-updater.ts#L128-L137`](../../../src/adapters/repositories/practice-session-question-state-updater.ts#L128-L137), [`#L174-L193`](../../../src/adapters/repositories/practice-session-question-state-updater.ts#L174-L193)). [`toErrorRecord`](../../../src/adapters/shared/with-idempotency.ts#L39-L49) normalizes an escaped raw error to `INTERNAL_ERROR`; repository-wrapped database failures already arrive as `ApplicationError('INTERNAL_ERROR')` and retain that code. Either shape is cached for the default 24h TTL. The policy is wired to `question:submitAnswer` ([`question-controller.ts#L262-L270`](../../../src/adapters/controllers/question-controller.ts#L262-L270)), `practice:finalizeExamAnswers` ([`practice-controller.ts#L345-L352`](../../../src/adapters/controllers/practice-controller.ts#L345-L352)), and `practice:setPracticeSessionQuestionMark` ([`practice-controller.ts#L425-L432`](../../../src/adapters/controllers/practice-controller.ts#L425-L432)).

The caching becomes user-visible because submit and mark clients reuse their key. Shared practice flows mint the submit key when a question loads ([`question-flow-actions.ts#L191-L194`](<../../../app/(app)/app/practice/shared/question-flow-actions.ts#L191-L194>)) and do not rotate it in either submit error branch ([`#L377-L413`](<../../../app/(app)/app/practice/shared/question-flow-actions.ts#L377-L413>)); the standalone question page has the same load-time mint and no error-path rotation ([`question-page-logic.ts#L168-L171`](<../../../app/(app)/app/questions/[slug]/question-page-logic.ts#L168-L171>), [`#L263-L288`](<../../../app/(app)/app/questions/[slug]/question-page-logic.ts#L263-L288>)). The question remains rendered in error state, and `canSubmitAnswer` blocks only `loading`, not `error` ([`practice-page-logic.ts#L34-L46`](<../../../app/(app)/app/practice/practice-page-logic.ts#L34-L46>), [`practice-view.tsx#L490-L505`](<../../../app/(app)/app/practice/components/practice-view.tsx#L490-L505>), [`#L549-L570`](<../../../app/(app)/app/practice/components/practice-view.tsx#L549-L570>)). The mark-for-review key is cleared only after success ([`use-practice-session-mark-for-review.ts#L149-L174`](<../../../app/(app)/app/practice/[sessionId]/hooks/use-practice-session-mark-for-review.ts#L149-L174>)). This is the residual [BUG-278](./bug-278-end-discard-idempotency-caches-transient-errors-under-fixed-key.md) explicitly warned about but scoped out of ("Do not reuse `shouldCachePracticeSessionStateWriteError` as-is").

## Reachability

Any signed-in entitled user submitting an answer through Quick Practice, filtered Practice, the standalone question page, a Tutor session, or a session-review retry can reach `question:submitAnswer`; active Exam navigation saves drafts and does **not** call that action. Exam mode calls submit only when the page model explicitly permits a review-question commit ([`use-practice-session-question-flow.ts#L472-L480`](<../../../app/(app)/app/practice/[sessionId]/hooks/use-practice-session-question-flow.ts#L472-L480>), [`use-practice-session-page-model.ts#L497-L504`](<../../../app/(app)/app/practice/[sessionId]/hooks/use-practice-session-page-model.ts#L497-L504>)). Mark-for-review is an Exam-session path. The server preconditions are a cache-approved execution failure and a successful `storeError` write. The clean deterministic example is a one-off `57014` cancellation that aborts the business transaction but not a later idempotency-store statement; connection loss around `COMMIT` is outcome-indeterminate and must not be described as definitely uncommitted.

## Reproduction

Submit re-click leg:

1. In Tutor mode, select a choice and click Submit. The action reaches `executeIdempotent` with the current `submitIdempotencyKey` ([question-controller.ts#L262-L270](../../../src/adapters/controllers/question-controller.ts#L262-L270)).
2. Inject a one-off `57014` in the session-state update statement so that the raw cancellation escapes the updater. It is outside the `40001`/`40P01` composition-root retry set, the outer transaction aborts, `toErrorRecord` maps the raw error to `{ code: 'INTERNAL_ERROR' }`, and the state-write policy returns `true`, so [`storeError`](../../../src/adapters/shared/with-idempotency.ts#L195-L202) persists it. A cancellation first wrapped by a repository as `ApplicationError('INTERNAL_ERROR')` reaches the same stored code.
3. The client's `!res.ok` path sets `loadState` to `error` without rotating the key ([question-flow-actions.ts#L401-L413](<../../../app/(app)/app/practice/shared/question-flow-actions.ts#L401-L413>)); the question, the user's selection, and Submit are still rendered ([practice-view.tsx#L549](<../../../app/(app)/app/practice/components/practice-view.tsx#L549>)).
4. The user clicks Submit again. The same key hits the existing record and the cached error is thrown without re-execution ([with-idempotency.ts#L308-L316](../../../src/adapters/shared/with-idempotency.ts#L308-L316)).

Expected: the retry re-executes the (now healthy) use case and the answer commits.

Actual: the cached `INTERNAL_ERROR` replays deterministically for the key's remaining TTL. On the shared practice surfaces, the ErrorCard's "Try again" reloads the question and mints a fresh key, but discards the selection; the standalone question page likewise mints on reload. The more immediate Submit re-click is broken under the old key.

Mark-for-review leg: same steps 1-2 against `practice:setPracticeSessionQuestionMark`. The hook mints its key lazily and holds it in a ref ([use-practice-session-mark-for-review.ts#L86-L90](<../../../app/(app)/app/practice/[sessionId]/hooks/use-practice-session-mark-for-review.ts#L86-L90>)), and the error path (~L138-L146) returns without clearing it — only success clears at [L172](<../../../app/(app)/app/practice/[sessionId]/hooks/use-practice-session-mark-for-review.ts#L172>). After one cached transient failure, every subsequent mark toggle in that session replays the stale error until the page is reloaded.

## Root Cause

Two halves compose:

1. **Server policy conflates terminal, rollback-certain transient, and outcome-indeterminate errors.** [`shouldCachePracticeSessionStateWriteError`](../../../src/adapters/controllers/shared/practice-session-idempotency-policy.ts#L7-L15) excludes only `StateChangedConcurrently`; a rollback-certain `57014`, an application `INTERNAL_ERROR`, and an outcome-indeterminate transport failure all reach the same cache-true branch. Contrast [`shouldCachePracticeSessionLifecycleError`](../../../src/adapters/controllers/shared/practice-session-idempotency-policy.ts#L17-L29), which is an allowlist of two typed terminal conflict reasons.
2. **Clients reuse keys after failure.** Shared and standalone submit keys rotate on question load, not submit failure; the mark key clears only after success. Cached-error replay then happens at [`with-idempotency.ts#L308-L317`](../../../src/adapters/shared/with-idempotency.ts#L308-L317).

**Not affected — refuted during verification:** `practice:finalizeExamAnswers` also uses this policy, but the end-session client rotates its key on thrown failures and on non-ok execution errors ([`practice-session-page-logic.ts#L219-L231`](<../../../app/(app)/app/practice/[sessionId]/practice-session-page-logic.ts#L219-L231>), [`#L277-L290`](<../../../app/(app)/app/practice/[sessionId]/practice-session-page-logic.ts#L277-L290>)). It deliberately preserves the key only for `ConcurrentRequestInProgress`, which is generated by the wrapper wait path and is not a cached execute error. Thus the cached failures at issue here are orphaned on finalize.

## Impact

A rollback-certain transient can become a deterministic, user-visible failure loop: Submit re-click replays stale failure instead of retrying (recoverable through question reload at the cost of the selection), and mark-for-review is blocked for the page lifetime. For a connection loss around commit, the business outcome is unknown: the answer/mark may have committed even though the cache and UI report failure. This is not evidence of destructive data corruption, but it is another reason not to equate every `INTERNAL_ERROR` with either "safe to retry" or "safe to cache." Severity remains P3 because the trigger is narrow and user recovery exists; the `storeError` statement must also succeed after the business-path failure.

## Proposed Fix

1. **RECOMMENDED — classify at the transaction owner, then cache by typed determinacy.** For a vetted rollback-certain failure such as `57014` raised by a business statement, either perform a bounded retry from a fresh transaction or map it to an explicit non-cacheable application reason; after either path, do not let it fall through as cacheable generic `INTERNAL_ERROR`. Keep terminal reasons (`AlreadyEnded`, `ExamTimeExpired`, and any separately typed monotone answer conflict) cacheable. Do not use nonexistent error codes such as `FORBIDDEN`, and do not classify from outward `INTERNAL_ERROR` alone: a connection loss around commit is indeterminate, while repository adapters can wrap several distinct causes in that same code.
2. **Close the ambiguous-outcome seam before broadening submit retries.** Unscoped attempts have no per-request uniqueness key, so a retry after an unknown commit can duplicate history. Either persist the request idempotency key with the attempt/business write or transactionally couple the idempotency outcome before treating all submit infrastructure failures as fresh-retry candidates. Mark writes express a desired state and are naturally replay-safe.
3. **Client defense in depth must follow the same determinacy rule.** Rotate submit/mark keys after determinate non-ok responses that are intentionally cached; preserve keys for thrown transport/timeouts and `ConcurrentRequestInProgress`. Once a rollback-certain server error aborts its claim, same-key retry is the intended path and needs no client rotation.
4. **Regression tests:** pin a real or driver-shaped `57014` rollback followed by a same-key successful retry for submit and mark, pin that cached terminal conflicts still replay, and pin the chosen behavior for an outcome-indeterminate failure. Preserve finalize's `ConcurrentRequestInProgress` no-rotation test.

Corrections folded in from adversarial verification (not fix options, but scope boundaries): active Exam draft navigation does not call `question:submitAnswer`; the affected submit clients are Quick/filtered Practice, standalone questions, Tutor sessions, and session-review commits. The `finalizeExamAnswers` leg is refuted as described above, and "stuck until page reload" is overstated for shared practice submit because the ErrorCard reload path recovers at the cost of the selection. The reachable defect is same-key Submit replay plus the page-lifetime mark-toggle failure.
