## How Records Work

- **When to file.** File a bug or debt record for a defect, an existing engineering liability, or an investigation that spans more than one pull request or needs an independent challenge before code. New feature work is specified in [product documents](../product/README.md), even when it spans several PRs; duration alone does not make a feature debt. A proven fix that lands in one pull request may use that PR's description as its record, with the same sections, unless a check outlives the PR: then it needs a record, so the weekly due check sees it.
- **Write first, challenge on the branch.** Commit the record first on the work branch and push the branch. A second agent challenges it there. An exploitable security finding takes precedence over the push-first rule: keep its write-up, branch history, repro and challenge private until the fix is deployed and the owner approves disclosure. A public draft PR is public too. Coordinate private review and release with the owner; this does not authorize bypassing a gate.
- **Edit in place.** When understanding changes, rewrite the text and add a one-line `Corrected YYYY-MM-DD: what changed` note, rather than appending dated sections. Keep receipts short: the pull requests, the promotion and each check's outcome. Run IDs and SHAs go in pull-request descriptions.
- **IDs.** `pnpm exec tsx scripts/next-record-id.ts bug` (or `debt`) prints the next free ID from these records and the ledger. This is a candidate, not a reservation. Two branches can receive the same ID. Before merging, integrate the latest target branch and run the guard; the second branch renumbers its file, heading, index row and citations together. Never renumber an already merged record.
- **Ship it with its fix.** The record and its fix go up in one pull request, so one review covers both.
- **Statuses.** Open, In Progress, Blocked (needs an action outside the repository), or `Verifying — <the remaining check>; due YYYY-MM-DD`. Open, In Progress and Blocked may add the next action after a dash, as `Open — <next action>`, which is where a `due` date goes. A record is Verifying when its fix has merged and a check remains that only promotion or production can satisfy; the fixing PR sets that status effective on merge. Before merge the PR and its checks are the evidence, not a claim that production is fixed. The status is one line of at most 200 characters; detail goes in the body. Priorities: P0 broken, data lost or a security hole open; P1 major function broken; P2 degraded with a workaround; P3 minor; P4 trivial.
- **Due checks and queue review.** The weekly job maintains one aggregate issue for dated actions in any live status, including Verifying checks, plus the queue review date above. A status can schedule an action with `due YYYY-MM-DD`; a conditional deadline alone is not machine-readable. GitHub runs the schedule from the default branch, so promotion is required for new rules and records to reach that schedule. Start a session with Now and the Waiting triggers relevant to its work. Triage overdue work, perform checks within the session’s authority, and leave a named next action when blocked; an owner-only decision does not authorize an unrelated session to act.
- **Weekly human review.** The repository owner or their assigned session evaluates every Waiting trigger and pending owner decision, using the trigger’s named evidence source; records which fired, which remain false, and which could not be checked in the review PR description; promotes fired work to Active and names it in Now; then advances `Queue review due` by at most seven days from that review. A trigger needing external data that cannot be checked becomes a Blocked record with a dated follow-up. Do not silently extend dates or treat the weekly job as evaluating prose triggers. New Waiting rows name the observable trigger and where to check it; owner-dependent work names the decision and decision maker.
- **Tracking.** A bug in shipped code stays open until its fix is promoted and any production proof is recorded. A branch-local defect still needs red-first proof, review and CI, and its record says it was branch-local.
- **Evidence.** A fix that deletes a pattern lands with the guard that keeps it deleted, and a guard lands with a red test for the state it rejects. A scheduled-only proof is not claimed until a hosted run has executed it.
- **Audits.** A sweep files each confirmed finding that needs a record by the rule above as its own record, with links to its independent fix PRs. It does not create a second audit register. Its method and coverage go in the pull request's description. A candidate found invalid closes with the source-level reason it cannot happen.
- **Links.** Only this index links records. Elsewhere, cite a record by its ID: look up an open ID in this index and a closed ID in the ledger. The guard rejects a link into the deleted archive unless it pins a commit, as the ledger's header does. A path link would break when the record closes. A code comment keeps the lasting reason beside the code; an ID alone is not the explanation. Never invent a replacement for a deleted link target just to turn the guard green: find where the content went, or cite the ID. Owner-adopted legal and security text keeps its links until the owner revises it; arrange that revision before closing a record it links, rather than leaving a broken policy link.
- **Closing.** Once the last check is recorded, the next pull request that touches this folder:
  1. moves lasting knowledge home: a rule to `AGENTS.md` or `.claude/rules/`, a decision to an ADR, a reason to a code comment, and an unfinished tail to a Waiting row with its trigger;
  2. verifies each unfinished item is complete, explicitly declined by its decision maker, or preserved with a trigger and acceptance criteria in Waiting; then deletes the record and any asset folder;
  3. adds its ledger line in ID order: `ID · title · disposition · date · path · #PR · commit`, the full 40-character commit being a reachable commit that held the final record. Before deletion, verify `git show <commit>:<path>` retrieves its final evidence and that the commit will remain reachable after the merge. Verify the closing PR is real. The guard checks receipt shape, not GitHub existence or the meaning of the evidence. The disposition is Resolved, Won't Fix, Invalidated, Superseded, Reclassified, Accepted or Decomposed, as the record shows; never relabel an invalidated record as fixed;
  4. removes its row, and updates Now.
- **Assets.** Records get no asset folders: screenshots and receipts go on the pull request. DEBT-414's folder, `assets/debt-414/`, predates this rule and goes when it closes.
