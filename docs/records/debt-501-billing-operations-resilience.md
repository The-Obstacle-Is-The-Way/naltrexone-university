# DEBT-501: Billing Operations Can Leave Payers Without Access as the Service Grows or Changes

**Status:** Resolved — every check recorded 2026-11-28; items 1, 2 and 3 move to Waiting
**Priority:** P2
**Date:** 2026-10-05

## Summary

The owner-requested adversarial hunt of the payment flows (2026-10-05) found no defect that charges an ordinary Checkout buyer without granting access. It did find gaps in billing operations. Each can leave a payer without access, or charge someone twice, when the service grows, an operator changes something, or timing is unlucky. Each item names its trigger. One live purchase, the owner's on 2026-11-24, is recorded working end to end (item 7).

### 1. The daily reconcile never reaches the tail once the table grows (P2) — waits for its trigger

- **Evidence.** The all-pages sweep starts at offset 0 on every run (`src/adapters/jobs/reconcile-all-stripe-subscription-pages.ts:132`) and stops after a 40-second budget (`:13`). It logs "resume at offset N", but the cron passes no offset (`app/api/cron/reconcile-stripe-subscriptions/route-handler.ts:232-233`). Rows are never removed. A stopped-early run that overruns `maxDuration = 60` also kills the deleted-account cleanup after it (BUG-262's safety net).
- **Trigger.** The cron raises `stripe_reconcile_stopped_early` (built 2026-10-10), an estimated 500 to 1,000 rows from now. Item 9 makes sure the cron runs at all.
- **Decided: oldest-first order, no cursor.**
  - Record each row's last attempt and process rows oldest first by `coalesce(last_attempted_at, created_at)`, then ID. Claim each row before its Stripe call with one committed `update … set last_attempted_at = clock_timestamp() where id = $1 and coalesce(last_attempted_at, created_at) < $start returning id`; skip a row whose claim returns nothing. Claims change neither `version` nor `updated_at`.
  - `$start` is read from the same database clock before the first page. The claim uses `clock_timestamp()`, not `now()`, because `now()` is when its transaction began and can precede the run's start.
  - A row whose claim fails is left out of the run's remaining pages. Record the outcome or error after the Stripe call, so a row that keeps failing moves to the back instead of starving the tail.
  - Once a run no longer reaches every row, a failing row moved to the back sits out the runs between its attempts, so it can never fail in three finished runs in a row, which item 9's `stripe_reconcile_row_failing` counts. Keep a count of each row's consecutive failed attempts with its recorded outcome (a success resets it; a run that skips the row leaves it), and raise the kind from that count instead.
  - One run at a time: a run holds a Postgres advisory lock for its whole length, and a run that cannot take it exits without claiming or canceling anything, so two runs never claim the same row or cancel each other's choices. Item 9's start is recorded only once the lock is held, so an overlapping run that exits raises no `stripe_reconcile_stopped`; a test shows that, and that a killed lock holder still raises it.
  - Each page reads afresh from the head of that order, taking only rows earlier than the run's start, so no row is attempted twice in a run. Remove the `offset` parameter; `scope=page` takes the next `limit` rows.
  - Check time before each claim, and reserve a cleanup budget inside `maxDuration`. Bound the drain's customer deletes and their retries to the remaining cleanup time. Prove that slow reconciliation cannot consume cleanup's reserved time; separate `try` blocks alone do not.
  - Keep terminal rows: repairing stale local state is the job's purpose. Any pruning policy needs an independently justified terminal-state contract.
  - Before shipping, specify discovery for customers with no local subscription row, which the local-row scan cannot reach (`src/adapters/jobs/reconcile-stripe-subscriptions.ts:70`), and name the residual for absent customer mappings. Do not mark coverage complete from a local-row scan.
  - Tests against real Postgres: the order, a crash mid-run, interleaved and sustained inserts, at most one attempt per row per run (including a claim written in a transaction begun before the run's start was read), a concurrently claimed or deleted row, a failed claim, the budget, two overlapping runs (the second exits without claiming), provider failure, and a row whose three failed attempts have runs that skip it between them, which still raises `stripe_reconcile_row_failing`.

### 2. Only one price ID per plan is recognized (P2) — waits for its trigger

- **Evidence.** `getSubscriptionPlanFromPriceId` matches only the current environment's monthly and annual IDs (`src/adapters/config/stripe-prices.ts:15-22`). Any other ID fails: webhooks return 500 (`stripe-subscription-normalizer.ts:100-105`), reads throw `INTERNAL_ERROR` (`drizzle-subscription-repository.ts:44-51`), as in DEBT-310's incident, reconcile rows fail, and the success page redirects with `unknown_plan`. The renewal job also selects subscribers by today's price IDs and states today's configured amounts (`src/adapters/jobs/send-due-renewal-notices.ts:77`, `:208`, `:280`, `:449`, `:618`), so after a price change existing subscribers would get no notice, or one stating the wrong amount.
- **Who it locks out today.** Production already holds subscription rows: by the owner's account (2026-10-13), real people took live trials, and a row is removed only with its user (`db/schema.ts:230-232`). A changed price ID would make every read of those rows throw and the reconcile fail them. The price-ID rule in `docs/architecture/environments.md` (done 2026-10-09) is the only guard, and it is in force.
- **Moved to Waiting** by the owner, 2026-11-15, and removed from the pre-sale list. Trigger: a change of either price ID is planned, in any environment; the rule forbids making it first. Item 7's live purchase confirms that today's live Prices charge what the consent text states.
- **Decided 2026-10-10: a subscription's plan is a recorded fact.**
  1. When the webhook, the reconcile or the success sync learns of a subscription, take the plan from Stripe's Price (accepted only for our product, and only as a flat fee: `recurring.interval` `month` or `year` with `interval_count` 1, `recurring.usage_type` `licensed`, and `billing_scheme` `per_unit` with a `unit_amount` and no `transform_quantity`, as the subscription's only item, with quantity 1) and store plan, amount and currency, in nullable columns filled by every write and by the reconcile. Reads fall back to today's mapping until production has no empty row; a second migration then makes them required and removes the fallback.
  2. Reads use the stored plan. Only Checkout creation reads the configured price IDs.
  3. Renewal notices and reminders select by stored plan, and state the stored amount and currency.
  4. An unknown product, or a subscription or Price step 1 does not accept, refuses the write, leaves the event retryable, and raises an unknown-price alert through DEBT-505's path. Open for this design, settled before it ships: refusing a change to a stored subscription, such as its quantity raised to 2, leaves its stored terms and status, so a notice could state terms Stripe no longer charges, and refusing its cancellation leaves access until the stored period ends. The design must keep such a subscription's notices from stating the stored terms, and must record a cancellation of the stored subscription, under the shared contract's fence, while still refusing its terms and raising the alert.
  5. Checkout refuses a configured price that step 1 would not accept, or whose Stripe amount, currency or interval differs from `lib/pricing-data.ts`, and alerts (currency, and `interval_count` here and in step 1, added by the owner, 2026-11-19; `usage_type` in both, added by the owner, 2026-11-20, since a metered Price charges its amount per unit of usage; step 1's whole check, product included, added by the owner, 2026-11-21, so a buyer is not charged for a subscription step 4 would refuse; `billing_scheme` `per_unit` with a `unit_amount`, added 2026-11-21 under the owner's flat-fee choice, so step 1 always stores, and step 3 always states, the Price's own amount: a tiered Price has none; no `transform_quantity` here and in step 1, and in step 1 one item with quantity 1, which Checkout always sends (`src/adapters/gateways/stripe/stripe-checkout-sessions.ts:1368`), added 2026-11-21 under the same choice, since each can change what Stripe charges).

### 3. A subscription created outside the app's Checkout is acknowledged and dropped (P3) — waits for its trigger

- **Evidence.** The normalizer requires `subscription.metadata.user_id` (`stripe-subscription-normalizer.ts:38-52`). The controller logs `metadata_missing` and returns 200 without recording the event (`stripe-webhook-controller.ts:830-840`).
- **Trigger.** Support or the owner plans to create a subscription in the Dashboard, a Payment Link or a script, for example to repair "I paid but can't get in".
- **Decided.** Fall back only to the trusted `stripe_customers` mapping, with agreement checks when subscription metadata is present; customer metadata is not an ownership authority. Persist an unresolved outcome in the event ledger with a retry or operator disposition. Prove missing, conflicting and repaired mappings through signed-webhook integration cases.

### 4. A card added at or after trial end is never applied (P3) — expiry bound declined

- **Shipped with BUG-364.** Completion of an add-card Session checks the stored subscription before calling Stripe and again when recording consent (`checkSetupSubscription`, `src/adapters/controllers/stripe-webhook-controller.ts:246-278`). A trial whose stored row is no longer entitled ends the setup as `subscription_inactive`: the card is detached, and no consent or acknowledgment is recorded. Billing's return notice reads the stored row, not the detach: it says the card was not saved while an in-trial cancellation is scheduled, and otherwise that Stripe is confirming the card (`app/(app)/app/billing/page.tsx:183-198`, `:286-287`).
- **The gap left.** The add-card Session still uses Stripe's 24-hour default (`createStripeTrialPaymentMethodSetupSession`, `src/adapters/gateways/stripe/stripe-checkout-sessions.ts:254-300`, no `expires_at`). A completion processed after Stripe canceled the trial but before the cancellation webhook updates the stored row passes the check, attaches the card (controller `:364-377`), and then fails to set it as the subscription's default (`:387-398`, through `src/adapters/gateways/stripe-payment-gateway.ts:232-249`), since Stripe allows only metadata and cancellation details to change on a canceled subscription. The delivery fails until the cancellation webhook is processed; then the check ends it as `subscription_inactive`. No provider test covers this path.
- **Declined** by the reviewing session, 2026-11-15, at the owner's delegation: the expiry bound (the earlier of trial end and 24 hours). Its outcome holds once the setup's completion is processed: that path detaches the card, and nothing is charged, since the trial is no longer entitled. Until then the card stays attached to a trial that will not charge it.

### 9. Nothing notices when the daily reconcile stops running (P3)

- **Evidence.** The renewal job checks in with Sentry's cron monitor, and the watcher opens an issue when it misses 25 hours. The reconcile route has no monitor, and its one alert comes only from a run. A firewall rule or failed deployment can stop a run before the handler, and a `CRON_SECRET` mismatch answers 401; each leaves an hour of Vercel logs and no record.
- **Impact.** Webhooks still sync each subscription, so this is the repair path going quiet: drift and BUG-343's duplicate cancellation stop without a signal.
- **Decided 2026-10-30: option 2.** Each scheduled full run (`dryRun=false&scope=all`, the cron's own query) records its start, once `CRON_SECRET` passes, and its finish once reconciliation returns with at least one row that did not fail, or with no rows (the result's `scanned` and `failed`, `src/adapters/jobs/reconcile-all-stripe-subscription-pages.ts:180-182`). So a run whose reconciliation throws (the route answers 500, `app/api/cron/reconcile-stripe-subscriptions/route-handler.ts:239-247`, `:289-294`) or in which every row failed (the route still answers 200, `:296-299`, so a run whose every Stripe lookup failed would otherwise look finished) is reported like a killed one: in each, the repair path repaired nothing. A run in which only some rows failed records its finish, so one customer that fails every day does not raise `stripe_reconcile_stopped` while the job works for everyone else; its row is logged as "Stripe subscription reconciliation failed" and retried by the next run, and a duplicate already detected on it still raises `stripe_duplicate_subscription`. A row whose Stripe listing fails never reaches duplicate detection (`hadDuplicates` is set only after the listing, `src/adapters/jobs/reconcile-stripe-subscriptions.ts:122`, `:237`), so it could hide a duplicate; each finish therefore also stores its failed rows' subscription IDs (the result's `failures`), and the watch raises a second new kind, `stripe_reconcile_row_failing`, when one subscription failed in each of the last three finished runs (both rules the reviewing session's, 2026-11-18, at the owner's delegation); a diagnostic dry or single-page run records neither, so it cannot mask a stopped one. The monitored renewal job raises a new kind, `stripe_reconcile_stopped`, as it already watches GitHub's schedules (`checkScheduledChecksRunning`, `src/adapters/jobs/scheduled-checks.ts:117`), when no run has started in the past 24 hours, or any run started more than the route's `maxDuration` (60 seconds, `app/api/cron/reconcile-stripe-subscriptions/route.ts:16`) ago has no finish recorded and has not been reported yet; an alert that resolves `sent` marks those runs reported, while `suppressed` or `failed` leaves them for the next watch (`OperationalAlertOutcome`, `src/application/ports/operational-alerts.ts:63`; start, finish and report sit on one row per run). Every unreported start is checked, not only the latest or a fixed window: Hobby fires each cron anywhere in its hour, so the 08:00 reconcile can still be running when the 09:00 watch reads it, and a later watch then catches it if it was killed, even when a later run succeeded or a day's watch was missed. Its red-first tests cover a killed run, a run whose reconciliation throws, a run in which every row failed, a run in which only some failed, which records its finish, one subscription failing in three finished runs in a row, which raises `stripe_reconcile_row_failing`, and in two, which does not, a killed run first seen after a missed watch, and a suppressed or failed alert, which leaves its runs unreported. Option 1, a second Sentry cron monitor, needs a paid Sentry plan.
- **Rejected** by the reviewing session, 2026-11-15: reading the start from the cron's rate-limiter row. It gives the limiter's table a second meaning that a limiter change could silently break, and it cannot see a killed run.
- **Built in #1742** and promoted in #1744, as decided.
  - **The code.** Migration 0056 adds `stripe_reconcile_runs`. The route records the runs. `src/adapters/jobs/stripe-reconcile-watch.ts` is the renewal job's watch.
  - **Two decided rules, applied as written.** The 24-hour window reports a missed day on that same day. The 60 seconds is the route's `maxDuration`, pinned by `tests/stripe-reconcile-route-max-duration.test.ts`.
  - **What the independent review found.** A rejected page's `(page@offset=…)` marker counts in `failed` but not in `scanned`. So the finish compares only the failed rows with the rows scanned, and stores only Stripe subscription IDs. Each of the watch's steps also fails on its own.
  - **Red-first tests.** Every scenario listed above has one. The store's fake and Postgres share one contract.
  - **Two accepted edges** (`docs/architecture/observability.md`). A release promoted between 08:00 and 10:00 UTC can send one false stop, because the table is still empty. A start recorded in the first seconds after 09:00 UTC, read by a watch in those same seconds, can be reported as a stop.
  - **Production.** Live since 2026-11-25 03:43Z. The first watch ran at 09:54Z that day: the renewal job's Sentry monitor checked in, and the server project shows neither alert. The run row itself was not read. A store read failure, which the watch only logs, is therefore not excluded, and Hobby keeps runtime logs for one hour (DEBT-512).
