# BUG-343: A Second Checkout Can Leave a Hidden Second Subscription

**Status:** Open — build option 9 red first; an agent re-runs the TEST-mode reproduction on released code; the owner checks the Dashboard in the pre-sale Stripe session; due 2026-11-22
**Priority:** P2
**Date:** 2026-10-13

---

## Summary

One user could end up with two live Stripe subscriptions. One Checkout page was completed while another tab's checkout request was still running; that request then handed back a second page, completable for up to 24 hours. The app kept one subscription and reported nothing about the other.

Options 2, 3, 5 and 6 shipped on 2026-10-14: #1492, #1494 and #1496, promoted by #1493, #1495 and #1497 the same day. A checkout now re-checks the customer's subscriptions before handing back a Session, and a completed Checkout ends the customer's other open subscription Sessions created before its event, once this environment has stored the user's subscription (R25). What remains needs two open pages for one customer, which the code can leave, as reproduced on 2026-11-18 (Evidence): a request that fails after creating its page while another is open leaves its page open, and a later request for the same plan and terms hands it back without expiring the other. If both pages are completed before the first completion's webhook sweeps the other, the customer has two subscriptions. The sweep runs from the first completion's webhook, so the window is seconds when that webhook arrives and its sweep succeeds, and lasts while Stripe delays or redelivers it, up to the open page's 24-hour expiry. The daily reconcile cancels such a duplicate, without a refund, and raises `stripe_duplicate_subscription`; the owner refunds by hand. Option 9, decided 2026-11-18, has every request expire the customer's other open pages it finds before handing one back; automatic refunds stay declined.

## Evidence

- **The race,** reproduced in Stripe TEST mode on 2026-10-14 with the real adapter: two `trialing` subscriptions for a first checkout, and two `active` paid subscriptions, $58 in all, for a returning customer. Stripe did not redirect the second page, and its refusal to expire a completed Session matched none of the adapter's terminal patterns.
- **Stripe's "limit customers to one subscription" setting** is a redirect for a customer who already holds an `active`, `past_due`, `unpaid` or `paused` subscription, not `trialing`, and Stripe describes no check at completion ([Stripe: limit customers to one subscription](https://docs.stripe.com/payments/checkout/limit-subscriptions.md?payment-ui=stripe-hosted)). It cannot stop the residual, where both pages load before either completes.
- **The existing correction.** The daily reconcile, at 08:00 UTC (`vercel.json:11-12`), lists each customer's subscriptions, `trialing` included, and cancels all but the canonical one with `subscriptions.cancel` and no options (`src/adapters/jobs/reconcile-stripe-subscriptions.ts:309-316`). It marks consent terminated only for the canonical subscription (`:287`). Nothing yet notices if the reconcile stops running: that watch is DEBT-501 item 9, not yet built.
- **What Stripe's cancel does** ([Stripe: cancel a subscription](https://docs.stripe.com/api/subscriptions/cancel)). It credits and refunds nothing. And "by default, upon subscription cancellation, Stripe stops automatic collection of all finalized invoices for the customer", which "you can resume … manually". The reconcile's cancel passes no option that changes this, so canceling the duplicate can stop collection of a finalized, unpaid invoice on the kept subscription too.

- **How two open pages arise,** reproduced on 2026-11-18 against `FakeStripeCheckoutClient` with its expire and retrieve faults (the probe was not kept). The post-create reconcile expires the customer's other open Sessions; when an expire fails, it fails the request with `STRIPE_ERROR` (`src/adapters/gateways/stripe/stripe-checkout-sessions.ts:650-662`, called at `:1517-1526`) and leaves the request's own new Session open. A later request lists one open Session (`limit: 1`, `:1166-1176`) and, for the same plan and terms, hands it back after the subscription re-check (`:1219-1239`), without listing or expiring the others. Two cases reproduced it, each ending with a same-plan retry that handed back the new page while the earlier page stayed open:
  - a trial checkout whose read and expire of the earlier page failed, so it created its page under a recovery key (`:1201-1208`, `:1299-1307`), then failed again to expire the earlier page;
  - an annual checkout racing a monthly one: the monthly request handed back its page, and the annual request, whose listing before its create found no open page, failed to expire the monthly page.

  A paid checkout for the same plan and terms replays the earlier page instead: its idempotency key is the user and plan (`fallbackCheckoutSessionIdempotencyKey`, `:548-552`), and the first probe, run without a trial, got the earlier page back.

## Impact

- **The residual.** Two open Checkout pages, which a failed request can leave (Evidence), both completed before the first completion's webhook sweeps the other: seconds when that webhook arrives and its sweep succeeds, longer while Stripe delays or redelivers it, up to the open page's 24-hour expiry. A first-time customer gets two trials, one of which the reconcile cancels within about 25 hours at no charge. A returning customer is charged twice until the owner refunds by hand on the alert.
- **"Within about 25 hours":** the reconcile is scheduled at 08:00 UTC and Hobby starts it anywhere in that hour, so two runs can start nearly 25 hours apart, plus the run's own time. It holds only while the reconcile runs, its run reaches the customer (a run stopped by its time budget or page cap raises `stripe_reconcile_stopped_early`) and that customer's row succeeds (a row whose Stripe lookup, write or cancel fails is logged as "Stripe subscription reconciliation failed" and left to the next run, `src/adapters/jobs/reconcile-stripe-subscriptions.ts:363-379`), and only for a customer with a local subscription row: the reconcile starts from those rows and lists each one's customer, so it finds a duplicate that has no row of its own, but not a customer the webhook stored nothing for (DEBT-501 item 1). Until DEBT-501 item 9 is built, a reconcile that stops running stops this correction without a signal. The hand refund also needs `stripe_duplicate_subscription` to reach the owner, which BUG-377's next drill proves. So DEBT-501 item 9 must ship before the first live sale, and BUG-377 must be verified.
- **A hidden trial the reconcile has not yet canceled** ends at its trial end without a charge, since it has no payment method, unless a card becomes the customer's default. The app's trial portal profile disables card updates (`src/adapters/gateways/stripe/stripe-portal-configurations.ts:34`), but the Dashboard's login-link portal uses its own configuration, so a card added there could become the default and convert the hidden trial. That is unverified; the owner's Dashboard check below settles it.
- **The hidden subscription's consent record** stays unterminated after the reconcile cancels it. No notice depends on it, since notices select by the one stored row.
- **Likelihood:** low. The product is pre-revenue; the first exposure is the first paid checkout.

## Options

Shipped: 2 (re-check before handing back a Session), 3 (sweep on completion), 5 (alerts) and 6 (the fake refuses to expire a Session that is not open). Decided, not built: 9 (one exit for every Session handed back, in the Resolution). Declined:

- **Option 4: correct a duplicate within seconds.** On `customer.subscription.created`, cancel the second-ranked live subscription, refund its charge, mark its consent terminated and keep collecting the kept subscription's invoices. It adds a webhook handler, a refund gateway method with its fake and contract scenario, and real-Stripe and Postgres proofs.
- **Option 4a: refund in the reconcile's existing cancel.** A keyed refund of the duplicate's paid invoice beside the reconcile's cancel, which must also resume collection of the kept subscription's invoices. No new handler; the correction still takes up to about 25 hours.
- **Option 7: shorten Session lifetime** with `expires_at`, to as little as 30 minutes. It caps the tail only while the completion webhook is delayed or failing; once it arrives, option 3's sweep ends the other pages.
- **Option 8: make the app the only writer of subscriptions.** Closes the race completely, but changes the purchase page, disclosures and consent.

## Resolution (decided)

Options 2, 3, 5 and 6, decided 2026-10-14, each for the case the one before cannot close. Rules R24 and R25 state options 2 and 3.

- **Option 9: one exit for every Session handed back,** decided by the owner, 2026-11-18. The reuse path (`:1219-1239`) runs the same post-create reconcile and re-check as the create path (`:1517-1534`) on the Session it found. Both of the adapter's exits (`:1239`, `:1543`) then hand back only the newest open subscription Session the request's listing found (up to `OPEN_CHECKOUT_SESSION_RECONCILE_LIMIT`, 10), after expiring the others, and a failed expire still fails the request. A Session created after that listing can stay open, but only a later request that expires the older ones hands it back. So at most one Session handed back is open at a time while each listing returns every open Session the customer has; with more than 10 open, one can be handed back beside an older one. A concurrent create can also expire the Session a request is about to hand back, as on the create path today: that link no longer completes, and the buyer starts checkout again. No check before the return closes that window, since the expire can land after it. No lock is added: the adapter holds no database lock across Stripe calls, on purpose (BUG-245, `:671-672`). The reuse path gains one listing, and an expire for each other open Session. Red first in the adapter's checkout tests with `FakeStripeCheckoutClient`'s `setExpireFault` and `setRetrieveOverride`: both reproductions in Evidence end with one open subscription Session after the retry, and a reuse that hands back a Session while a concurrent create fails to expire it leaves the create's Session open and unreturned until a later request expires the first. Its own code pull request.
- **Automatic refunds (options 4 and 4a): declined** by the owner, 2026-11-15, and re-confirmed on 2026-11-18 with the wider window and option 9 stated. On `stripe_duplicate_subscription`, the owner refunds the duplicate by hand in Stripe's Dashboard, cancels it if the reconcile has not (the duplicate is the one the reconcile does not keep, as the runbook row says), and checks that the kept subscription's open invoices still collect, resuming automatic collection on any the cancel stopped. When this record closes, it leaves a Waiting row that revisits option 4a the first time a charged duplicate happens in production.
- **Option 7: declined** by the reviewing session, 2026-11-15, at the owner's delegation. It helps only while our webhook is failing and a second page is completed in that time, the daily reconcile cancels the duplicate either way, and a short lifetime also expires pages people are still filling in. *Corrected 2026-11-17: the first reason, that option 3's sweep ends the tail, missed a delayed webhook.* Option 8 is not taken.
- **The hold on inviting former trial users back** "until the fix ships" was lifted by its own condition on 2026-10-14, when #1493 and #1495 released options 2 and 3.
- **The Dashboard checks are kept** (reviewing session, 2026-11-15), in the owner's pre-sale Stripe session: in live and test mode, whether "limit customers to one subscription" is on with the portal's login link enabled; which portal configuration that link uses, and whether a card added there becomes the customer's default; and whether the former live trials ended `canceled` with no payment method. Keep the setting on, as `docs/architecture/integrations/stripe.md` says.
