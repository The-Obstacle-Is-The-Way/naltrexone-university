# BUG-343: A Second Checkout Can Leave a Hidden Second Subscription

**Status:** Verifying — an agent re-runs the TEST-mode reproduction on released code, once BUG-380's fix lets the helpers complete Stripe's page; due 2026-12-09
**Priority:** P2
**Date:** 2026-10-13

---

## Summary

One user could end up with two live Stripe subscriptions. One Checkout page was completed while another tab's checkout request was still running; that request then handed back a second page, completable for up to 24 hours. The app kept one subscription and reported nothing about the other.

Options 2, 3, 5 and 6 shipped on 2026-10-14: #1492, #1494 and #1496, promoted by #1493, #1495 and #1497 the same day. A checkout now re-checks the customer's subscriptions before handing back a Session, and a completed Checkout ends the customer's other open subscription Sessions created before its event, once this environment has stored the user's subscription (R25). That left one way to two open pages handed to one customer, reproduced on 2026-11-18 (Evidence): a request that failed after creating its page while another was open left its page open, and a later request for the same plan and terms handed it back without expiring the other. If both pages were completed before the first completion's webhook swept the other, the customer had two subscriptions. Option 9, decided 2026-11-18 and built on 2026-11-25 (R32), closes that way: every request expires the customer's other open pages it lists before handing one back. A page a failed request leaves open stays open, handed to no one, until a later request hands it back after expiring the older ones, or a later request or the sweep ends it. What remains is in Impact. The sweep runs from the first completion's webhook, so a second open page stays completable for seconds when that webhook arrives and its sweep succeeds, and for as long as Stripe delays or redelivers it, up to the page's 24-hour expiry. The daily reconcile cancels a duplicate subscription, without a refund, and raises `stripe_duplicate_subscription`; the owner refunds by hand. Automatic refunds stay declined.

## Evidence

- **The race,** reproduced in Stripe TEST mode on 2026-10-14 with the real adapter: two `trialing` subscriptions for a first checkout, and two `active` paid subscriptions, $58 in all, for a returning customer. Stripe did not redirect the second page, and its refusal to expire a completed Session matched none of the adapter's terminal patterns.
- **Stripe's "limit customers to one subscription" setting** is a redirect for a customer who already holds an `active`, `past_due`, `unpaid` or `paused` subscription, not `trialing`, and Stripe describes no check at completion ([Stripe: limit customers to one subscription](https://docs.stripe.com/payments/checkout/limit-subscriptions.md?payment-ui=stripe-hosted)). It cannot stop the residual, where both pages load before either completes.
- **The existing correction.** The daily reconcile, at 08:00 UTC (`vercel.json:11-12`), lists each customer's 100 newest subscriptions (one page, `src/adapters/jobs/reconcile-stripe-subscriptions.ts:21`, `:121-130`), `trialing` included, and cancels all but the canonical one with `subscriptions.cancel` and no parameters, only an idempotency key (`src/adapters/jobs/reconcile-stripe-subscriptions.ts:309-316`). It marks consent terminated only for the canonical subscription (`:287`). DEBT-501 item 9's watch, live since 2026-11-25, raises `stripe_reconcile_stopped` if the reconcile stops running.
- **What Stripe's cancel does** ([Stripe: cancel a subscription](https://docs.stripe.com/api/subscriptions/cancel)). It credits and refunds nothing. And "by default, upon subscription cancellation, Stripe stops automatic collection of all finalized invoices for the customer", which "you can resume … manually". The reconcile's cancel passes no option that changes this, so canceling the duplicate can stop collection of a finalized, unpaid invoice on the kept subscription too.

- **How two open pages were handed back,** reproduced on 2026-11-18 against `FakeStripeCheckoutClient` with its expire and retrieve faults, and again on 2026-11-25 as the first two cases of `stripe-checkout-sessions-one-exit.test.ts`, which failed before option 9. The line numbers in this bullet are the adapter's at `13c7ba0d`, before that fix. The post-create reconcile expired the customer's other open Sessions; when an expire failed, it failed the request with `STRIPE_ERROR` (`src/adapters/gateways/stripe/stripe-checkout-sessions.ts:650-662`, called at `:1517-1526`) and left the request's own new Session open, as it still does. A later request listed one open Session (`limit: 1`, `:1166-1176`) and, for the same plan and terms, handed it back after the subscription re-check (`:1219-1239`), without listing or expiring the others. Two cases reproduced it, each ending with a same-plan retry that handed back the new page while the earlier page stayed open:
  - a trial checkout whose read and expire of the earlier page failed, so it created its page under a recovery key (`:1201-1208`, `:1299-1307`), then failed again to expire the earlier page;
  - an annual checkout racing a monthly one: the monthly request handed back its page, and the annual request, whose listing before its create found no open page, failed to expire the monthly page.

  A paid checkout for the same plan and terms replays the earlier page instead: its idempotency key is the user and plan (`fallbackCheckoutSessionIdempotencyKey`, `:548-552`), and the first probe, run without a trial, got the earlier page back.

## Impact

- **The residual, after option 9.** Two open Checkout pages, both handed back, and both completed before the first completion's webhook sweeps the other: seconds when that webhook arrives and its sweep succeeds, longer while Stripe delays or redelivers it, up to the open page's 24-hour expiry. Option 9 hands a page back only after expiring the other open pages its listing returns, so two can be handed back and open together only when a listing does not return every open page the customer has: it reads ten. A first-time customer gets two trials, one of which the reconcile cancels within about 25 hours at no charge. A returning customer is charged twice until the owner refunds by hand on the alert.
- **"Within about 25 hours":** the reconcile is scheduled at 08:00 UTC and Hobby starts it anywhere in that hour, so two runs can start nearly 25 hours apart, plus the run's own time. It holds only while the reconcile runs, its run reaches the customer (a run stopped by its time budget or page cap raises `stripe_reconcile_stopped_early`) and that customer's row succeeds (a row whose Stripe lookup, write or cancel fails is logged as "Stripe subscription reconciliation failed" and left to the next run, `src/adapters/jobs/reconcile-stripe-subscriptions.ts:363-379`), with the duplicates among the customer's 100 newest subscriptions, and only for a customer with a local subscription row: the reconcile starts from those rows and lists each one's customer, so it finds a duplicate that has no row of its own, but not a customer the webhook stored nothing for (DEBT-501 item 1). Since 2026-11-25, DEBT-501 item 9's watch raises `stripe_reconcile_stopped` when the reconcile stops running. The hand refund also needs `stripe_duplicate_subscription` to reach the owner, which BUG-377's next drill proves, so BUG-377 must be verified before the first live sale.
- **A hidden trial the reconcile has not yet canceled** ends at its trial end without a charge, since it has no payment method, unless a card becomes the customer's default. The app's trial portal profile disables card updates (`src/adapters/gateways/stripe/stripe-portal-configurations.ts:34`), but the Dashboard's login-link portal uses its own configuration, so a card added there could become the default and convert the hidden trial. That is unverified; the owner's Dashboard check below settles it. *Settled 2026-11-25 (BUG-384): that configuration's payment-method updates have been off since that day, so no card can be added there.*
- **The hidden subscription's consent record** stays unterminated after the reconcile cancels it. No notice depends on it, since notices select by the one stored row.
- **Likelihood:** low. The product is pre-revenue; the first exposure is the first paid checkout.

## Options

Shipped: 2 (re-check before handing back a Session), 3 (sweep on completion), 5 (alerts) and 6 (the fake refuses to expire a Session that is not open). Built on 2026-11-25: 9 (one exit for every Session handed back, in the Resolution). Declined:

- **Option 4: correct a duplicate within seconds.** On `customer.subscription.created`, cancel the second-ranked live subscription, refund its charge, mark its consent terminated and keep collecting the kept subscription's invoices. It adds a webhook handler, a refund gateway method with its fake and contract scenario, and real-Stripe and Postgres proofs.
- **Option 4a: refund in the reconcile's existing cancel.** A keyed refund of the duplicate's paid invoice beside the reconcile's cancel, which must also resume collection of the kept subscription's invoices. No new handler; the correction still takes up to about 25 hours.
- **Option 7: shorten Session lifetime** with `expires_at`, to as little as 30 minutes. It caps the tail only while the completion webhook is delayed or failing; once it arrives, option 3's sweep ends the other pages.
- **Option 8: make the app the only writer of subscriptions.** Closes the race completely, but changes the purchase page, disclosures and consent.

## Resolution (decided)

Options 2, 3, 5 and 6, decided 2026-10-14, each for the case the one before cannot close. Rules R24 and R25 state options 2 and 3.

- **Option 9: one exit for every Session handed back,** decided by the owner, 2026-11-18, and built on 2026-11-25 as decided. Both of the adapter's exits, the reuse path's and the create path's, return through `handBackNewestOpenCheckoutSession`. It runs the reconcile (`reconcileOpenCheckoutSessions`) on the Session the request holds, the one it created or the one the reuse path found, and then the subscription re-check on the Session the reconcile keeps. So both exits hand back only the newest open subscription Session the request's listing found (up to `OPEN_CHECKOUT_SESSION_RECONCILE_LIMIT`, 10), after expiring the others, and a failed listing or expire fails the request. The Session the reuse path finds is the customer's newest open one (its `limit: 1` listing; Stripe lists newest first, though the order within one second is unproven) and has passed the plan, variant and renewal-terms match. So the reuse exit hands back another Session only when the reconcile's listing holds an active one with renewal metadata that sorts after it by `created`, then ID (`getCanonicalOpenCheckoutSession`): one created after the `limit: 1` listing, or one created in the same second with a larger ID, which may predate that listing. That Session can be for the other plan or other renewal terms, as on the create exit (BUG-245's two-tab case): the buyer sees its plan and price on Stripe's page, and its metadata carries the hash and version of the disclosure of the request that created it. That request's pricing dialog showed that disclosure and took the renewal opt-in, which the server also requires (`app/pricing/subscribe-to-plan.ts:71-76`), from the same user: the listing holds only this customer's Sessions, and the webhook records consent only when the Session's user, customer and plan match the subscription (`stripe-webhook-processor.ts:165-175`). The returned Session does not record what this request's dialog showed, the plan the buyer asked for. Every request keeps the newest, so two whose listings see the same Sessions hand back the same one; if each kept its own, each would expire the other's. A Session created after the reconcile's listing can stay open, but only a later request that expires the older ones hands it back. So at most one Session handed back is open at a time while each listing returns every open Session the customer has; with more than 10 open, one can be handed back beside an older one. A concurrent create can also expire the Session a request is about to hand back, as on the create path: that link no longer completes, and the buyer starts checkout again. No check before the return closes that window, since the expire can land after it. When that expire lands between the reuse path's two listings, the reuse path still ranks the Session it found newest: it expires the Session the other request kept, and hands back a link that no longer completes. Both buyers start checkout again, and no two pages stay open. It takes two overlapping requests, one for each plan, while two pages are already open, which itself takes an earlier failed request (found in review, 2026-11-25). The buyer starts again by reopening the plan dialog, which mints a new idempotency key: a form still on screen replays the link it was given (ADR-015). A fix that dropped the found Session once the listing omitted it was tried and withdrawn: the Session may have completed instead, and then handing back an older open page would be the worse error. A request is refused, not handed an expired page, when the only Session it holds passes its 24-hour expiry between the adapter's check and the reconcile; before, the reconcile returned that Session (found in review, 2026-11-26). No lock is added: the adapter holds no database lock across Stripe calls, on purpose (BUG-245, in the comment above `reconcileOpenCheckoutSessions`). The reuse path gains one listing, and an expire for each other open Session. Red first in `stripe-checkout-sessions-one-exit.test.ts`, with `FakeStripeCheckoutClient`'s `setExpireFault`, `setRetrieveOverride` and `setCreateFault`: both reproductions in Evidence end with one open subscription Session after the retry; a reuse that cannot expire another open Session is refused; a reuse that hands back a Session while a concurrent create fails to expire it leaves the create's Session open and unreturned until a later request expires the first; a reuse whose reconcile finds a newer Session that a concurrent request created for the other plan hands that one back and expires the Session it found; when the Session a reuse found completes beside that newer one, the request is refused and no Session stays open; and a reuse with no other Session open makes one more listing and no expire. Two more cases there were not red for option 9: one states the limit above, and one failed before the refusal on expiry. The other open Sessions are expired before the subscription re-check. So when that re-check cannot list the subscriptions, the request is refused with the others ended and the kept Session still open, handed back to nobody, until a later request ends it or hands it back. When the re-check finds a subscription and fails to expire the kept Session, later requests are refused at their first subscription check, so that Session stays open until the completion sweep ends it, if it predates that event, or it reaches its 24-hour expiry. The adapter sets no idempotency key of its own on an expire (2026-11-28). Stripe documents that it replays the answer saved under a key, server errors included, for at least a day. So the adapter's earlier key, fixed per Session and on `main` for every expire, would repeat one failed expire on every later request: a buyer switching plans during such a failure would be refused the other plan's page until the earlier page lapsed. This was not observed. The SDK keys each call afresh. One case there was red first on the fixed key, with the fake replaying a saved server error, and two more prove that a failed reconcile listing fails the request on either exit; they fail when the adapter swallows that failure. The provider contract's fourteenth scenario runs the first reproduction and its retry through the adapter, on the fake and in Stripe TEST mode, with the read and the expire failed by the case for the one request that must fail; the adapter's `stripe` input narrowed to `StripeCheckoutSessionsClient` for it.
